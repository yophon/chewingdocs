# 第一个插件与开发循环

第二层把 dsh 拆开看了一遍:09、10 篇讲 Cordis 的插件、服务、事件和可回收的副作用,11 篇讲 bundle → profile → home → `--patch` 四层叠加,12 到 17 篇讲主循环、工具管线、LLM 层、上下文和会话日志。从这一篇开始换个视角,站到插件作者这一边。第三层前半(18-21)依次回答四个问题:插件怎么写、怎么跑起来,工具怎么写,配置和分发怎么做,新模型怎么接。

这一篇先把开发循环跑通:写一个最小插件,用一个 overlay 文件把它挂进 Web profile,再做一个能看到效果的完整例子。最后讲新行为该挂在哪个扩展点,以及怎么调试。

> 一句话先记住:**dsh 没有可以打补丁的"核心"**。你写的插件和内置插件地位相同,挂在同一棵插件树上,通过 `ctx` 注册能力,卸载时这些注册会自动撤销。开发循环只需要两样东西:一个 overlay 文件,加上 `dsh web --patch`。

## 一、插件长什么样

### 1.1 最小模块

插件就是一个导出 `apply` 的 TypeScript 模块。框架加载插件时调用 `apply`,传入 `ctx`:

```ts
import type { Context } from '@deepseek-ai/cordis'

export const name = 'hello-plugin'

export function apply(ctx: Context) {
  // inject 声明的依赖在 apply 运行前已经就绪
  console.log('[hello-plugin] plugin loaded!')
}
```

模块级可以导出的东西:

| 导出 | 必需 | 作用 |
| --- | --- | --- |
| `apply(ctx, config)` | 是 | 注册能力的入口。第二个参数是校验过的配置 |
| `name` | 否 | 插件名 |
| `inject` | 否 | 依赖的服务名数组,例如 `['tools', 'systemPrompt']`。依赖全部就绪后才会调用 `apply` |
| `Config` | 否 | 同名的 Schemastery schema,加载时校验配置并填默认值(见 20 篇) |

通过 `ctx` 注册的东西,包括事件监听、工具、LLM adapter 和 `ctx.effect()` 返回的清理函数,都会在插件卸载时撤销。需要显式清理的资源(比如定时器、连接)放进 `ctx.effect()`,让它返回 disposer。

### 1.2 对象形态与类形态

同样的插件也可以写成对象形态或类形态:

```ts
import { Service, type Context } from '@deepseek-ai/cordis'

// 对象形态
export default {
  name: 'my-plugin',
  inject: ['tools'],
  apply(ctx: Context) { /* ... */ },
}

// 类形态:给别的插件提供服务时用
export class MyService extends Service {
  static inject = ['tools']
  constructor(ctx: Context) {
    super(ctx, 'myService')
  }
}
```

大多数情况用函数形态就够了。只有要把能力作为服务暴露给其他插件(`ctx.myService`)时才用类形态。三种形态的区别、`inject` 的等待和重载语义见 09 篇,Fiber 状态机见 10 篇。

## 二、开发循环:overlay + `--patch`

### 2.1 准备

两种跑法,区别只在命令前缀:

- **源码仓库**:fresh checkout 之后先 `pnpm run build`,之后用 `pnpm dsh <args...>`。这个脚本用 tsx 直接跑 `apps/cli/src/bin.ts`,不会自动重新构建
- **已安装的 CLI**:直接用 `dsh <args...>`

下面以源码仓库为例,在仓库根目录建一个练习目录:

```bash
mkdir -p scratch-plugin/src
```

把 1.1 的代码存为 `scratch-plugin/src/my-plugin.ts`。

### 2.2 写 overlay

`scratch-plugin/cordis.yml` 就是一个 patch 列表,用 `insert` 插入一行新的插件配置:

```yaml
- insert:
    - id: hello
      name: '/absolute/path/to/deepseek-harness/scratch-plugin/src/my-plugin.ts'
```

`id` 是这一行在整棵树里的地址,以后用 patch 覆盖它、在 Plugin Manager 里开关它,都靠这个 id。`name` 可以是绝对路径、file URL 或包名。

关于路径:入门教程要求写绝对路径。但当前源码里,`--patch` 文件中 `insert` 行的 `./`、`../` 路径会被锚定到 patch 文件所在目录(`anchorInsertedPluginNames`),app-boot README 也这样写。两种都能用,写绝对路径最不容易出错。

### 2.3 启动

```bash
pnpm dsh web --patch ./scratch-plugin/cordis.yml
```

打开 `http://127.0.0.1:3080`,终端里能看到 `[hello-plugin] plugin loaded!`。

`--patch` 是第四层,在 profile 和 home 两层 patch 之后应用,可以重复写多次,按命令行顺序叠加(见 11 篇)。它只影响这次启动,不会写进 profile,适合开发期挂本地插件。

### 2.4 改了代码之后:HMR 默认不监听源码

框架文档说加载了 `@deepseek-ai/dsh-hmr` 之后,改插件源码会自动卸载旧实例、加载新实例。但要注意 base bundle 里 `hmr` 这一行的默认配置:

```yaml
- id: hmr
  name: '@deepseek-ai/dsh-hmr'
  disabled: !!js "!ctx.get('profileContext')"
  config:
    root: []
```

`root: []` 的意思是**只保留配置文件监听,不监听源码模块**。Web profile 默认会热重载 profile 和 home 两层的 `cordis.patch.yml`,但改插件 `.ts` 文件不会触发重载。所以有两种做法:

1. **最简单**:改完代码,`Ctrl+C` 后重新执行 `pnpm dsh web --patch ...`
2. **开启源码监听**:在同一个 overlay 里覆盖 `hmr` 行。hmr README 给的写法是 `root: ["."]`,这里的 `.` 相对 HMR 的 base 目录(默认是配置树的 base URL,也就是 profile 目录)

```yaml
- id: hmr
  disabled: false
  config:
    root: ['/absolute/path/to/deepseek-harness/scratch-plugin/src']
- insert:
    - id: hello
      name: '/absolute/path/to/deepseek-harness/scratch-plugin/src/my-plugin.ts'
```

`root` 是 chokidar 的监听根,README 只演示了 `["."]`。上面把它指向 profile 目录之外的插件目录,本文没有逐项核实,请在你的版本上实测。另外,HMR 的配置监听只覆盖 profile 的 `cordis.patch.yml` 和 `$DSH_HOME/cordis.patch.yml`(源码里的 `patchFiles`),不包括 `--patch` overlay,**改 overlay 本身要重启**。

热重载之所以能安全进行,是因为所有注册都是 effect:旧实例卸载时它的监听器、工具、section 全部撤销,新实例重新注册,不会留下重复注册。

## 三、完整例子:给每轮对话加一条项目约定

下面的插件做三件看得见的事,用的都是第二层讲过的扩展点:

- 往 system prompt 里加一段固定的项目约定(`ctx.systemPrompt.section()`,16 篇)
- 观察每次工具调用的最终结果(`tools/result`,13 篇)
- 在每轮结束时打一行日志(`session/event` 上的 `turn/end`,17 篇)

```ts
import type { Context } from '@deepseek-ai/cordis'
// 只为拿到各包的类型声明合并(ctx.systemPrompt 和事件签名)
import type {} from '@deepseek-ai/dsh-system-prompt'
import type {} from '@deepseek-ai/dsh-tools'
import type {} from '@deepseek-ai/dsh-session'

export const name = 'house-rules'
export const inject = ['systemPrompt']

export function apply(ctx: Context) {
  // 1. 静态 section:文本不变,不破坏缓存前缀
  ctx.systemPrompt.section({
    name: 'house-rules:conventions',
    order: 4000,
    text: 'In this repository, run `pnpm test` before claiming a change works.',
  })

  // 2. 观察冻结后的最终工具结果;监听器抛错会被隔离,不影响调用
  ctx.on('tools/result', (exec, result) => {
    ctx.logger.info('[house-rules] %s -> %s', exec.name, result.isError ? 'error' : 'ok')
  })

  // 3. turn/end 是会话事件,不是 Cordis 事件:听 session/event 再看 type
  ctx.on('session/event', (session, event) => {
    if (event.type !== 'turn/end') return
    ctx.logger.info('[house-rules] %s turn %d ended: %s',
      session.id, event.data.turn, event.data.reason.kind)
  })
}
```

几个要点:

- **`order` 的取值**:section 按 `order` 升序拼接,相同 order 再按名字排序。仓库内置 section 的位置是集中分配的:身份 -1000、persona 前缀 0、各工具说明 1000 到 3100、生成的 tools SDK 5000、环境相关后缀 10000 以后。外部插件可以用任意有限数,上例的 4000 落在工具说明之后、tools SDK 之前
- **section 名字唯一**:同一层重复注册会抛错。要给某个 agent 单独覆盖,通过 `agent.ctx` 注册同名 section
- **文本保持稳定**:section 每次请求都会重复发送。往里放时间戳或计数器,每一轮都会改写缓存前缀(16 篇)。会变的事实应该用 `ctx.systemPrompt.context()` 或 `agent.inject()`
- **`turn/*`、`step/*`、`tool/call`、`tool/result` 都是持久化的会话事件类型**,不是同名的 Cordis 事件。直接 `ctx.on('turn/end', ...)` 永远不会触发
- **类型**:`import type {} from '...'` 引入各包对 `Context` 和 `Events` 的声明合并,`exec`、`result`、`event.data` 才有类型

把 overlay 里的 `name` 指向这个文件,重启后在 Web 里让模型跑一条命令,终端会依次打出工具结果和 turn 结束的日志。

## 四、新行为该挂在哪

### 4.1 architecture.md 的对照表

`docs/architecture.md` 的 "Where new behavior goes" 一节给出了规则:**新行为挂到有文档的扩展点上,改主循环本身要同步更新这张表**。节选:

| 想做的事 | 机制 |
| --- | --- |
| 接入一个模型提供方 | 在 `ctx.llm` 上注册 adapter(21 篇) |
| 给模型加一个能力 | 在 `ctx.tools` 上注册,schema 自动进入 prompt 组装(19 篇) |
| 加一个人用的命令 | 注册到 `ctx.commands`,不经过模型回合 |
| 管理后台任务 | 注册到 `ctx.jobs`,`job_*` 工具负责读取和停止 |
| 加文件系统访问或策略 | 注册 `ctx.fs` provider,或监听 `fs/*` 事件 |
| 拦截一次请求、工具调用或一轮 | 用对应的 `agent/*` 或 `tools/*` 事件;`agent/turn-stopping` 可以结束一轮 |
| 给模型补充上下文 | `agent.inject()`,在下一次被接纳的请求里出现 |
| 做 UI 或编辑器集成 | 驱动 `ctx.agents`,从 `session/event` 渲染 |
| 加持久化的会话状态 | 扩展 `SessionEventMap`,从日志渲染和回放(17 篇) |
| 只对一个 agent 生效的注册 | 用那个 agent 的 `agent.ctx` |

### 4.2 常见需求对应的扩展点

extension cookbook 的 feature → mechanism 表把每个产品功能都对应到一个扩展点上的监听器,**没有一行需要改主循环**。结合工具管线的选择规则(13 篇),常见需求可以这样对应:

| 需求 | 用什么 | 说明 |
| --- | --- | --- |
| 按策略允许 / 拒绝 / 询问某次工具调用 | `tools/pre-execute` waterfall | 可重排的策略层,返回 `PreToolDecision`,必须调 `next()` 往下传 |
| 一条任何后续监听器都推翻不了的禁令 | `ctx.tools.guard()` | 单调的最终拒绝 |
| 超时、重试、计量 | `tools/execute` | 包住一次 dispatch 的生命周期 |
| 改写结果或附加上下文 | `tools/post-execute` | 显式改写 |
| 审计、指标、采集 | `tools/result` | 只读观察最终结果 |
| 静态的 prompt 片段 | `ctx.systemPrompt.section()` | 本篇的例子 |
| 每步之前检查或改写输入 | `agent/pre-step` | 自动压缩就挂在这里 |
| 请求失败后恢复 | `agent/request-error` | 上下文溢出恢复挂在这里 |
| 每轮结束后续跑 | 观察 `turn/end` 会话事件后 `followup()` | `/loop` 的实现方式 |
| 过滤某个 agent 可见的工具 | `ctx.tools.restrict()` | 展示、查找、执行三处保持一致 |

`system-prompt/assemble` 也是一个扩展点,但它是"整份组装结果"的变换,返回值是权威的,监听器要自己负责保留 PTC 模式和结构化输出协议的内容。能用 `section()` 或 `restrict()` 解决的,不要用它。

## 五、能力接缝:三种角色

### 5.1 心智模型

当一个能力通用到需要可替换的实现时,dsh 把它拆成三种角色,合起来叫一个**能力接缝**(capability seam):

| 角色 | 职责 | Bash 的例子 |
| --- | --- | --- |
| **Service Definition** | 定义 Cordis 服务和请求 / 结果类型,通常是抽象 `Service` 类 | `dsh-shell` |
| **Service Provider** | 实现这个服务 | `dsh-bash-local`,在本机执行命令 |
| **Consumer** | 使用这个服务,常见的是一个给模型调用的工具 | `dsh-tool-bash`,`inject: ['shell']` |

依赖方向是关键:Provider 依赖 Definition,Consumer 依赖 Definition,**Provider 和 Consumer 互不依赖**。所以在 `cordis.yml` 里把 provider 那一行换成另一个实现了同一服务的包,工具不用改一行代码。文件系统和子进程 provider 共享同一个执行环境,把它们指向远程沙箱,Bash、PTY、LSP 会一起跟过去。

注意术语:**单独一个角色不叫 seam**,一个普通的扩展点也不叫 seam。

### 5.2 什么时候定义新接缝

- **默认不拆**。一个简单的工具插件不需要三个包,`practice/index.md` 原话是"Do not split preemptively"。角色需要独立演化或独立替换时才拆包,一个包也可以同时承担多个角色
- **已有接缝就去消费它**。要执行命令,`inject: ['shell']`;要读写文件,用 `ctx.fs`;要跑后台任务,用 `ctx.jobs`。不要绕过接缝直接调 `child_process`,否则沙箱和远程执行都管不到你
- **请求 / 结果类型归 Service Definition 所有**,Provider 和 Consumer 只依赖 Definition 包
- **默认值显式解析**。在一个显式的 `resolve(request): Spec` 步骤里处理默认值,不要把 `?? default` 散落在 `run()` 里

当前内置的接缝家族和包关系在 `docs/capability-seams.md`(自动生成的图)里。

## 六、调试

| 手段 | 用法 |
| --- | --- |
| 看组合后的配置树 | `pnpm dsh web --patch ./scratch-plugin/cordis.yml --dump-config`,每一行旁边有注释,标出来自哪个文件、被哪些 overlay 改过。`!!js` 表达式不求值,匹配不上的 patch 目标打到 stderr |
| 只看 bundle 层 | `--dump-default-config` |
| 看配置 schema | `--dump-config-schema`,输出 profile 条目和 patch 的 JSON Schema,不挂载插件 |
| 启动失败 | 必需插件激活失败时,终端打印失败插件、挂起插件和缺失的服务,最后一行 `Full diagnostics:` 指向 `$DSH_HOME/logs/startup-<timestamp>-<uuid>.log`(默认 `~/.dsh/logs/`)。报告里的原始错误可能含配置值或凭证,分享前先检查 |
| 插件一直不加载 | 多半是 `inject` 的某个服务不存在,插件停在 PENDING(10 篇)。用 `--dump-config` 确认 provider 那一行在不在、有没有被禁用 |
| 运行时 API 查询 | Creator 模式(`cordis` 预设)带两个只读工具 `cordis_inspect_list` 和 `cordis_inspect_query`,可以查服务方法、事件签名、当前 Loader 条目及其配置状态(20 篇) |

`ctx.logger` 的输出直接打到启动 dsh 的终端,开发期最直接的观察手段就是它。

## 踩坑

1. **直接 `ctx.on('turn/end', ...)`**——`turn/end` 是会话事件类型,不是 Cordis 事件。听 `session/event`,再判断 `event.type`
2. **改了插件源码却没看到变化**——base 的 `hmr` 行默认 `root: []`,不监听源码。重启,或在 overlay 里覆盖 `hmr` 的 `root`
3. **改了 `--patch` overlay 以为会热更新**——HMR 只监听 profile 和 home 两层 patch,改 overlay 要重启
4. **在 section 文本里放时间、计数器**——每轮都改写缓存前缀。会变的事实用 `context()` 或 `agent.inject()`
5. **忘了写 `inject`**——`apply` 里 `ctx.systemPrompt` 是 undefined,或者服务还没就绪就被调用。依赖什么就声明什么
6. **监听 `tools/result` 却没导入 `@deepseek-ai/dsh-tools`**——这个包对 `Events` 的声明合并没有生效,事件名和参数都没有类型。只需要类型时加一行 `import type {} from '包名'`
7. **一上来就拆三个包**——简单插件不需要接缝。角色需要独立演化时才拆
8. **绕过已有接缝直接 spawn 进程**——沙箱后端和远程执行环境都管不到。执行命令走 `ctx.shell` / `ctx.subprocess`
9. **以为 overlay 改动会进 profile**——`--patch` 只影响当次启动。要长期生效,写进 profile 的 `cordis.patch.yml`,或打成 bundle 安装(20 篇)

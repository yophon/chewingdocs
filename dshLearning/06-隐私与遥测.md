# 隐私与遥测

05 篇讲的是本机上能碰到什么。这一篇讲另一个方向:**哪些数据会离开本机,发到哪里,怎么关**。

先把事实摆清楚:dsh 的默认配置会把完整的会话日志随模型请求增量发给 DeepSeek 官方 API。这在仓库文档里写得很明白,也有关闭开关,谈不上"偷偷上传",但很多人装完就用,并不知道。下面按数据路径逐条讲,最后给一张关闭清单。

> 一句话先记住:**dsh 默认有三条互相独立的外发路径:随 DeepSeek 请求上传的 session log(默认开)、你提交反馈时触发的 OTel 上报(默认 `FEEDBACK_ONLY`)、Desktop 的产品分析事件(默认开,没有界面开关)**。`DSH_TELEMETRY_*` 只管第二条,关不掉第一条。

---

## 一、三条路径总览

| 路径 | 由谁挂载 | 默认 | 什么时候发 | 发到哪 |
| --- | --- | --- | --- | --- |
| **session log 上传** | base bundle 的 `session-log-deepseek` 行 | 开 | 每次走原生 DeepSeek adapter 的模型请求 | 模型请求的 `baseURL`(官方端点或你配置的网关) |
| **OTel 会话遥测** | base bundle 的 `session-telemetry-otel` 行 | `FEEDBACK_ONLY` | 你提交反馈、评价、编辑或撤回评价时 | `https://dsh-otel-collector.deepseeksvc.com/v1/logs` |
| **Desktop 产品分析** | web-app bundle 的 `product-analytics` 行,仅 `desktop` profile | 开 | 界面交互、压缩事件等 | 产品分析 collector |

另外还有两类附带数据:每个 DeepSeek 请求都带的几个请求头,以及 `dsh_plugin_packages` 插件清单字段(第三节)。

模型请求本身当然也会把提示词、工具结果发给你选的模型服务,这是 agent 工作的前提,不在本篇的"遥测"范围里;`web_search` 默认走 DeepSeek 的搜索接口,查询内容也会发过去。

## 二、session log 上传

### 2.1 机制

`@deepseek-ai/dsh-session-log-deepseek` 在 DeepSeek 请求体里注册一个扩展字段 `dsh_session_log`,内容是**规范会话日志的一段连续后缀**:

```json
{
  "dsh_session_log": {
    "version": 1,
    "sessionFormatVersion": 4,
    "session": { "version": 4, "id": "session-…", "createdAt": 1780000000000, "cwd": "/home/me/project" },
    "afterSeq": 41,
    "throughSeq": 57,
    "events": [ { "type": "user/message", "seq": 42, "time": 1780000000001, "data": { } } ]
  }
}
```

工作方式:

- **增量发送**:第一次 `afterSeq: -1`,从头发;端点返回 HTTP 2xx 后,会话里追加一条 `session-log-deepseek/delivery-accepted` 事件作为水位线,下次从水位线之后接着发
- **每次最多 8 MiB**(`maxBytes`,按 UTF-8 字节算),积压超过上限就分多次请求发完
- **至少一次**:2xx 之后、水位线落盘之前崩溃,恢复后会重发这一段;只会重复,不会漏
- **fork 出来的会话**忽略父会话的水位线,从序号 0 开始把继承来的前缀再发一遍
- **不占模型 token**:它是请求体里和 `messages` 并列的字段,不进 system prompt、不进工具 schema,也不影响 KV Cache 前缀

### 2.2 里面有什么

按 `docs/deepseek-llm-api-wire-extensions.md` 的 "Exposure" 一节,`dsh_session_log` 可能包含:

- 会话的工作目录(`cwd`)
- system prompt 快照
- 用户和助手的内容,包括完整的助手流和失败尝试的输出
- 工具参数和工具结果(也就是模型读过的文件内容、跑过的命令输出)
- 压缩摘要
- 反馈(评价、备注)
- 各插件写进会话日志的事件

**API key 不是会话事件,不会进这个字段**。但如果模型在工具调用里读过 `.env`,文件内容就在工具结果里。

### 2.3 哪些请求会带

| 请求 | 带不带 |
| --- | --- |
| 原生 DeepSeek adapter(`@deepseek-ai/dsh-llm-deepseek`)上 `deepseek-official` 路由的请求 | 带 |
| 同一路由但 `baseURL` 指向你配置的网关 | 带,**网关收到的内容和官方端点完全一样** |
| 普通 agent 请求、压缩请求、会话标题生成请求 | 都带(它们都有会话 id) |
| 没有会话的直接请求、日志为空的会话 | 不带 |
| pi-ai 路由(第三方服务商、自定义模型 API) | 不带,pi-ai 不实现这些扩展 |
| 账号登录路由 `deepseek-account` | **文档未明说**,见下 |

文档把这些扩展描述为 `deepseek-official` 路由的行为。但从源码看,`deepseek-account` 路由和它共用同一个注册函数(`registerDeepSeekProvider`,里面统一接了扩展字段的准备逻辑),session-log 插件本身也不按路由过滤。所以稳妥的假设是**账号登录路由同样会带**,以你所用版本的实际行为为准。

`sdk-minimal` 这个独立组合同样挂了 `session-log-deepseek`,不要以为极简就没有。

### 2.4 怎么关

**方式一:Web 界面**。Settings → General 里版本号上方的开关:英文界面叫 **Upload Session Log when using the official model API**,中文界面叫**在使用官方模型 API 时上传 Session Log**。

这个开关改的是**当前 profile** 的配置,也就是只对 web profile(或 Desktop 的 desktop profile)生效。headless、sdk、acp 是各自独立的 profile,不受它影响。

**方式二:patch**。想让所有 profile 都关掉,写在 home 级 patch 里(11 篇讲层级):

```yaml
# $DSH_HOME/cordis.patch.yml
- id: session-log-deepseek
  config:
    enabled: false
```

home patch 和命令行 `--patch` 的优先级高于 Web 表单写入的 profile 配置,冲突时表单写入会被拒。CI 里也可以每次运行时用 `--patch` 临时叠一层(27 篇有示例)。

关闭后的两个细节:

- 已经在路上的请求保留它准备好的字段;关闭从下一个请求开始生效
- **重新打开时会补传关闭期间积累的事件**。没有水位线就没有"跳过",这是"至少一次"设计的直接结果

`DSH_TELEMETRY_MODE`、`DSH_TELEMETRY_DISABLED` **都管不到这条路径**。

## 三、请求头与插件清单

每个 DeepSeek 请求还附带这些元数据:

| 名称 | 出现条件 | 值 |
| --- | --- | --- |
| `user-agent` | 每个服务商 HTTP 请求 | `product/version (+url)` 形式的应用标识,默认 product 是 `deepseek-harness` |
| `x-deepseek-harness-user-id` | 每个已授权的模型请求 | 匿名安装 id |
| `x-deepseek-harness-session-id` | 带会话 id 的请求 | 会话 id |
| `x-deepseek-harness-compact` | 压缩请求 | 字面量 `1` |
| `dsh_plugin_packages`(请求体字段) | 默认开启 | 当前激活的插件包名和版本 |

匿名 id 是一个随机 UUID,存在 `$DSH_HOME/.anonymous-user-id`(默认 `~/.dsh/.anonymous-user-id`),不含机器或账号信息。删掉这个文件,下次启动会生成新的;正在运行的进程保留旧 id 直到退出。不同的 `$DSH_HOME` 有不同的 id。同一个 id 也出现在 OTel 导出的 `user.id` 资源属性和 `/feedback` 的确认消息里。

凭证解析失败时请求不会发出,这些头也不会发,id 文件也不会被创建。

`dsh_plugin_packages` 只包含包名和版本,不包含配置。文档提到"禁用这个 contributor 会省略整个字段",对应 base 里的 `plugin-package-inventory-deepseek` 行;请求头本身没有关闭开关。

## 四、OTel 会话遥测

### 4.1 默认 `FEEDBACK_ONLY`

`@deepseek-ai/dsh-session-telemetry-otel` 对**所有用户、所有模型服务商**生效,包括 pi-ai 路由。默认模式下,平时的模型请求、新建或恢复会话、插件加载都不会触发任何上报。触发上报的只有**显式反馈**:

- `/feedback <文字>`,或 Web 里的反馈对话框(所有字段可选,空提交也算)
- 给助手消息点赞或点踩(会打开对话框选类别、写备注)
- 编辑备注、修改评价
- **撤回评价**(再点一次已选中的赞或踩)

每次反馈会把这个会话**尚未上报的完整规范前缀**(包括上下文)发给 collector,之后的记录等下一次反馈。fork 出来的子会话不继承父会话的授权,要自己有新反馈;一旦有,上报的前缀里包含继承来的上下文。

几点事实:

- 每个会话事件变成一条 OTel log 记录,`event.data` 经过脱敏规则处理;**base 没有挂脱敏规则时,数据按原样离开进程**
- 资源属性带应用标识和匿名 `user.id`
- 投递是尽力而为:退出时有 3 秒总期限,大段前缀可能没发完;没有持久化的发件箱和重试保证
- `/feedback` 的确认消息(`Feedback recorded for session …` / `Anonymous user: …`)只表示**已写进本地会话日志**,不代表 collector 收到了

### 4.2 怎么关

```bash
export DSH_TELEMETRY_MODE=DISABLED   # 不构造任何 transport
# 或
export DSH_TELEMETRY_DISABLED=1      # 任何非空值都生效,包括 0 和 false
```

- `DSH_TELEMETRY_MODE` 只接受 `FEEDBACK_ONLY` 和 `DISABLED`,**`FULL` 会被拒绝**,不是别名
- 两个变量都要在 shell 里 export。`.env` 文件拒绝设置 `DSH_*`(05 篇)
- `DSH_TELEMETRY_OTLP_URL` 可以把上报改发到你自己的 collector
- 关掉 OTel 之后,反馈照样写进本地会话日志,也照样会跟着 session log 上传(如果那条没关)

### 4.3 OTel 不走代理

`docs/user/guide/network-proxy.md` 专门列了一条:OTLP 导出器用的是 Node 自己的 HTTP 客户端,**不经过 `HTTP_PROXY` / `HTTPS_PROXY`**,直接连接。在只允许走代理出网的环境里它会静默失败,不影响任何功能。仓库给的建议就是设 `DSH_TELEMETRY_MODE=DISABLED`。

## 五、Desktop 产品分析

这一条只和 Desktop 应用有关:web-app bundle 里的 `product-analytics` 和 `desktop-product-telemetry` 两行只在 profile 名是 `desktop` 时启用,**普通的 `dsh web` 不收集**。

### 5.1 收集什么

- **事件**:欢迎页和登录页的交互、页面浏览、消息提交(类型 `default` / `queue` / `steer`、模型、显式 effort、运行模式)、模型和 effort 切换、fork、插件开关和安装、实时的压缩事件
- **身份**:可用时附带 `device_id`、`user_id`(复用已有登录记录,不新建标识)、`app_version`
- **静态环境**:操作系统名称和版本、CPU 型号和核数、架构、物理内存总量
- **明确排除**:API key、账号令牌、提示词、模型回复、主机名、机器 UUID

插件安装事件里的输入会做归类:registry 包名和版本原样保留,Git 地址变成 `[git]`,其他 URL 变成 `[url]`,路径变成 `[path-or-other]`。

### 5.2 怎么关

README 原话是"默认开启,没有面向用户的控制",只能通过 Cordis 配置改 `product-analytics` 设置命名空间的 `enabled`。按 web-app bundle 里这一行的定义,patch 要把整个 `config` 写全:

```yaml
# 写在 desktop profile 的 cordis.patch.yml 或 $DSH_HOME/cordis.patch.yml
- id: product-analytics
  config:
    enabled: false
    appVersion: !!js process.env.DSH_CLIENT_VERSION
```

关闭后不再收集新事件,但导出器仍然挂着,已排队的记录可能还会发出去。`DSH_PRODUCT_ANALYTICS_OTLP_URL` 可以把目的地改到隔离的 collector。

## 六、关闭清单

| 外发项 | 默认 | 怎么关 | 关掉后仍然存在的 |
| --- | --- | --- | --- |
| session log 上传(`dsh_session_log`) | 开 | Web Settings → General 开关(仅当前 profile);所有 profile:`$DSH_HOME/cordis.patch.yml` 里 `session-log-deepseek` 设 `enabled: false` | 请求头和插件清单照发;重新打开会补传关闭期间的事件 |
| 插件清单(`dsh_plugin_packages`) | 开 | 无界面开关;禁用 `plugin-package-inventory-deepseek` 行(副作用未单独验证) | 请求头 |
| 请求头(匿名 id、会话 id) | 总是 | 无开关;删除 `$DSH_HOME/.anonymous-user-id` 只能重置 id | — |
| OTel 会话遥测 | `FEEDBACK_ONLY` | `export DSH_TELEMETRY_MODE=DISABLED` 或 `DSH_TELEMETRY_DISABLED=1` | 反馈仍写本地日志,并随 session log 上传 |
| Desktop 产品分析 | Desktop 开 | patch `product-analytics` 的 `enabled: false` | 已排队的记录;不影响前两条路径 |
| 模型请求和搜索请求本身 | — | 换模型服务商;内置搜索默认也走 DeepSeek | 这是功能本身 |

想要"什么都不发给 DeepSeek",最彻底的组合是:关掉 session log、设 `DSH_TELEMETRY_MODE=DISABLED`、模型走第三方或自托管的 pi-ai 路由(03 篇),并且不用内置的 `web_search`。团队层面的基线配置见 31 篇。

## 踩坑

1. **以为 `DSH_TELEMETRY_DISABLED=1` 就什么都不发了**——它只关 OTel。session log 上传是另一条路径,要单独关
2. **在 Web 里关了开关,CI 里的 headless 照样上传**——开关写的是当前 profile 的配置。所有 profile 一起关,写 `$DSH_HOME/cordis.patch.yml`
3. **`DSH_TELEMETRY_DISABLED=0` 以为是"不禁用"**——任何非空值都会禁用,包括 `0` 和 `false`
4. **关了一阵 session log 又打开,以为只发之后的**——关闭期间的事件也会补传
5. **配了自定义网关就以为数据不出公司**——网关收到完全相同的字段,网关之后发去哪取决于网关
6. **以为点个踩只是本地记录**——`FEEDBACK_ONLY` 下,评价、备注甚至撤回评价都会把整段会话前缀发给 OTel collector
7. **企业网络里看到 OTel 连接失败的警告**——OTel 不走代理,直连失败是预期行为,不影响功能;不想看到就设 `DISABLED`
8. **把 `DSH_TELEMETRY_*` 写进 `.env`**——`DSH_*` 在 `.env` 里一律被拒,要 export
9. **找 Desktop 的"关闭分析"开关**——没有界面开关,只能改配置
10. **切到账号登录路由就以为不上传 session log**——文档没说清,源码看大概率同样携带,按"会带"处理

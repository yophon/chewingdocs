# 团队落地:安全基线、版本锁定与私有化

30 篇回答"该不该用 dsh";这一篇假设团队已经决定试一试,要回答的是"怎么在团队里安全地用起来"。内容大多在前面各篇出现过——05 篇的权限与沙箱、06 篇的隐私与遥测、11 篇的四层叠加、20 篇的打包分发、27、28 篇的无人值守和公网部署——这里不重复机制,只把它们收拢成团队能执行的基线、流程和一页清单。本站 Claude Code 系列的安装登录与 settings 一篇讲过 managed 层怎么给整个组织下发策略;截至这个版本,dsh 的文档里没有对应的强制层,所以下面很多"基线"要靠运行环境本身来兜底。

> 一句话先记住:**把 dsh 当成"在隔离环境里运行、版本钉死、数据出口逐条确认过的实验平台"来落地**。它没有经过安全审计,每个小版本都可能 breaking,默认还会把会话日志发给 DeepSeek——这三件事决定了团队基线的形状。

---

## 一、先接受三个前提

| 前提 | 出处 | 对团队意味着什么 |
| --- | --- | --- |
| 实验性 developer preview,未经安全审计 | `SAFETY.md` | 不能把 dsh 当作不可信工作负载的唯一安全控制 |
| "THERE WILL BE COMPATIBILITY-BREAKING CHANGES" | `README.md` | 版本必须钉死,升级是一次有计划的变更 |
| 所有发布都是预发布 | 仓库 20 个 `dsh-v*` tag 全部带 alpha / rc 后缀 | 没有"稳定版"可以跟,只能自己选一个验证过的版本 |

还有一条容易忽略:dsh 的扩展是同进程插件,团队 bundle、MCP server、第三方插件都和 Host 同权。**落地的大部分工作,是决定"谁的代码可以进这个进程"**。

## 二、安全基线

### 2.1 运行环境

`SAFETY.md` 的建议是:最小权限运行,优先用一次性虚拟机、容器或专用环境,备份它能访问的文件,不暴露不想承担风险的凭证和数据。落到团队里:

- **默认在 VM 或容器里跑**,工作目录只挂需要的仓库;需要 `danger-full-access` 的任务只在可丢弃的环境里开
- 容器里**不要挂宿主机的 `~/.ssh`、云厂商凭证目录**:dsh 的沙箱默认不限制读(05 篇),挂进去就等于给了模型

### 2.2 权限预设怎么选

base bundle 里配了三个预设,另有一个实验性选项:

| 预设 | sandbox mode + approval | 团队里的用途 |
| --- | --- | --- |
| `read-only` | `read-only` + `ask` | 代码阅读、审查、问答 |
| `workspace-write` | `workspace-write` + `ask` | **默认**,日常开发 |
| `danger-full-access` | `danger-full-access` + `never` | 只在一次性 VM / 容器里用 |
| Auto review(实验性) | Full access 的沙箱值 + `ask`,每次调用先让当前模型审一遍 | 先别进基线;它"can allow unsafe actions" |

几个要点:

- 进程级默认值由 `DSH_PERMISSION_MODE` 决定,不设就是 `workspace-write`;设成 `danger-full-access` 时审批自动变成 `never`。**`never` 是自动拒绝**,不是自动批准:CI 里"不弹窗"靠的是拒掉越界动作,而不是放开它们
- `workspace-write` **只管文件写**:读和网络都不限制;Landlock 和 Seatbelt 后端也不隐藏宿主进程(bwrap 会用私有 PID 命名空间隐藏)
- **`sdk-minimal` profile 固定 `danger-full-access`**,不挂审批服务。它只能在隔离环境里用

### 2.3 沙箱之外的可信代码

这些东西都**不在 agent 沙箱里**,进团队之前要当成"安装软件"来审:

| 东西 | 为什么在沙箱外 | 出处 |
| --- | --- | --- |
| MCP server | 每个 server 命令都是沙箱外的可信可执行代码,所以默认一个都不启用 | `apps/cli/reference/README.md` |
| 插件 / bundle 及其依赖构建脚本 | Host 代码在进程内、工作区沙箱之外运行;pnpm `allowBuilds` 放行的脚本以宿主用户权限执行 | `packages/boot/plugin-manager/README.md` |
| Creator 模式的 `plugin_manager` 工具 | 模型能装插件;每次操作需要审批,**`danger-full-access` 下不需要** | 同上 |

最后一行值得单独记:**Creator 模式 + `danger-full-access` = 模型可以不经确认往 Host 里装代码**。基线里两者不要同时出现。

### 2.4 插件审查清单

- 来源:npm 包钉精确版本,git 来源钉 commit(插件市场索引的 git 版本本身就要求 40 位 commit);市场里的标题、作者都是市场自己声明的,确认框里看清实际来源
- 看它的 `cordis.patch.yml` 动了哪些行,装好后用 `dsh --profile <name> --dump-config` 确认每一行来自哪个文件
- 看 `engines.dsh` 是否覆盖你们钉的版本(**兼容性检查不是安全检查**);要跑依赖构建脚本却说不清原因的,不批

## 三、数据基线

### 3.1 默认出口清单

06 篇有逐项说明,这里只给团队必须做决定的清单:

| 出口 | 默认 | 发往 | 关闭方式 |
| --- | --- | --- | --- |
| 会话日志 `dsh_session_log` | **开** | `llm-deepseek` 路由的请求,**包括经配置网关的请求** | Web 设置 → 通用 → 在使用官方模型 API 时上传 Session Log;或 `session-log-deepseek` 行 `enabled: false` |
| 插件清单 `dsh_plugin_packages` | 开 | 同上 | `plugin-package-inventory-deepseek` 行 `enabled: false` |
| 匿名用户 id / 会话 id 请求头 | 开 | 同上 | 随 `llm-deepseek` 适配器发送;走 Custom model API 时不发 |
| OTel 会话上传 | `FEEDBACK_ONLY`:只在用户主动反馈后上传 | DeepSeek 的 collector,`DSH_TELEMETRY_OTLP_URL` 可改 | `DSH_TELEMETRY_MODE=DISABLED`,或任意非空的 `DSH_TELEMETRY_DISABLED` |
| Desktop 产品分析事件 | 开,**没有界面开关** | 产品遥测 collector | `product-analytics` 设置命名空间的 `enabled` 改为 `false`;普通 Web 不挂这个服务 |
| `web_search` | 开 | DeepSeek 的搜索端点,与模型路由无关 | 见第六节 |

两个容易漏的细节:**`DSH_TELEMETRY_*` 管不到会话日志**,它只管 OTel 那一行;**`DSH_*` 变量不能写进 `.env`**,launcher 拒绝从文件读取决定启动方式的变量,必须 export。另外,OTel 和会话日志的导出内容都可能包含消息文本、工具参数和结果、工作区路径。

### 3.2 把关闭写成补丁

团队要求"使用官方 API 时不上传会话日志"的话,写成一个补丁文件:

```yaml
# baseline.cordis.yml
- id: session-log-deepseek
  config:
    enabled: false
- id: plugin-package-inventory-deepseek
  config:
    enabled: false
```

放在哪一层很关键(11 篇):bundle 层 < profile 的 `cordis.patch.yml` < `$DSH_HOME/cordis.patch.yml` < `--patch`。

- 放进**团队 bundle**:是基线,但个人在 Web 里拨开关会写进 profile 层,把它覆盖掉
- 放进**`$DSH_HOME/cordis.patch.yml`**:对这台机器上所有 profile 生效,Web 表单写入冲突时会被拒绝。**容器镜像和 CI 用这一层**
- 一次性任务用 `--patch ./baseline.cordis.yml`,优先级最高

### 3.3 代理与直连

`docs/user/guide/network-proxy.md` 里和合规相关的几条:

- 只读 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` / `NO_PROXY`,不读系统代理设置;**项目自己的 `.env` 不能设代理**,只能 export 或写在 `$DSH_HOME/.env`。`NO_PROXY` 不支持 CIDR,SOCKS 不支持
- **OTLP 导出器不走代理**,出口被封时直接失败;workflow worker 和 Node PTC 运行时拿不到代理设置
- 代理 URL 里的密码对 dsh 启动的所有命令可见,包括模型写的命令;TLS 拦截代理要在启动前 export `NODE_EXTRA_CA_CERTS`

### 3.4 凭证

| 事实 | 出处 |
| --- | --- |
| Web 保存的 key 存在 `$DSH_HOME/.credentials.yaml`,settings 里只留引用 | `docs/user/guide/providers.md` |
| 查找顺序:存储文件 > 启动环境 > 项目 `.env` > `$DSH_HOME/.env` | `packages/credentials/credentials-local/README.md` |
| 文件以仅属主可读创建;POSIX 上别人可读就拒绝加载,提示 `chmod 600` | 同上 |
| **agent 的工具进程以同一个用户运行,能读这个文件**;沙箱不禁读;系统钥匙串 provider 还没做 | 同上 |
| shipped `headless` profile 关闭凭证存储,只用环境变量和 `.env` | `docs/upgrade-guide/v0.2.1-alpha.2/stored-credentials-precedence/guide.md` |

团队做法:**给 dsh 的 key 单独开、限额、可随时吊销**;CI 里用 secret 注入环境变量,不要往镜像里放 `.credentials.yaml`;同一个名字既存在文件里又 export 时,以文件为准,排查"用错 key"先看这里。

## 四、版本锁定

### 4.1 钉死 CLI

- npm:安装或运行都写精确版本,例如 `npx @deepseek-ai/dsh@0.2.1-rc.2 web`,团队工具仓库里用精确版本 + lockfile
- Node 要满足根 `package.json` 的 `engines`:`^22.19.0 || >=24.0.0`
- Desktop 在签名资源里自带精确的运行时,包和 lockfile 与 npm CLI 分开,但共享 `$DSH_HOME` 里的产品数据;Python SDK 的 runtime wheel 里打包的就是 `dsh` CLI,wheel 版本同样要钉

### 4.2 升级前读升级指南

仓库要求每个对外可感知的 breaking change 都写一份升级指南,路径是 `docs/upgrade-guide/<version>/<slug>/guide.md`,每份都是 Change 和 Migration 两段。目前共 42 份,其中 0.2.1 的四个 alpha 占 34 份(22 + 10 + 1 + 1),也就是说从 `0.2.0-rc.2` 升到 `0.2.1-rc.2` 要读 34 份。几份对团队影响直接的例子:

- `stored-credentials-precedence`:存储的 key 优先于 export 的变量;headless 不再使用保存的 key 和登录
- `plugin-engines-dsh`:有 `engines.dsh` 时只看它,忽略 DSH peer 依赖
- `from-default-profile-replaces-target`:`--from-default-profile` 会整体替换目标 profile
- `web-listener-trust-config`:`--trusted-host` 改由 `webStartup` 服务承载,监听地址不再接受 `0.0.0.0` 这类通配地址,旧的 Web 补丁会让 Connection 起不来

### 4.3 插件兼容性:`engines.dsh` 与豁免

- 安装和 profile 启动都会检查插件的 `engines.dsh`(没有就看 `@deepseek-ai/dsh*` peer 依赖),不满足就拒绝;预发布版本也参与范围匹配
- 确认要冒险时,用精确版本对精确 dsh 版本授予豁免,写进该 profile 的 `compatibility.json`:

```sh
dsh plugin --profile team version-exemptions
dsh plugin --profile team allow-version @acme/dsh-team-baseline@1.0.0 --dsh-version 0.2.1-rc.2 --accept-risk
dsh plugin --profile team revoke-version @acme/dsh-team-baseline@1.0.0 --dsh-version 0.2.1-rc.2
```

**豁免不继承**:插件升级或 dsh 升级后都要重新评估。

### 4.4 profile 也要锁

profile 在 `$DSH_HOME/profiles/<name>`,里面有 `package.json`(依赖和 `dsh.profile.bundles`)、`pnpm-lock.yaml`、`cordis.patch.yml`、`compatibility.json`、`pnpm-workspace.yaml`。

- 这几个文件就是这个 profile 的"锁"。**升级前整个目录备份**,或者纳入团队的配置仓库
- 官方可选 bundle 按当前 dsh 版本精确保存;升级 dsh 后要让它们跟上(Web 插件页对官方插件的 Update)
- `--from-default-profile <template>` 会**删掉原 profile 的依赖和用户补丁**,换成模板的新副本,别拿它当"刷新"用

### 4.5 会话格式

会话格式 v4 已定稿,并已随 `dsh-v0.2.0-rc.2` 发布(`docs/session-format-status.md`)。以写方式打开旧格式会话时,会在原文件旁发布新 generation,原文件不改、不删;读取时选编号最高的 generation,**遇到比自己新的格式会拒绝打开**。所以升级前备份 `$DSH_HOME/sessions`:将来一旦出现新格式,回滚到旧版本后,新版本写过的会话可能打不开。

## 五、共享团队配置

### 5.1 团队 bundle

把团队基线做成一个 bundle(20 篇),发到私有 npm 或 git:

```json
{
  "name": "@acme/dsh-team-baseline",
  "version": "1.0.0",
  "type": "module",
  "files": ["cordis.patch.yml"],
  "engines": { "dsh": "0.2.1-rc.2" },
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
}
```

`engines.dsh` 直接写成验证过的精确版本:升级 dsh 就意味着发一个新版本的团队 bundle,两边一起走变更流程。安装:

```sh
# 从 web 模板创建 team profile;带 dump 参数时只替换、不启动
dsh --profile team --from-default-profile web --dump-default-config
dsh plugin --profile team add @acme/dsh-team-baseline@1.0.0
# 确认团队 bundle 的层出现在配置树里
dsh --profile team --dump-config
```

`cordis.patch.yml` 里放团队共识:关闭的数据出口、模型路由、默认权限预设、经过审查的 MCP server。记住它在 bundle 层,**是基线不是强制**(3.2 节)。

### 5.2 私有插件市场与私有 registry

- 打开实验性的 Custom plugin markets bundle 后,Plugins 页出现 Discover;dsh 不内置任何索引源,每个源只属于当前 profile
- 索引是一个静态 JSON,**放在 https 静态托管上**(网络路径上的人能改 http 索引里的安装来源);仓库里的参考生成器从一份包名 / git URL 列表生成它,只下载和读文件,不安装、不执行:

```sh
pnpm --filter @deepseek-ai/dsh-plugin-market-generator start --input plugins.txt --output site/index.json --title "Team plugins"
```

- Plugin Manager 的 `registry` 和 `fallbackRegistries` 决定 Web / agent 安装问哪个 registry;**配置集之外的私有 registry 只会被单独询问,不会回落到公共源**。`fallbackRegistries` 默认是 npmmirror,有供应链要求的团队要改

### 5.3 共享 skills 与指令文件

- 项目级 skills 放 `.agents/skills`(或 `.dsh/skills`),随仓库提交;个人的放 `~/.dsh/skills` 或 `~/.agents/skills`
- 项目约定写 `AGENTS.md`,dsh 同时读 `CLAUDE.md`,内容相同只渲染一次;个人偏好写 `AGENTS.local.md` / `CLAUDE.local.md` 并加进 `.gitignore`
- 默认渲染预算 65,536 字节,超了先丢范围更大的文件。根目录的 `AGENTS.md` 写短,细节放子目录或 skill

## 六、私有化:模型网关

两条路,差别在 dsh 的线协议扩展跟不跟着走:

| 路线 | 配置 | dsh 线协议扩展 | 适合 |
| --- | --- | --- | --- |
| `llm-deepseek` 指向网关 | `baseURL` 或 `DEEPSEEK_BASE_URL`;网关要兼容 Anthropic Messages | **全部发往网关**:匿名用户 id / 会话 id 头、`dsh_plugin_packages`、`dsh_session_log` | 网关透传 DeepSeek,又想保留原生适配 |
| Custom model API(pi-ai) | Provider ID、base URL、协议(OpenAI Chat Completions / Responses / Anthropic Messages)、凭证、模型 | 不发,`llm-pi-ai` 不实现这些扩展 | 公司网关、自托管的 OpenAI 兼容服务 |

注意事项:

- 第一条路上,网关能看到完整会话日志字段;网关再转发给谁,决定了日志最终到哪。**不想让网关或上游拿到,就把 `session-log-deepseek` 关掉**,不要指望"换了 base URL 就不上传"
- 自托管模型:仓库没有 Ollama 的官方文档,能确定的说法是通过 Custom model API 接 OpenAI 兼容的自托管服务。很多网关拒绝 `developer` 角色或 `max_completion_tokens`,用 `compat.supportsDeveloperRole: false` 和 `compat.maxTokensField: max_tokens` 修正(03 篇)
- **`web_search` 不跟模型路由走**,它用 `DEEPSEEK_API_KEY` 调 DeepSeek 自己的端点(`DEEPSEEK_SEARCH_BASE_URL` 可改)。完全私有化时,要么把它指到允许的端点,要么在 profile 里关掉搜索工具
- Provider ID 一旦建立不能改名,会话、默认模型、凭证引用都用它。团队统一命名后再大面积铺开

## 七、共享部署

`dsh web` 默认只监听 `127.0.0.1:3080`。要让别的机器访问(28 篇):

- `--host` 只能是一个具体地址,`0.0.0.0` 会直接报错;前面放反向代理,用 `--public-url` 声明浏览器看到的地址
- **`--public-url` 只是展示,不授予信任**,浏览器用的域名必须用 `--trusted-host` 列出;TLS 在代理上或监听器上(`--tls-cert` / `--tls-key`)终止,dsh 不申请、不续期证书
- **启动时打印的 URL 带着进程凭证**,只发给该用的人;监听端口本身要用防火墙限制到代理或可信网络
- 它不是多租户服务:拿到 URL 的人共用同一个进程、同一个 profile 和其中的凭证,插件改动对使用这个 profile 的所有会话生效
- 实验性的 GitHub 审查 overlay 需要 TLS 反向代理或隧道,webhook secret 通过 `DSH_GITHUB_WEBHOOK_SECRET` 凭证引用提供

## 八、可观测性

| 想看什么 | 用什么 | 注意 |
| --- | --- | --- |
| 一个会话的完整过程 | 会话日志,`$DSH_HOME/sessions/--<normalized-cwd>--/<id>/` 下的 `session.vN.jsonl.zstd` | 默认 zstd 压缩,要用外部工具直接读就把 `session-persistence-jsonl` 的 `compression` 设为 `'none'`(整行 config 会被替换,`root` 照 `--dump-config` 的原值一起写) |
| 逐步的耗时、token、工具输入输出 | Web 的 Trajectory 标签页 | 17 篇讲事件日志 |
| 导出给别人看 | Web 的 `/export` 或会话头部菜单下载 ZIP | 包含子会话和附件,先脱敏 |
| CI 任务的过程 | headless `--json` 事件流,退出码 0 / 1 | stderr 只留 `dsh:` 诊断 |
| 启动 / 插件安装失败 | `$DSH_HOME/logs/startup-*.log`;profile 下 `.plugin-manager/logs` | 启动报告**原样记录、不脱敏**,可能含配置和凭证值 |

关于 OTel 要把语义弄清楚:会话 OTel 只有 `FEEDBACK_ONLY` 和 `DISABLED` 两种模式,`FULL` 会被拒绝,**它不是持续的可观测性通道**,只有用户主动反馈时才放出那一段会话前缀。`DSH_TELEMETRY_OTLP_URL` 只是把这些反馈触发的记录改发到你的 collector,鉴权头要在配置里用 `exporter.headers` 显式写,不从环境继承。需要持续的指标或审计流,目前要自己写插件订阅 `session/event`(18 篇的开发循环),或者定期离线处理会话日志。

## 踩坑

1. **以为团队 bundle 里关掉的出口一定关着**——bundle 层优先级最低,个人在 Web 里拨开关就覆盖了。机器级要求写进 `$DSH_HOME/cordis.patch.yml` 或 `--patch`
2. **把 `DSH_TELEMETRY_DISABLED` 写进 `.env`**——`DSH_*` 变量不从文件读取,必须 export;而且它只管 OTel,不管会话日志
3. **以为换了网关 base URL 就不再上传会话日志**——`llm-deepseek` 的线协议扩展会照样发给网关。要么关 `session-log-deepseek`,要么改走 Custom model API
4. **CI 里的 headless 用不了 Web 里保存的 key**——shipped headless profile 关闭了凭证存储,用环境变量注入
5. **用 `--from-default-profile` "刷新"团队 profile**——它会删掉原 profile 的依赖和用户补丁。要保留就先备份
6. **升级 dsh 不读升级指南,也不重审豁免**——0.2.1 一个小版本就有 34 份指南;豁免绑定精确的插件版本和 dsh 版本,任何一边升级都要重新授予
7. **把 `DSH_TELEMETRY_OTLP_URL` 当成接入自家可观测平台**——它只改反馈触发的会话上传去向,不会产生持续数据
8. **把 `--public-url` 当成访问控制**——它只是展示地址;信任靠 `--trusted-host`,端口安全靠防火墙,打印的 URL 本身就是凭证
9. **在 Creator 模式下开着 `danger-full-access`**——模型可以不经确认安装插件,而插件代码在沙箱之外运行

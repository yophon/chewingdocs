# 配置、打包与分发

18、19 篇的插件都是靠 `--patch` overlay 挂进来的,只在开发机上、只在当次启动生效。这一篇讲插件怎么走出开发机:先让它接受配置,再打成 bundle,用 `dsh plugin` 装进 profile;然后看 Web 的 Plugin Manager、Creator 模式和实验性的插件市场。最后单独讲一节安全,因为 dsh 插件和 Claude Code 的插件一样,本质上都是在你机器上运行的代码。

和 Claude Code 对照:Claude Code 的插件打包的是 skills、子代理、hooks、MCP 配置这类扩展,通过 marketplace 分发。dsh 的插件是 npm 包形式的 TypeScript 模块,装进 profile 目录,由 pnpm 管理依赖,直接运行在 dsh 进程里。

> 一句话先记住:**配置用 Schemastery 在加载时校验;分发的单位是 bundle(在 `package.json` 里声明了 `dsh.bundle` 的 npm 包),落点是 profile**。插件跑在 dsh 进程内,拥有完整的 API 访问权限,不受 agent 沙箱约束,装插件和运行一段不受限的代码是同一个分量。

## 一、插件配置

### 1.1 导出 `Config` 接口和同名 schema

```ts
import type { Context } from '@deepseek-ai/cordis'
import Schema from '@deepseek-ai/schemastery'

export const name = 'weather'

export interface Config {
  apiKey: string
  timeoutMs: number
  mode: 'fast' | 'accurate'
}

export const Config: Schema<Config> = Schema.object({
  apiKey: Schema.string().required(),
  timeoutMs: Schema.number().default(30000),
  mode: Schema.union(['fast', 'accurate']).default('fast'),
})

export function apply(ctx: Context, config: Config) {
  // 这里拿到的 config 已经校验过、填好默认值
}
```

Cordis 加载插件时用导出的 schema 校验配置、填默认值,**校验失败直接让加载失败**,并给出可操作的错误。不要把一个普通对象导出成 `Config`,它没有实现 Cordis 要求的 Standard Schema 接口。

在 `cordis.yml` 或 patch 里给这一行写配置:

```yaml
- insert:
    - id: weather
      name: dsh-weather-plugin
      config:
        apiKey: !!js process.env.WEATHER_API_KEY
        timeoutMs: 8000
```

### 1.2 几条设计原则

- **两个部署可能想设得不一样的值,都应该是配置字段**。判断标准:不改代码,能不能在 `cordis.yml` 里改掉它
- **密钥不进代码、不读零散的 key 文件**。用 `!!js process.env.X` 从环境变量喂进配置,这是 cookbook 推荐的 Cordis 原生做法
- **约束写进 schema**。能自我校验的约束(范围、枚举、必填)在加载时就失败,比运行到一半才报错好
- **记住 patch 是整体替换**。用户在 profile 里覆盖你的行时,`config` 会被整体替换而不是深合并(11 篇),所以默认值放在 schema 里,别指望用户只写改动的那一个键

非 volatile 字段被修改后,HMR 会卸载旧实例、加载新实例。因为注册都是 effect,替换不会留下旧实例的注册。

## 二、volatile:不重建实例的热改字段

有些设置希望在 UI 上改完立即生效、又不想重建插件实例(比如重试次数)。在 schema 上加 `.volatile()`,接口里用 `Volatile<T>`:

```ts
import type { Context, Volatile } from '@deepseek-ai/cordis'
import z from '@deepseek-ai/schemastery'

export interface Config {
  endpoint: Volatile<string | undefined>
  retries: Volatile<number>
}

export const Config = z.object({
  endpoint: z.string().volatile(),
  retries: z.number().step(1).min(0).default(3).volatile(),
})

export function apply(ctx: Context, config: Config): void {
  ctx.on('loader/volatile-update', () => {
    ctx.logger.info('Retry limit: %d', config.retries.get())
  })
}
```

- **用的时候再 `.get()`**。一个需要一致快照的操作在开始时取一次值,别在中途反复读
- **跨字段校验用 `.check()`**,在 Host 上持久化之前执行
- **`role('secret')`** 让值不出现在表单响应里。由凭证系统管理的值用凭证引用
- **只有 volatile 字段进入设置表单**。`dsh-settings` 只暴露活跃且地址唯一的条目上的 volatile 字段,普通字段仍然只能改配置文件。保存会写进当前 profile 的 patch,经 Config Editor 和 volatile HMR 应用,插件实例不变

关于 UI 要说清楚:Web 侧栏 **Plugins** 页面上的配置页,是插件自己的浏览器端注册的(`plugins.row.config` 或 `plugins.bundle.config` slot)。设置服务的表单描述里有 `autoGenerate` 标志,但 README 明说目前没有任何内置客户端据此自动生成页面。也就是说,第三方插件声明了 volatile 字段,并不会自动在 Plugins 页上出现一张表单。要出现,得给包加 `dsh.client` 声明和 `./client` 导出,按客户端模块系统的 lazy-CJS 工厂格式构建。仓库的 `clientBundle` 构建预设在 `packages/client/tsdown.client.ts`,没有作为包发布,仓库外的包要自己复刻这一步。

## 三、打包成 bundle

### 3.1 两个概念、两种清单

| | bundle | profile |
| --- | --- | --- |
| 是什么 | 一个携带配置层的 npm 包 | `$DSH_HOME/profiles/<name>` 下的一个目录 |
| 清单字段 | `package.json` 的 `dsh.bundle` | `package.json` 的 `dsh.profile` |
| 回答的问题 | 这个包贡献什么 | 这个组合由哪些 bundle、按什么顺序组成 |
| 谁写 | 插件作者 | `dsh plugin` 和 Plugin Manager 维护,不要手写 |

没有一个东西同时是两者。

### 3.2 bundle 的最小结构

```text
hello-plugin/
├── package.json       # 声明 dsh.bundle
├── cordis.patch.yml   # profile 列出这个 bundle 时应用的那一层
└── index.js           # patch 行引用的插件模块
```

```json
{
  "name": "dsh-hello-plugin",
  "version": "0.1.0",
  "type": "module",
  "main": "index.js",
  "files": ["index.js", "cordis.patch.yml"],
  "engines": { "dsh": ">=0.2.0 <0.3.0" },
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
}
```

```yaml
- insert:
    - id: hello
      name: dsh-hello-plugin
```

要点:

- **patch 行用包名引用模块**,让 Node 的模块解析找到装好的代码,而不是写相对源码路径
- **`patch` 也可以是有序列表**,比如 `["./base.patch.yml", "./web.patch.yml"]`,按顺序作为一层应用,每个文件里的相对插件路径相对该文件解析
- **`engines.dsh` 声明支持的 dsh 版本范围**。安装和 profile 启动都会拒绝范围不满足的 bundle;没写 `engines.dsh` 时,改为检查 `@deepseek-ai/dsh*` peer 依赖的范围。按 app-boot README,预发布版本(如 `0.2.1-rc.2`)也参与范围匹配
- **要和宿主共享实例的 dsh 包,同时写进 `peerDependencies` 和 `devDependencies`**。peer 让运行时用安装方的那份(只有一份 cordis 实例),dev 那份给类型检查和独立测试用。独立版本的第三方依赖和无状态工具包放 `dependencies`
- **没有 `dsh.bundle` 的包也能装**,但只是普通依赖,`dsh plugin` 会给出警告、不激活任何层。给其他插件包引用的库就用这种形式

### 3.3 bundle 在叠加顺序里的位置

有效配置从空树开始,依次应用:profile `dsh.profile.bundles` 列表里的各个 bundle(`@deepseek-ai/dsh-base` 在最前,其余按添加顺序)→ profile 自己的 `cordis.patch.yml` → `$DSH_HOME/cordis.patch.yml` → 每个 `--patch`(11 篇)。对 bundle 作者有两个推论:

- 你的 patch 可以按 id 覆盖更早层的行(`dsh-web-app` 就是这样覆盖 `dsh-base` 的),但要写全这一行需要的所有键
- 用户可以在 profile patch 里覆盖你的行,不用动你的包。所以把用户大概率会保留的默认值放在 schema 里

## 四、用 `dsh plugin` 安装

### 4.1 它就是 profile 目录里的 pnpm

`dsh plugin --profile <name> <pnpm-args...>` 在 profile 不存在时先初始化它(有模板用模板,否则只含 `@deepseek-ai/dsh-base`),然后把剩余参数原样转发给 profile 目录下的 `pnpm`,所以 pnpm 的所有动词都能用,pnpm 必须在 PATH 上。每次成功执行后,`dsh.profile.bundles` 会按安装状态重新对齐:声明了 `dsh.bundle` 的依赖加入层栈,删掉的依赖移出层栈。

| 场景 | 命令 |
| --- | --- |
| 本地目录(link) | `dsh plugin --profile demo add ./hello-plugin` |
| 当前目录的插件仓库 | `dsh plugin --profile demo add .`(相对路径锚定到你执行命令的目录) |
| npm 包 | `dsh plugin --profile demo add dsh-hello-plugin` |
| pnpm pack 出的 tarball | `dsh plugin --profile demo add ./hello-plugin-0.1.0.tgz` |
| GitHub,钉住提交 | `dsh plugin --profile demo add github:you/hello-plugin#<sha>` |
| 卸载 | `dsh plugin --profile demo remove dsh-hello-plugin` |
| 查依赖来源 | `dsh plugin --profile demo why <pkg>` |

`--profile <name>` 必须写在转发参数之前。装完先验证,再启动:

```bash
dsh --profile demo --dump-config   # 能看到 "# == dsh-hello-plugin" 这一层
dsh --profile demo
```

### 4.2 改了 bundle 成员要重启

CLI 参考写得很明确:pnpm 操作成功后,磁盘上的 profile 清单和 bundle 列表已经变了,但**正在运行的 profile 保留启动时的 bundle 集合**,增删或更新 bundle 之后要重启那个 profile。普通的 profile / home patch 编辑仍然走热重载。

(hmr README 提到它会监听 profile 清单、在 bundle 列表变化时重新组合,Plugin Manager 在有 HMR 时也能直接应用。两份文档的表述有出入,用 CLI 改完 bundle 重启一次最稳妥。)

### 4.3 从 Git 安装:构建脚本这一关

Git 安装拿到的是**源码,不是构建产物**,没有人替你跑 `build`,TypeScript 包会因为缺 `lib/` 而加载失败。两边各要做一件事:

- **作者**提供 `prepare` 脚本(pnpm 在 git 安装后运行它),自包含地从源码构建出入口文件,不能依赖兄弟 monorepo 之类的开发期环境
- **用户**放行构建。pnpm 10 及以上默认拒绝运行 git 依赖的 `prepare`,第一次 `add` 会失败,dsh 会提示去改 profile 的 `pnpm-workspace.yaml`。把 pnpm 打印的包名原样抄过去,再重新 `add`:

```yaml
allowBuilds:
  dsh-hello-plugin: true
```

这个放行等于**允许这个包在安装时以你的用户权限执行代码**,而且是在 agent 的任何沙箱之外。只放行信任的源码,并且钉住提交(`#<sha>`),免得之后的推送悄悄改变要执行的代码。不想让用户放行,就分发构建好的产物:发布到 npm(`pnpm publish` 时构建好 `lib/`),或者给 `pnpm pack` 出来的 tarball。本地目录和 tarball 都不需要放行。

### 4.4 版本不兼容与豁免

安装命令里点名的包会在 pnpm 运行**之前**做兼容性检查:本地路径读它自己的 `package.json`,registry 规格查它选中版本的 `engines` 和 `peerDependencies`。不满足就拒绝,不下载、不跑构建脚本。git 和 tarball 要先拉下来才知道,所以在安装后判断,不满足就恢复清单和锁文件。

确实要用一个声明不兼容的版本,可以加豁免,写在 profile 的 `compatibility.json` 里,按"精确包版本 × 精确 dsh 版本"记录:

```bash
dsh plugin --profile demo version-exemptions
dsh plugin --profile demo allow-version dsh-hello-plugin@0.1.0 --dsh-version 0.2.1-rc.2 --accept-risk
dsh plugin --profile demo revoke-version dsh-hello-plugin@0.1.0 --dsh-version 0.2.1-rc.2
```

授权前会打印风险警告:不兼容的插件可能导致崩溃或数据丢失。豁免不会被插件升级或 dsh 升级继承,也不授权依赖脚本。

## 五、Plugin Manager 与 Creator 模式

### 5.1 Web 的 Plugins 页

基于 base 的 profile 自带 Plugin Manager(`@deepseek-ai/dsh-plugin-manager`)。Web 侧栏的 **Plugins** 页面可以:开关 bundle 和其中可单独寻址的行、按规格(包名、Git 地址、tarball、绝对本地路径)安装、查看 pnpm 输出、取消安装、卸载。有 HMR 时配置改动立即生效,没有 HMR 时要重启。改动影响使用这个 profile 的所有会话。

开关一行插件,只会在 profile 的 `cordis.patch.yml` 里写一条 `disabled` 覆盖,而且只记录和 bundle 默认值不同的部分。开关一个 bundle,改的是 `dsh.profile.bundles` 列表;重新启用会把它追加到末尾,可能改变配置优先级。pnpm 因为构建脚本被拦时,页面会列出待放行的包,提供 **Allow these scripts and retry**。诊断日志在 profile 的 `.plugin-manager/logs` 下。

### 5.2 Creator 模式:让 agent 管插件

Creator 模式就是 `cordis` 这个 agent 预设(04 篇)。它挂了 `tool-cordis`,并启用了 `standard`、`ptc` 预设里写着 `disabled: true` 的插件管理和市场工具行:

| 工具 | 作用 |
| --- | --- |
| `plugin_manager` | 列出条目和 bundle、安装 / 卸载 / 启用 bundle、管理版本豁免 |
| `cordis_inspect_list` / `cordis_inspect_query` | 只读查询运行时 API:服务方法、事件、类型,当前 Loader 条目及其配置状态,单个条目配置的 JSON Schema |
| `plugin_market` | 只读浏览插件市场,只有打开实验性市场 bundle 时才有(见第六节) |

`plugin_manager` 的每个动作都要求 `danger-full-access` 沙箱模式,否则必须为这一次调用获得审批。审批策略是 `never`、被拒绝、被取消或没有审批渠道,都不会执行;批准一次也不会改变会话的权限模式。其他预设默认关闭这个工具。

用法上最实用的是**从一句话生成"只含配置"的 bundle**。官方文档的例子是接一个 Streamable HTTP 的 MCP server:在 Creator 模式里说"把 `<endpoint>` 上的 MCP server 以 `demo` 为名配置到这个 profile,马上可用,然后调它的 ping 工具"。agent 会写一个 patch 只插入 `@deepseek-ai/dsh-mcp-client` 的 bundle,再用 `plugin_manager install_bundle` 装上。验证两件事:管理结果是 `application: applied`,以及 `mcp__demo__ping` 调用成功。结果是 `restart-required` 说明已保存但还没激活。

`cordis_inspect_query` 很适合写插件之前查准确的服务签名和事件参数,比翻源码快。它不能调用业务方法,也不能改配置。

### 5.3 cordis-host-runner 不是 Creator 的工作方式

`@deepseek-ai/dsh-cordis-host-runner` 提供运行时检查注册表(`ctx.cordisInspect`,上面两个 inspect 工具靠它),另外还有一套**进程内、会话级**的动态插件定义(`define` / `run` / `stop` / `undefine`),Host 侧代码跑在 `node:vm` 里。要注意三点:没有任何模型工具能创建动态定义;重启后定义全部消失;vm 只隔离全局变量,**不是安全边界**,声明的服务照样能碰到真实运行时。Creator 的持久化工作流用的是安装 bundle,不是这套机制。

## 六、插件市场(实验性)

插件市场是一个 JSON 索引文件,列出可安装的 dsh bundle 及其标题、图标、作者和版本。它在可选 bundle `@deepseek-ai/dsh-experimental-plugin-market-bundle` 里,界面名叫 **Custom plugin markets**,默认关闭。这是 developer preview 里的实验功能,用之前对照你的版本重新核对。

打开方式:**Plugins** → **Experimental plugins** 旁的 **More** → 打开 **Custom plugin markets**。之后 **Installed** 旁边多出 **Discover** 标签页,Creator 模式多出只读的 `plugin_market` 工具。

- **dsh 不内置任何索引源**,要自己在 Discover 里 **Add index source** 填 URL。只接受 `http:` / `https:`,不能带用户名密码或 `#` 片段。`http:` 索引在网络路径上可被篡改,包括里面的安装规格,跨不受控网络时用 `https:`
- **安装前有确认**:显示这个版本的来源(npm 包和 registry,或 Git 仓库、提交、目录),确认后走正常的安装流程,兼容性检查一个不少
- **市场内容是第三方声明**:标题、描述、图标、作者、来源都由市场自己写,dsh 只校验格式

最小索引:

```json
{
  "format": 1,
  "title": { "en": "Team plugins", "zh": "团队插件" },
  "plugins": [
    {
      "name": "dsh-plugin-foo",
      "title": "Foo",
      "icon": "icons/foo.svg",
      "versions": [
        { "version": "1.1.0", "publishTimestamp": 1790476800, "source": { "type": "npm" }, "engines": { "dsh": ">=0.2.0-rc.2" } }
      ]
    }
  ]
}
```

`source` 也可以是 `{ "type": "git", "url": <https>, "commit": <40 位 sha>, "path"?: <目录> }`。相对图标 URL 相对索引 URL 解析,所以把 `index.json` 和 `icons/` 放在一起发布到任意静态托管就行。任何一条规则不满足,整个索引被拒绝,错误带 JSON 路径。

不想手写可以用仓库里的参考生成器 `apps/plugin-market-generator`,输入一个每行一个 npm 包名或 https Git 地址的列表:

```bash
pnpm --filter @deepseek-ai/dsh-plugin-market-generator start \
  --input plugins.txt --output site/index.json --title "Team plugins"
```

它只列出声明了 `dsh.bundle` 的版本,npm 包取所有未废弃的版本,Git 仓库取 `vX.Y.Z` / `X.Y.Z` / `<name>@X.Y.Z` 标签和默认分支。**生成器只下载和读取文件,从不安装包、不运行包里的代码**:tarball 在内存里读并校验完整性哈希,Git 对象拉进临时裸仓库按 blob 读,禁用 hooks 和子模块。缓存放在列表旁边的 `.plugin-market-cache`。

## 七、安全:插件就是进程内代码

| 风险点 | 事实 | 做法 |
| --- | --- | --- |
| 运行时 | 插件在 dsh 进程内运行,拥有完整的 Cordis API,不在 agent 的工作区沙箱里 | 和对待 `bash` 访问权一样对待装插件 |
| 安装时 | git 依赖的 `prepare`、被放行的构建脚本以你的用户权限执行 | 只放行读过源码的包,钉提交 |
| 来源 | 插件市场的标题、作者、来源都是第三方声明 | 只添加信任的索引源,确认框里核对来源 |
| Creator 模式 | agent 能写 bundle 并安装,改动跨会话持久 | 保持 `plugin_manager` 每次审批;不要在 `danger-full-access` 下随手开 Creator |
| 动态定义 | cordis-host-runner 的 vm 不是安全边界 | 当成 bash 级权限 |

MCP 也是一样的道理:CLI 默认带 `@deepseek-ai/dsh-mcp-client` 依赖,但不启用任何 MCP server,因为每个 server 命令都是沙箱之外的可执行代码(22 篇)。

## 踩坑

1. **把普通对象导出成 `Config`**——没有实现 Standard Schema,Cordis 不认。用 `Schema.object({...})`
2. **以为用户覆盖你的行时只改了一个键**——patch 整体替换 `config`,默认值要放在 schema 里
3. **声明了 `.volatile()` 就等 Plugins 页出表单**——目前没有内置客户端自动生成表单,要自己写浏览器端注册配置页
4. **把 `@deepseek-ai/cordis` 等共享包放进 `dependencies`**——装出第二份实例,服务和事件对不上。放 `peerDependencies` + `devDependencies`
5. **TypeScript 插件从 GitHub 装完加载失败**——git 安装不跑 `build`。作者加 `prepare`,用户在 `pnpm-workspace.yaml` 的 `allowBuilds` 里放行;或者改发 npm / tarball
6. **`allowBuilds` 放行了没钉提交的 GitHub 包**——对方之后的推送会在你机器上执行。用 `#<sha>`
7. **`dsh plugin add` 之后马上在运行中的 Web 里找新插件**——bundle 成员变化要重启 profile
8. **`dsh plugin add .` 装进了错误的目录**——`--profile` 必须在转发参数之前;相对路径相对你执行命令的目录
9. **以为打开插件市场就有现成的插件可装**——dsh 不内置索引源,要自己添加
10. **用 `allow-version` 绕过兼容性检查后忘了**——豁免只对精确版本对生效,但崩溃和数据丢失的风险是真实的,不用时 `revoke-version`

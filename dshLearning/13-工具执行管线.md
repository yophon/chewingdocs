# 工具执行管线

12 篇的 turn 流程图里有一行被一笔带过:`tool/call* → tools/pre-execute → tools/execute → tools/post-execute → tool/result*`。这一篇把它展开。05 篇从用户角度讲了沙箱模式和审批策略怎么选;这里从内部看:一个工具调用从模型发出到结果入日志,中间经过几道关、每道关由谁把守、哪些地方可以插手。

结构上可以对照 Claude Code 的 hooks(claudeLearning 11 篇):`PreToolUse` 和 `PostToolUse` 在 dsh 里有对应物。区别在于,dsh 里这些不是外部脚本,而是进程内的类型化 waterfall,而且整条管线由工具注册表 `dsh-tools`(`ctx.tools`)统一执行,工具作者自己不写权限逻辑。

> 一句话先记住:**一个调用先落盘为 `tool/call`,再依次经过 pre-execute(允许/拒绝/取消/询问)→ 审批 → 单调 guard → execute 包装 → 工具本体 → post-execute → 最终冻结的 `tools/result`,最后落盘为 `tool/result`**。策略可以拒绝调用、改写结果,但**永远改不了参数**;所有失败都会变成结构化的错误结果,不会终止 turn。

---

## 一、全景图

按 `docs/tool-execution-pipeline.md` 和 `packages/core/tools/src/index.ts` 整理:

```text
assistant/message 里的 tool-call 块
  │
  ▼
[S] tool/call                       先写日志,再执行;UI 据此画"进行中"卡片
  ▼
tools/pre-execute   waterfall ── allow / deny / cancel / ask
  │ ask ─→ ctx.approval.request() ── allowed-once ─→ 继续
  │                               └─ rejected / cancelled / unavailable ─→ 拒绝
  ▼
ToolGuard(ctx.tools.guard 注册,只能拒绝或弃权)
  ▼
tools/execute       waterfall(包在派发外面:超时、重试、指标)
  ▼
工具本体 execute()   ├─ 改文件:fs/write-intent / fs/edit-intent(只管 tool-fs)
                    └─ 起进程:ctx.shell → ctx.sandbox.confine(argv)
  ▼
projectContent      工具自带:装入执行期准备好的内容(拒绝结果也会经过这里)
  ▼
tools/post-execute  waterfall ── accept / block / 换 content / 换 value / 加上下文
  ▼
finalizeContent     工具自带:最后一道只改内容的变换(管线异常也会经过)
  ▼
tools/result        只读通知:冻结的、可无损 JSON 化的最终结果
  ▼
[S] tool/result     模型看到的唯一结果;整批结束后 additionalContexts 作为 user/message 追加
```

任何一步抛异常,都由注册表外层统一归一成 `isError` 结果。这种结果会跳过 post-execute,但仍然经过 `finalizeContent` 和 `tools/result`。

`ctx.tools` 的公开方法只有八个:`register`、`restrict`、`guard`、`presentAs`、`get`、`schemas`、`executionMode`、`execute`。上面这条管线就是 `execute()` 的内部过程。

## 二、调用先落盘,参数永不改写

### 2.1 `tool/call` 在执行前写入

调用开始时,循环先把 `tool/call` 追加进会话日志,然后才进入策略。两个后果:

- 进程在工具执行中途崩溃,日志里留着"发出过但没有结果"的调用。12 篇讲过,下次收尾时它会被补上 `TOOL_OUTCOME_UNKNOWN`,而不是被悄悄重跑
- UI 可以立刻用 `presentCall(args)` 画出卡片,不用等结果

### 2.2 参数在进入策略前就冻结了

`execute()` 先把模型给的参数做一次无损 JSON 物化,深度冻结,再分配一个不透明的 `token` 作为调用身份。之后所有 waterfall 看到的都是同一个只读对象。

`PreToolDecision` 里没有"改参数"这个选项。类型注释和 tools README 都说明了原因:参数已经写进日志、展示给用户,如果策略能改,历史、审计、UI 和实际执行就会对不上。改写参数的设计目前只是一份 proposed 状态的维护者笔记。

这一点和 Claude Code 不同:Claude Code 的 `PreToolUse` 可以返回 `updatedInput` 改写参数,dsh 刻意不提供。

## 三、pre-execute:允许、拒绝、取消、询问

### 3.1 决策类型

```ts
type PreToolDecision =
  | { kind: 'allow' }
  | { kind: 'deny'; reason: string; info?: ToolErrorInfo }
  | { kind: 'cancel' }
  | { kind: 'ask'; reason?: string; displayReason?: { readonly en: string; readonly [locale: string]: string } }
```

| 决策 | 结果 |
| --- | --- |
| `allow` | 继续往下走。listener 调 `next()` 等于默认允许 |
| `deny` | 跳过工具本体;`reason` 是给模型看的文字,`info` 是结构化的错误身份(可带只给用户看的 `reason`) |
| `cancel` | 产生标准的取消结果,而不是"被策略拒绝" |
| `ask` | 交给 `ctx.approval`;只有 `allowed-once` 才继续,其余一律拒绝 |

waterfall 按 listener 顺序执行,每个 listener 要么返回决定截断后面的链,要么调 `next()` 委托下去。异步的检查要观察 `exec.signal`;listener 跑完后,注册表还会再检查一次取消。

### 3.2 谁在听

按 `docs/event-producer-consumer.md`,`tools/pre-execute` 的监听者有 `tool-jobs`、`workspace-changes`,以及实验性的 `hooks-claude-code`、`hooks-codex`(把 Claude Code / Codex 的 hook 配置映射过来,23 篇)和 `auto-review`。

`auto-review` 值得单独说一句:它是实验性插件,在每个原生或 PTC 内层调用前让当前模型评估这次操作,允许就以 Full access 执行,拒绝就转为询问用户。思路接近 Claude Code auto mode 的分类器,但出厂默认关闭,README 自己也写明它可能放过不安全的操作。

注意 plan mode 不在这张表里。12 篇提过,plan mode 只是提示词层面的软约束,真正的边界在沙箱和审批。

## 四、审批:`ctx.approval` 一次一问,失败即拒绝

`ask` 决定交给审批接缝 `dsh-user-approval`(行 id `approval`)。它的结果是一个封闭集合:

```ts
type ApprovalOutcome = 'allowed-once' | 'rejected' | 'cancelled' | 'unavailable'
```

注册表把这四种结果映射成不同的拒绝原因,让模型分得清"用户说不"和"没人能回答":

| 结果 | 含义 | 模型看到的拒绝原因(源码原文) |
| --- | --- | --- |
| `allowed-once` | 只放行这一次调用 | —(继续执行) |
| `rejected` | 用户明确拒绝,或会话策略是 `never` | `the user rejected tool "<name>"` |
| `cancelled` | 请求被撤回(比如 turn 被取消) | `approval for tool "<name>" was cancelled` |
| `unavailable` | 没有回答者、回答者抛错或返回了非法值 | `... requires approval, but no approval channel is available` |

还有两种情况不会走到审批服务,直接拒绝:部署里根本没挂 `ctx.approval`;调用没有关联的 agent(没有会话可审计,也没有 UI 可路由)。

几条关键规则(`docs/subsystems/approval.md`):

- **会话策略只有 `ask` 和 `never` 两种**。`never` 在派发给任何回答者之前就确定地返回 `rejected`,是**自动拒绝**,不是自动批准。后注册的回答者即使用 `prepend` 插到最前面,也绕不过它
- **每一问都落两条审计事件**:`approval/asked` 和 `approval/decided`,用一个新的 `ApprovalRequestId` 配对,只进日志,不进模型历史。策略切换记成 `approval/policy`,重放时以最后一条为准;模型通过运行时上下文快照得知当前策略,而不是读这条事件
- **审批必须发生在打开的 turn 里**。空闲时调 `request()` 会在写任何东西之前直接报错,因为审计对必须落在日志的提交/重放边界之内
- **请求里不带工具参数**。回答者通过 `callId` 把提示挂到 UI 已经展示过的那个调用上,避免出现两份可能不一致的参数

回答者挂在 `approval/request` waterfall 上:Web UI 提供人工回答,ACP 桥为它自己的 agent 提供机器决策。headless 运行没有 UI,`ask` 默认会落到 `unavailable` 并拒绝。各 profile 默认用哪种策略、怎么切换,见 05 篇。

## 五、ToolGuard:不怕顺序的最后一道拒绝

waterfall 的问题是**顺序敏感**:一个后注册、`prepend` 到前面的 listener 可以直接返回 `allow`,截断后面所有检查。对"无论如何都不能执行"的规则,dsh 提供另一种机制:

```ts
type ToolGuard = (execution: Readonly<ToolExecution>) => string | undefined
```

- 通过 `ctx.tools.guard(guard)` 注册,在**整个 pre-execute waterfall 和审批之后**、工具本体之前同步运行
- 返回字符串就拒绝,返回 `undefined` 表示弃权。**没有"允许"这个返回值**,所以没有任何 listener 能把 guard 的拒绝翻回许可
- 按作用域生效,可以只对某个 agent 注册

仓库里的实际例子在子代理的结构化输出(`packages/subagent/subagent/src/structured.ts`):子代理一旦记录了结构化结果,guard 就拒绝后续所有调用,理由是 "structured output already recorded"。

| 机制 | 能做什么 | 顺序影响 | 适合 |
| --- | --- | --- | --- |
| `tools/pre-execute` | 允许、拒绝、取消、询问 | 有,按 waterfall 顺序 | hooks、审批类策略、可组合的检查 |
| `ctx.tools.guard()` | 只能拒绝 | 没有,单调组合 | 归属方的硬性规则 |

## 六、执行:包装、本体、文件与进程

### 6.1 `tools/execute`:包在派发外面

这一层 waterfall 包住派发本身,适合做超时、重试、指标。包装者只能替换 `exec.signal`,调用身份不可变;注册表会在调用本体前把原始的调用方 signal 重新融合进去,所以包装者没法让调用脱离取消。

base 里的 `timeout-policy` 行(`dsh-tool-call-timeout-policy`)就挂在这里。它没有自己的配置,超时值来自各工具定义上的 `timeoutMs`,比如 `web_fetch` / `web_search` 默认 30 秒。到点后它中止派生的 signal,等工具配合取消、`next()` 结算后,给模型一条 `Error: tool call timed out after <ms>ms`(错误码 `TOOL_TIMEOUT`)。它**不能硬杀**不理会 signal 的工具。`bash`、`read`、`write`、`edit` 没有声明 `timeoutMs`,不受它管。bash 自己的命令超时是执行器层的另一回事(base 里 `bash-sandbox` 行配的是 `timeoutMs: 60000`)。

### 6.2 文件修改:`fs/write-intent` / `fs/edit-intent`

`tool-fs` 的 `write` 和 `edit` 不直接写盘。它们先派发两个单槽决策 waterfall,由 `fs-observation-policy` 根据"这个会话看到过这个文件的哪个版本"做决定(`docs/subsystems/filesystem.md`):

| 观察状态 | `write` | `edit` |
| --- | --- | --- |
| 从未见过 | `createIfAbsent`:只能新建,文件已存在就报 `FS_NOT_OBSERVED` | `FS_NOT_OBSERVED` |
| 确认不存在 | `createIfAbsent` | `FS_NOT_FOUND` |
| 见过某版本 | `replaceIfVersion`:版本变了就报 `FS_STALE_VERSION` | 带版本守卫编辑 |

这就是 dsh 的"先读后改"策略:任何一次窗口化的 `read` 都会记下当前版本,文件没变就能授权后续的写和改。沙箱化的文件 provider `fs-sandbox` 再按沙箱模式把关,越界写入报 `FS_SANDBOX_DENIED`,和操作系统拒绝的 `FS_PERMISSION_DENIED` 区分开。

注意范围:**这两个事件只管 `tool-fs` 的修改**。模型用 bash 跑 `sed -i` 改文件,不经过它们,只受操作系统沙箱约束。这和 Claude Code 里只靠 `Edit|Write` matcher 看不到 shell 改动是同一类问题。

### 6.3 起进程:把 argv 原样交给沙箱

bash 这类工具走 12 篇讲的 shell 接缝:`tool-bash` → `ctx.shell`(base 在非 Windows 上是 `bash-sandbox`)→ `ctx.sandbox`。交接方式是(`docs/subsystems/sandbox.md`):

1. 消费方用 `ctx.sandboxPolicy.resolve()` 得到这次调用的完整策略:模式加上从会话 cwd 推出的 `workspaceRoot`
2. 模式是 `danger-full-access` 就直接 spawn 原始 argv,不调用沙箱
3. 否则把**准备 spawn 的那个 argv** 交给 `ctx.sandbox.confine(argv, policy, signal)`,拿回 `ConfinedArgv`:替换后的 argv、`enforcement`(`full` 或 `partial`)、本后端的拒绝特征串 `denialSignatures`、运行器失败规则 `runnerFailureRules`
4. 没有可用后端时报 `SANDBOX_UNAVAILABLE` 并拒绝执行。对受限策略来说,**静默地不加沙箱运行是不合法的**

`enforcement` 是一个如实上报的事实:`partial` 表示后端只能管住一部分文件效果(比如旧版 Landlock ABI、Windows ACL 后端的部分边界)。沙箱模式只管文件效果,不管网络和读,各平台后端的差异和提权重试(`sandbox_permissions` + `justification`,审批通过后只对这一次调用生效)见 05 篇。

## 七、post-execute:改写结果、追加上下文

### 7.1 决策类型

```ts
type PostToolDecision =
  | { kind: 'accept'; content?: ContentBlock[]; value?: never; additionalContexts?: UserMessage[] }
  | { kind: 'accept'; value: JsonValue; content?: never; additionalContexts?: UserMessage[] }
  | { kind: 'block'; feedback: ContentBlock[]; additionalContexts?: UserMessage[] }
```

| 写法 | 效果 |
| --- | --- |
| `accept`(什么都不带) | 原样接受,等于调 `next()` |
| `accept` + `content` | 只换给模型看的内容,保留规范值和元数据 |
| `accept` + `value` | 换规范值;会按输出 schema 重新校验,并重新渲染内容和元数据 |
| `block` + `feedback` | 去掉值,变成 `isError` 结果,内容是纠正性反馈 |
| 任一种 + `additionalContexts` | 附加上下文,等整批工具结果落盘后作为 `user/message` 追加 |

content 和 value 只能二选一。tools README 提醒:**换 content 是展示策略,不是保密策略**。在 PTC 模式(14 篇)下,程序拿到的是规范值,只改 content 挡不住它;要真正隐藏,必须 block 或换掉 value。

仓库里的监听者有 `spill-policy`、`repeat-tool-reminder`、`tool-fs-search`,以及实验性的两个 hooks 桥。

### 7.2 两个工具自带的回调

- **`projectContent`**:在 post-execute 之前装入执行期准备好的内容。MCP 用它把真实的图片块装进结果,之后的策略照样可以替换或拦截
- **`finalizeContent`**:最后一道只改内容的同步变换。注册表在调用开始时就把它快照下来,每个归一后的结果恰好调用一次,管线异常绕过 post-execute 的结果也不例外

### 7.3 `tools/result`:只读的最终结果

注册表把结果无损快照、深度冻结后发出 `tools/result`。监听者不能改它,监听者抛的错也会被吞掉。做审计、指标、捕获最终结果用它;要改结果或追加上下文,才用 post-execute。

## 八、失败都变成结构化错误

工具失败不会终止 turn。模型看到的统一是 `Error: <message>`,结构化信息留在日志里:

| 错误码 | 什么时候出现 |
| --- | --- |
| `UNKNOWN_TOOL` | 调用了未注册或被 `restrict` 过滤掉的工具;PTC 模式下直接调用非 `run_code` 的工具 |
| `ABORTED_BEFORE_DISPATCH` | 工具本体被调用之前就取消了 |
| `ABORTED` | 本体已调用后取消,只替换原本会成功的结果 |
| `TOOL_TIMEOUT` | `timeout-policy` 判定超时 |
| `INVALID_TOOL_OUTPUT` | 工具返回值或策略换上的值不符合声明的输出 schema |

拒绝、包装器失败、工具失败、post 策略失败这些更具体的错误,不会被取消覆盖。被 `restrict` 过滤掉的全局工具既不出现在提示词里,也拒绝执行,表现和根本不存在的工具一样。

## 九、大输出:spill 与压缩时的裁剪

### 9.1 spill-policy:超预算就落盘

base 里这两行配合工作:

```yaml
- id: spill-local
  name: '@deepseek-ai/dsh-spill-local'

- id: spill-policy
  name: '@deepseek-ai/dsh-spill-policy'
  config:
    maxInlineTokens: 12500
```

`spill-policy` 是 spill 接缝(`ctx.spillStore`)的消费方,以 prepended 的 `tools/post-execute` listener 身份工作:它先调 `next()` 让其他策略跑完,再对最终被接受的内容做预算检查。超过 `maxInlineTokens`(按估算 token,文字和图片共享预算)时:

1. 调 `ctx.spillStore.saveText()` 把完整的格式化结果原样存下
2. 结果换成保持原顺序的头部和尾部预览,外加一条提示

```text
<retained head/tail preview>

(Omitted N bytes. Full formatted result stored at: /…/session-…/…-web_fetch.txt. Use read with offset/limit, or grep this path to search within it.)
```

几个细节:

- **本地后端**把文件写到 `<root>/session-<hash>/<random>-<safeName>`,根目录权限 0700、文件 0600,以独占方式创建,防止被预埋的符号链接重定向
- **定位符是不透明的**。本地后端恰好是路径,换成远程后端可能是 URI 或 key,所以提示里附带 `retrievalHint` 告诉模型怎么取回
- **尽力而为**:没挂后端、存储失败、拿不到图片定价时,记一条警告,保留原始内容,不会把成功的调用变成错误
- **`read` 的结果、block 掉的结果、换过 value 的结果不处理**。跳过 `read` 是为了避免"读 spill 文件又被 spill"的死循环
- 省略 `maxInlineTokens` 等于关闭这个策略
- bash 自己也会把超长输出截成尾部并另存全文,那是工具内部的行为,和这个策略无关

### 9.2 tool-result-pruner:压缩时再裁一次

spill 管的是"结果刚产生时"。会话变长后,历史里累积的大结果由 `tool-result-pruner` 处理(base 配置 `thresholdChars: 8192`、`headChars: 4096`、`tailChars: 1024`)。它只在压缩被触发时运行,而且排在摘要之前:把超长文本换成头部 + "middle pruned" 标记 + 尾部,不调用模型。完整原文仍在会话日志里。压缩的触发和策略见 16 篇。

## 十、和 Claude Code hooks 对照

| 维度 | Claude Code | dsh |
| --- | --- | --- |
| 执行前 | `PreToolUse`:allow / deny / ask / defer | `tools/pre-execute`:allow / deny / cancel / ask |
| 改参数 | 可以(`updatedInput`) | 不可以,参数在策略前就冻结 |
| 硬拒绝 | 多个 hook 并行,取最严格的结果 | `ToolGuard` 只能拒绝,与顺序无关 |
| 执行后 | `PostToolUse`:block、`additionalContext` | `tools/post-execute`:block、换 content / value、`additionalContexts` |
| 包住执行 | 没有对应物 | `tools/execute`(超时、重试、指标) |
| 只读观察 | — | `tools/result` |
| 写法 | 外部命令 / HTTP / prompt,JSON 进出 | 进程内插件 listener,类型化返回值;实验性 hooks 桥可以复用 Claude Code 的 hook 配置(23 篇) |
| 审批 | 权限模式 + 弹窗 | `ctx.approval`,一次一问,失败即拒绝,全程审计 |

## 踩坑

1. **想在 pre-execute 里"顺手修正"参数**——做不到,参数冻结后才进策略。正确做法是 deny 并在 `reason` 里告诉模型该怎么改,让它重新调用
2. **把 `never` 当成免审批**——`never` 是自动拒绝。想不被询问又能执行,要放宽沙箱模式,而不是改审批策略(05 篇)
3. **headless 运行里一堆调用被拒**——没有 UI 回答者时,`ask` 落到 `unavailable`,失败即拒绝。拒绝原因里写着 "no approval channel is available"
4. **用 waterfall 写"绝对不许"的规则**——别的插件 prepend 一个 listener 返回 `allow` 就能截断它。硬规则用 `ctx.tools.guard()`
5. **以为 post-execute 换掉 content 就把数据藏住了**——PTC 程序拿的是规范值。要保密就 block 或换 value
6. **指望 `fs/write-intent` 审计所有文件改动**——它只管 `tool-fs`,bash 改的文件看不到。全覆盖的审计要另想办法,比如监听 `turn/end` 后扫描工作区
7. **给工具设了 `timeoutMs` 却没生效**——这个字段只是声明,真正执行超时的是 `timeout-policy` 插件。工具本体也必须配合 `exec.signal`,否则没法停下
8. **看到 `partial` 也当完整沙箱用**——`enforcement: partial` 表示有些文件效果管不住。需要绝对边界的场景要检查这个字段
9. **spill 提示里的路径读不到**——定位符是不透明的,要按 `retrievalHint` 取。远程或非共址部署下它可能根本不是本地路径
10. **审计里找不到审批记录**——`approval/asked` / `approval/decided` 只进会话日志,不进模型历史。要从日志或会话查询里找,不要翻对话转录

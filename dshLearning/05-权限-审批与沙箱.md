# 权限、审批与沙箱

04 篇讲 agent 预设决定"模型手里有哪些工具"。这一篇讲另一半:**这些工具真正执行时,能碰到什么、什么时候要停下来问人**。

读过 Claude Code 系列 04 篇的话,先把那套心智放一放。Claude Code 是"权限模式 + allow/deny 规则 + 可选沙箱"三层;dsh 的结构更接近 Codex CLI:只有 **sandbox mode** 和 **approval policy** 两个旋钮,连模式名 `read-only` / `workspace-write` / `danger-full-access` 都和 Codex 一样。界面上的"权限预设"只是把两个旋钮捆在一起的快捷方式。

> 一句话先记住:**sandbox mode 管"文件能写到哪",approval policy 管"要越界时问不问人",两者互相独立**。plan mode、提示词、AGENTS.md 都不是边界。而且这两个旋钮**都不管读和网络**。

---

## 一、两个旋钮

### 1.1 sandbox mode:只管文件写

| 模式 | 写文件 | 说明 |
| --- | --- | --- |
| `read-only` | 一律拒绝(POSIX 后端只额外放行 `/dev/null` 这类 shell 必需的输出) | 只看不改 |
| `workspace-write` | 只能写会话工作区和平台临时目录 | 新会话的默认值 |
| `danger-full-access` | 不限制,命令直接以原始 argv 运行,不经过沙箱 | 等于关掉沙箱 |

它同时约束两类工具:shell 命令(`dsh-bash-sandbox` / `dsh-pwsh-sandbox`,包括子进程)和文件工具的 `write` / `edit`(`dsh-fs-sandbox`)。两边用同一个函数算可写根目录,不会出现"bash 能写、edit 不能写"的错位。

仓库对这个词汇表的定义很直白:`SandboxMode` **只管文件效果,网络和进程可见性不在它的范围内**。

### 1.2 approval policy:`ask` 和 `never`

每次审批请求只有四种结局:`allowed-once`、`rejected`、`cancelled`、`unavailable`。**只有 `allowed-once` 放行**,其余三种调用方一律按拒绝处理(fail closed)。

| policy | 行为 |
| --- | --- |
| `ask`(默认) | 交给已组合的应答者(Web 的审批面板、ACP 客户端等);**没有任何应答者时结果是 `unavailable`,等于拒绝** |
| `never` | 不问任何人,**每个请求直接 `rejected`** |

> **`never` 是自动拒绝,不是自动批准。**这是最容易写错的一点。CI 里想"别弹窗",`never` 的效果是"所有需要批准的动作都失败",而不是"都放行"。

审批面板只有"允许这一次"和"拒绝"两个选项,没有"总是允许"。dsh 的默认组合里也没有 Claude Code 那种按工具、按参数写的 allow / deny 规则表。想少弹窗,办法是换预设,而不是攒规则。

### 1.3 什么时候会弹审批

和 Claude Code 的 Manual 模式"每条没放行的 Bash 都问一次"不同,dsh 在 `workspace-write` 下**工作区内的命令和改动直接执行,不弹窗**。默认组合里会触发审批的主要是:

- **提权重试**:命令或 `write` / `edit` 被沙箱拒绝后,模型申请用更宽的模式重跑一次(第五节)。PTC 的 `run_code` 也有同样的参数
- **`plugin_manager` 工具**:Creator 模式下装插件、改组合,非 Full access 时每个动作都要审批(20 篇)
- **实验性的 Auto review** 判定为拒绝的调用(第六节)

审批请求和结果会写进会话日志(`approval/asked` / `approval/decided`),但不进模型的对话历史。审批在工具管线里的位置见 13 篇。

## 二、权限预设

### 2.1 三个预设

base bundle 的 `permission` 行配置了三个预设:

| 预设 key | 界面标签(英 / 中) | sandbox | approval |
| --- | --- | --- | --- |
| `read-only` | Read Only / 仅可查看 | `read-only` | `ask` |
| `workspace-write` | Workspace Write / 工作区内修改 | `workspace-write` | `ask` |
| `danger-full-access` | Full access / 完全权限 | `danger-full-access` | `never` |

另外两个名字是保留的:

- **`auto`**:实验性 Auto review 装上后才出现,只能用于当前会话(第六节)
- **`custom`**:派生出来的显示状态。当两个旋钮的组合不匹配任何预设时(比如某个插件或 patch 单独改了 approval policy),界面显示 `custom`。它不能被选中,只能从它切走

注意 Full access 的组合:`never` 本来是"一律拒绝",但 `danger-full-access` 下沙箱关了,也就没有需要提权的东西,`plugin_manager` 在这个模式下也不需要审批。所以**体感是"不问直接干"**,而不是"什么都被拒"。

### 2.2 怎么切

| 入口 | 作用范围 |
| --- | --- |
| Web 输入框旁的权限控件 | 当前会话 |
| `/permission` | 不带参数:列出当前预设和可选项;`/permission workspace-write`:直接切换 |
| Settings → General 里的默认权限 | **只影响之后新建的会话**,不改已打开的会话,也不提供 Auto |

在 Web 里通过选择器切到 Full access 或 Auto,会先弹一次风险确认;直接输入完整的 `/permission <预设>` 则立即执行。切换只改值真正变化的那个旋钮,重复选择当前预设什么也不写。headless、ACP、SDK 没有斜杠命令。

### 2.3 自定义预设表

预设表在 `@deepseek-ai/dsh-permission-presets` 的配置里。patch 会**整体替换**目标行的 `config`(11 篇),所以改默认值时要把整张表一起写上:

```yaml
# $DSH_HOME/cordis.patch.yml,对所有 profile 生效
- id: permission
  config:
    presets:
      read-only:
        sandbox: read-only
        approval: ask
      workspace-write:
        sandbox: workspace-write
        approval: ask
      danger-full-access:
        sandbox: danger-full-access
        approval: never
    defaultPreset: read-only
```

`defaultPreset` 必须指向表里存在的 key;`custom` 和 `auto` 不能出现在表里,否则插件加载时报错。

## 三、默认值:限制了什么,没限制什么

### 3.1 新会话从 `workspace-write` + `ask` 开始

base-backed 的 profile(web、headless、sdk、acp)新会话默认是 `workspace-write` 预设。这里的"工作区"是**会话创建时记录的工作目录**:CLI 下是你启动 `dsh` 的目录,Web 下是新建会话时选的 Workspace。

会话中途用 `working_directory` 工具切目录,改变的是相对路径和新进程的起点,**可写根目录仍然锚定在原始项目**(07 篇)。

### 3.2 三件默认不管的事

| 访问 | 默认 | 后果 |
| --- | --- | --- |
| 读 | **不限制** | `~/.ssh`、`~/.aws`、其他项目的源码,`read` 工具和 bash 都能读到 |
| 网络 | **不限制** | bash 里的 `curl` 照样能把数据发出去;`web_search` / `web_fetch` 在任何模式下都不逐次确认 |
| 进程可见性 | 取决于后端 | 只有 bwrap 用私有 PID 命名空间隐藏宿主进程;Landlock 和 Seatbelt 不隐藏 |

`web_fetch` 有一道自己的护栏:它只接受公网 HTTP(S) 目标,解析并校验每个目标地址,内网和回环地址在连接前就被拒绝(配了代理也一样)。但这只约束 `web_fetch` 这一个工具,bash 不受它保护。

另有一处是向好的:shell 子进程的环境变量会**按名字过滤**,名字里带 `KEY` / `PASSWORD` / `SECRET` / `TOKEN` 的变量和继承来的 `DSH_*` 不会传给模型跑的命令。这是名字启发式,`*PASSPHRASE*` 这类命名照样会漏过去。

### 3.3 `DSH_PERMISSION_MODE`

```bash
export DSH_PERMISSION_MODE=read-only     # read-only | workspace-write | danger-full-access
dsh --profile headless "审查这个仓库的错误处理"
```

它在 base 里同时决定两件事:`sandbox-policy` 行的回退 mode,以及 `approval` 行的 policy(值为 `danger-full-access` 时是 `never`,否则是 `ask`)。预设服务再根据这两个值推断出默认预设。

两点要注意:

- **必须 export,不能写进 `.env`**。项目 `.env` 和 `$DSH_HOME/.env` 都拒绝设置 `DSH_*` 整个命名空间,理由是一个克隆下来的仓库不应该能改掉你的审批策略
- **Web 里存过的默认预设优先**。源码里默认预设是"配置的 `defaultPreset`,没有才用推断值",所以在 Settings → General 选过默认权限后,`DSH_PERMISSION_MODE` 推出来的默认就不再起作用

恢复的会话保持它自己记录的权限,不会被新的默认值改写。

## 四、各平台的沙箱后端

### 4.1 后端选择

`dsh-sandbox-local` 按平台挑后端,链上有多个候选时逐个做功能探测,选中后在插件生命周期内缓存:

| 平台 | 后端 | 强制程度 | 备注 |
| --- | --- | --- | --- |
| Linux | 先 bwrap,再 Landlock | bwrap:full;Landlock 在旧内核 ABI 上可能 partial | 只有 bwrap 隐藏宿主进程;bwrap 下 `/tmp` 是临时挂载 |
| macOS | Seatbelt(`sandbox-exec`) | full | 依赖已被 Apple 标为废弃的 `sandbox-exec` |
| Windows | ACL 受限令牌(Low integrity) | **partial** | 硬链接可绕、读不受限;只跑 PowerShell 工具 |
| SSH 远端 | 远端主机自己的本地后端 | 随远端后端 | `dsh-sandbox-ssh`,见 29 篇 |

"强制程度"是后端**报告的事实**:`full` 表示模式承诺的文件效果全部被管住,`partial` 表示只管住一部分。Windows 上 dsh 明确报告 partial,不要把它当成硬边界。

### 4.2 fail closed

没有可用后端时(比如 Linux 上既没装 bwrap、内核也不支持 Landlock),`confine()` 直接以 `SANDBOX_UNAVAILABLE` 失败,**命令不会退化成无沙箱运行**。后端选择会缓存,装好 bwrap 后要重启 profile 才会重新探测。

模型看到的几种标记:

```text
[sandbox: file access denied under workspace-write mode]
[sandbox: escalation available — retry this exact command once with sandbox_permissions ...]
[sandbox: the sandbox runner itself failed under workspace-write mode — the command did not run; ...]
```

第一种是策略拒绝(沙箱正常工作,挡住了越界写);第三种是沙箱本身坏了,命令根本没跑。两者在实现里分开判断,不会把"沙箱故障"误报成"命令失败"。

## 五、提权重试

### 5.1 流程

```text
命令在 workspace-write 下写了工作区外的文件
  → 结果带 [sandbox: file access denied ...] 和提权提示
  → 模型在同一轮里用完全相同的命令重试一次,附 sandbox_permissions + justification
  → approval 服务:ask → 弹给你;never → rejected;没有应答者 → unavailable
  → allowed-once:只有这一次调用以更宽的模式运行
```

模型发出的重试参数大致是这样:

```json
{
  "description": "Install packages into the global cache",
  "command": "npm install",
  "sandbox_permissions": "danger-full-access",
  "justification": "npm 需要写工作区外的全局缓存目录"
}
```

### 5.2 规则

- `sandbox_permissions` 只能填比当前更宽的模式:`read-only` 可以升到 `workspace-write` 或 `danger-full-access`,`workspace-write` 只能升到 `danger-full-access`。填当前模式不需要审批,填更窄的直接报错
- 填了 `sandbox_permissions` 就必须给非空的 `justification`;只给 `justification` 不给模式会被拒
- **被拒绝的提权对这条命令是最终结果**,工具描述也告诉模型不要换个方式再试
- 批准**不改变会话的权限模式**,下一条命令仍回到原来的模式
- 只有挂了沙箱执行器时,工具 schema 里才出现这两个字段

### 5.3 没人回答时

| 场景 | 提权请求的结局 |
| --- | --- |
| Web | 弹审批面板,Enter 批准、Esc 拒绝 |
| headless | 没有组合任何应答者,`ask` 落空为 `unavailable`,一律失败 |
| SDK(`sdk` profile) | 同上,服务端到客户端的请求还没实现,没有审批回调 |
| ACP | 以 `session/request_permission` 转发给客户端,一次性 allow / reject,客户端可以自动回答 |
| `sdk-minimal` | 固定 `danger-full-access`,不挂审批和权限设置服务 |

所以无人值守时,要么把任务设计成在 `workspace-write` 内就能完成,要么把整个进程放进一次性容器再放宽权限(27 篇)。

## 六、沙箱之外的东西

### 6.1 不受沙箱约束的代码

- **MCP server**:每个 server 命令都是在 agent 沙箱之外运行的受信任代码,所以默认一个都不启用(22 篇)
- **Host 插件**:`dsh plugin` 装进 profile 的插件在宿主进程里运行,不在工作区沙箱内
- **Claude Code mods 桥**(实验性):mod 的 hooks 模块在进程内以完整权限运行,没有沙箱(23 篇)
- **外部 agent 子代理**:Codex、Claude Code 按各自的原生权限配置运行(24 篇)

### 6.2 Auto review(实验性,默认关闭)

`@deepseek-ai/dsh-experimental-auto-review` 随安装包附带但默认关闭,可以在 Web 侧栏的 Plugins 页打开或显式安装。打开后当前会话的选择器里多一个带 `EXP` 标记的 **Auto review**:

- 组合是 Full access 的沙箱值 + `ask`
- 每个工具调用(包括 PTC 里的子调用)执行前,用当前 agent 的模型评估一次风险;判定允许就以 Full access 执行,判定拒绝就转成审批问你
- 委派出去的进程内子代理固定 `never`,它们被拒就是最终结果
- 只能用于当前会话,不能设成默认;卸载时活跃的 Auto 会话会迁移到 Full access

仓库原话是它"可能放行不安全的动作、拒绝有用的工作、并额外消耗 token"。和 Claude Code 的 auto mode 定位相近,但这里是开发预览里的实验功能,用之前按你的版本重新核对。

### 6.3 SAFETY.md 的立场

仓库根目录的 `SAFETY.md` 写得很明确:dsh 是没有做过安全审计的开发预览版;沙箱、审批和权限控制**能降低风险,但不保证隔离**;即使限制被正确执行,也保护不了项目本来就被允许访问的资源。建议的做法是最小权限、**优先使用一次性虚拟机、容器或专用环境**、给可访问的文件做备份。

| 你想要 | 推荐配置 |
| --- | --- |
| 日常在自己机器上改代码 | 默认 `workspace-write`,敏感凭证别放在可读位置 |
| 只读审查陌生仓库 | `read-only`,最好再套一层虚拟机 |
| CI 里跑 headless | 保持 `workspace-write`,让容器承担外层隔离 |
| 完全放手 | Full access 或 `sdk-minimal`,**只在一次性容器里** |

## 踩坑

1. **以为 `never` 是"自动批准"**——它是自动拒绝。Full access 不弹窗,是因为沙箱关了、没有需要批准的提权,不是因为 `never` 放行
2. **以为 `workspace-write` 能保护 `~/.ssh`**——读不受限。凭证文件要么移出运行用户能读的范围,要么在虚拟机或容器里跑
3. **以为沙箱能防数据外泄**——网络不受限,bash 里的 `curl` 照样能发。`web_fetch` 的公网限制只管它自己
4. **把 `DSH_PERMISSION_MODE` 写进项目 `.env`**——`DSH_*` 在 `.env` 里一律被拒,要在 shell 里 export
5. **改了 `DSH_PERMISSION_MODE` 却发现 Web 新会话没变**——Settings → General 里存过的默认预设优先于它
6. **headless 里一堆调用失败**——没有审批应答者,`ask` 落空即失败。把任务限定在工作区内,或在容器里换预设
7. **在 Windows 上把沙箱当硬边界**——后端自己报告 partial:硬链接可绕,读不受限
8. **Linux 上命令报 `SANDBOX_UNAVAILABLE`**——bwrap 和 Landlock 都不可用。装 bubblewrap 后重启 profile,后端选择是缓存的
9. **用 patch 改 `permission` 行只写了 `defaultPreset`**——patch 整体替换 `config`,预设表回到 schema 默认的 `workspace-write` 和 `danger-full-access` 两项,Read Only 就没了。整张表要一起写
10. **以为 plan mode 能拦住改文件**——plan mode 只是提示词(08 篇),真正的边界在这一篇的两个旋钮

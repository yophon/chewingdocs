# 会话即事实源:事件日志与持久化

15、16 篇一直在说"记入日志""能从日志重建"。这一篇把这本日志本身拆开:它由哪些事件组成、模型看到的消息怎么从里面算出来、怎么落盘和迁移、怎么分叉和恢复,以及仓库怎样管住它的格式变化。这是第二层「读懂 dsh 内核」的最后一篇。

会话存在哪、怎么 resume / fork / 搜索、Trajectory 视图怎么用,这些用户侧功能在 07 篇;本篇只讲机制。

> 一句话先记住:**模型看到的一切都必须先写进日志(Model-visible means logged)。dsh 不单独保存"消息历史",消息是从 append-only 事件日志现算出来的;恢复、分叉、Trajectory、token 统计、会话上传,都是同一份日志的不同读法**。

---

## 一、原则:Model-visible means logged

`docs/architecture.md` 里这条原则只有几句:每个模型请求都必须能从日志重建;新的模型可见输入必须对应会话事件;要改已有消息内容的插件,注册纯函数式的 message projection。落到实现上:

- loop 发出的请求 = 最新 `request/header` 里的调用配置 + `deriveMessages()` 派生出的历史 + header 里的工具列表,没有别的来源
- 请求在发出前被深冻结,`llm/stream` listener 改不了它(15 篇)
- 插件想给模型加上下文,调 `agent.inject()`,它会作为 `user/message` 事件落进下一个请求;不能在内存里偷偷拼一段

好处很实际:任何一次"模型为什么这么回答"都能拿日志原样复现;失败的尝试、重试、压缩前的原文全都在;分叉和恢复只是"从某个位置重新派生"。

## 二、事件日志的形状

### 2.1 一条事件

```ts
type SessionEvent = {
  type: K                  // 比如 'user/message'
  seq: SessionSeq          // 在日志中的位置,seq = log.length,连续不跳号
  time: number             // 毫秒时间戳
  data: SessionEventMap[K]
  ignorable?: true         // 读者不认识这个 type 时能否跳过
  // 仅 surface 事件:surfaceOp,以及可选的 sourceEventSeqs
}
```

几条硬规则:**只追加,已提交的事件永不改写**;`Session.append` 在源头校验 `data` 必须是可序列化的 JSON,不合法直接抛错,所以内存里的日志永远等于后端能持久化的内容;读者遇到不认识、又没标 `ignorable: true` 的事件,必须拒绝重建会话,而不是静默丢掉。

### 2.2 核心事件

| 事件 | 是否进入 surface | 作用 |
| --- | --- | --- |
| `turn/start` / `turn/end` | 否 | 轮次边界;`turn/end` 带结束原因 |
| `step/start` / `step/end` | 否 | 步骤边界:一次模型调用加它请求的工具 |
| `system/message` | 是 | 渲染后的 system prompt(16 篇) |
| `developer/message` | 是 | 中途的工具增删 |
| `user/message` | 是 | 用户输入、注入的上下文、压缩摘要 |
| `assistant/message` | 是 | 组装好的助手消息,内嵌紧凑的原始流和 usage |
| `assistant/attempt` | 否 | 没有产生消息的尝试:失败、被重试、被取消 |
| `tool/call` | 否 | 工具调用记录,参数是原始 JSON 字符串 |
| `tool/result` | 是 | 工具结果,可带工具私有的 `meta` |
| `request/header` | 否 | 下一个请求的调用配置和工具列表,原因为 `initial` / `resume` / `change` / `series` |
| `request/context` | 否 | 路由、容量、`systemPromptUpdate` 模式,只在变化时记录 |
| `session/end-seed` | 否 | 继承历史与本次生命周期的分界 |

`turn/end` 的原因有 `completed`、`aborted`、`blocked`、`error`、`max-tokens`、`interrupted`、`forked`。其中 `interrupted` 只由崩溃恢复补写,`forked` 只由分叉构造补写,loop 运行时从不发出这两个。

### 2.3 一个轮次在日志里的样子

示意,省略了字段,序号仅为说明连续性:

```text
seq 0   turn/start          {"turn":1}
seq 1   step/start          {"turn":1,"step":1}
seq 2   system/message      surfaceOp: append     ← surface 节点 0
seq 3   user/message        surfaceOp: append
seq 4   request/header      {"reason":"initial", …}
seq 5   request/context     …
seq 6   assistant/message   surfaceOp: append     (内容里有一个 tool-call 块)
seq 7   tool/call           {"callId":…, "name":…, "arguments":"{…}"}
seq 8   tool/result         surfaceOp: append
seq 9   step/end
seq 10  step/start          {"turn":1,"step":2}
…
seq n   turn/end            {"turn":1,"reason":{"kind":"completed"}}
```

工具调用在两处出现:助手消息内容里的 `tool-call` 块进入 surface,给模型看;单独的 `tool/call` 事件是 log-only,给工具管线和界面用。

### 2.4 插件可以扩展词汇

`SessionEventMap` 支持声明合并,插件可以加自己的事件类型,比如 `compaction/start|summary|end`、`llm/retry`、`image/offload`、hooks 桥的 `hook/invoked` / `hook/result`、会话上传的 `session-log-deepseek/delivery-accepted`。这些都是 **log-only**:不带 `surfaceOp`,不进入模型历史。生成的 `docs/persistence-catalog.md` 列出了仓库里每一个持久事件,目前有 60 多个事件根。

实验性的包另有一条路:声明在 `PluginRecordMap` 里,用 `appendPluginRecord()` 写入 `plugin:` 前缀、自动标 `ignorable: true` 的记录,不进入正式的持久化 schema。

### 2.5 持久事件与实时事件

会话事件是要在重载后依然成立的事实,通过 `session/event` 广播;`agent/*` 事件携带活的 `Agent`,用来观察和拦截进行中的工作(12 篇)。流式输出最能说明区别:界面上逐字出现靠的是进程内的 `agent/assistant-stream` 帧;落盘的是一次尝试结束时整体写入的紧凑流,嵌在 `assistant/message` 或 `assistant/attempt` 里。进程在尝试结算前硬崩溃,这次尝试就不会留下持久记录。

## 三、Surface 与 deriveMessages()

### 3.1 surface:模型可见的有序节点

只有五种事件能进入 surface:`system/message`、`developer/message`、`user/message`、`assistant/message`、`tool/result`。每条都必须声明怎么加入:

```ts
type SurfaceOp =
  | 'append'                                              // 追加到尾部
  | { op: 'replace'; startSeq: SessionSeq; endSeq: SessionSeq } // 替换一段节点
```

`replace` 用新节点替换当前 surface 上的一个闭区间,区间按 surface 位置而不是 seq 大小来定,新节点的 `sourceEventSeqs` 必须列出所有被遮蔽的节点。压缩摘要和工具结果裁剪都靠它;节点 0 的 system prompt 受保护,不能被其他替换覆盖。被替换的事件仍在日志里,只是不再出现在 surface 上。`Session.surface` 暴露 `nodes`、`replaceGeneration`、`contentGeneration`,增量消费者据此区分"尾部增长"和"发生了改写"。

### 3.2 deriveMessages()

`Session.deriveMessages()` 把 surface 投影成模型看到的 `Message[]`:每个节点首次出现时投影一次并缓存,surface 被改写时重建;返回的消息深冻结,所以不可能通过投影去改日志里的历史。规则:

- `user/message` 原样变成 user 消息,注入的上下文也是 user 角色,由 `source` 区分来源
- `assistant/message` 带上产生它的 provider、model 和 adapter 私有的回放状态;**内容为空的助手消息被跳过**,比如被 `max-tokens` 截断、一个字都没输出的步骤
- `tool/result` 变成 tool 角色消息
- 其余事件都是结构性的,不产生消息

逐节点的纯函数 `deriveEventMessage()` 是公开的,外部重建工具可以用完全相同的规则投影日志的任意前缀。

同一份日志还有第二种投影:给人看的对话记录读的是"以 append 方式加入的事件",因为 surface 会故意遮蔽被摘要的区间,而人需要看到原文。

## 四、落盘:持久化接缝与 JSONL

### 4.1 `ctx.sessionPersistence`

持久化是一个可替换的能力,抽象服务只有四个操作:`create` / `open` / `stat` / `list`。`create` 和 `open` 返回 `SessionHandle`,所有读写都经过它:

| 方法 | 语义 |
| --- | --- |
| `read(offset?, length?)` | 读合法的连续前缀,不会读到写坏的尾部,同一句柄的读取不会倒退 |
| `append(events)` | 追加一批连续事件,首条 `seq` 必须等于下一个序号;resolve 只保证已接受、有序、可见 |
| `flush()` | **唯一保证落盘的操作** |
| `close()` | 幂等、不可取消;写句柄会先完成未决的持久化 |

单写者:同一进程里已有写句柄时,再次 `open(id, 'write')` 会报 `SessionAlreadyOwnedError`;只读观察者用 `open(id, 'read')`,在读句柄上写会报 `SessionReadOnlyError`。

### 4.2 JSONL 后端

base bundle 的 `session-persistence-jsonl` 行把根目录设在 `$DSH_HOME/sessions`。目录结构:

```text
<root>/
  --<规范化的 cwd>--/          # 按工作目录分的项目目录,没有 cwd 时为 _no-cwd/
    <编码后的会话 id>/
      session.jsonl.zstd       # v0 的命名
      session.v1.jsonl.zstd    # v1 起统一为 session.vN.jsonl[.zstd]
      …
```

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `root` | 必填 | 没有默认值,避免随进程 cwd 到处散落文件 |
| `compression` | `'zstd'` | 带校验和的 Zstandard 帧;`'none'` 是可直接阅读的换行分隔文本 |
| `listConcurrency` | `3` | 列表时并发的目录和头部读取数 |

当前格式每个事件一行;第一帧只放头部行,之后每批追加一帧,写完 `fsync` 才 resolve。会话是惰性物化的:`create` 不写任何东西,第一次 `append` 或 `flush` 才落盘。

### 4.3 写后批处理与检查点

`session/event` 是同步通知,后端把它路由进对应写句柄的批处理窗口,不阻塞生产者:第一条待写事件开启一个固定窗口,窗口到期发起一次持久的 `append`。`session/flush`(parallel 模式,所有 listener 都跑完才返回)会取消等待、排空缓冲,loop 在领取下一个普通轮次前用它做顺序和错误观察的检查点。

更严格的保证来自 `dsh-session-checkpoint-policy`:**在模型请求之前、在顶层工具可能产生外部副作用之前、在下一步骤开始之前**都先落盘,写失败就不执行(fail-closed)。

### 4.4 崩溃恢复不截断

崩溃在轮次中间的日志以一个没有 `turn/end` 的 `turn/start` 结尾。持久化层**不截断、不修复**——长任务的一个轮次可能非常大,这些事件在崩溃前已经落盘。它只丢弃物理上写坏的尾部片段(JSONL 后端甚至会从残缺的 Zstandard 帧里解出完整记录,下次写之前重新写入)。修复是读者的事:resume 时 loop 计算补全事件——缺失的工具错误结果、未关闭的 `step/end`、合成的 `turn/end {kind: 'interrupted'}`——再通过同一个写句柄追加。中断时正在跑的工具会得到"结果未知"的错误结果,而不是被自动重跑。只读的 session-query 在内存里做同样的补全,不写回。

## 五、格式版本与迁移

当前写入格式是 `packages/core/session/src/types.ts` 里的 `SESSION_FORMAT_VERSION = 4`。`docs/session-format-status.md` 另外记录两件事:v4 已定稿(`latestFinalizedVersion: 4`,基线在 `docs/persistence-changes/finalized/v4.json`),已发布版本是 4(证据标签 `dsh-v0.2.0-rc.2`)。

迁移规则:

- 每个代际一个文件,**已提交的代际文件永不重命名、替换或删除**
- 运行时总是选编号最高的代际;旧代际由相邻迁移包逐级升级:`session-format-v0-to-v1` … `session-format-v3-to-v4`,每个包只负责一步
- 以只读方式打开旧会话,只在内存里迁移,不写新文件;以写方式打开,先在旧文件旁边独占地发布新代际,再返回可写句柄
- 遇到比自己新的代际直接拒绝(`SessionFormatUnsupportedError`),即使旧代际文件还在;这与表示数据损坏的 `SessionPersistenceCorruptionError` 是两回事
- 当前格式会保留标了 `ignorable: true` 的未知事件;但从 v0 / v1 / v2 迁移时,遇到未知类型即使标了 `ignorable` 也拒绝

## 六、分叉、恢复与回放

**分叉**:`ctx.sessions.fork(source, boundary?, childSessionId?)`。`boundary` 是包含在内的 seq,默认是最后一条事件;选中的前缀必须停在轮次之外,否则直接拒绝,不会悄悄截断。子会话拿到深拷贝的种子事件,头部记录 `parentSession` 和 `isSeeded: true`,精确的继承长度由日志里最后一个 `session/end-seed {inherited: true}` 标记推出。fork 子代理不同:工具调用时父轮次通常还开着,所以它自己截到最近一个完整轮次(24 篇)。`session/end-seed` 只能由构造函数和 `buildForkSeed` 写入,它让"继承来的未闭合括号"(比如没配对的 `compaction/start`)和"正在进行的工作"可以区分开。

**恢复**:`ctx.agents.resume(options)` 先加载持久化的会话,补全中断的轮次,再发布给 loop。没有变化的 resume 延续原来的请求序列,前缀缓存不受影响(16 篇)。

**回放**:就是从同一批事件重新派生。`foldSurface(events, projections)` 和 `deriveEventMessage()` 让外部工具用同样的规则还原任意前缀;15 篇讲的 `dsh_session_log` 上传发送的也是这些规范事件。

## 七、读侧:projection、query 与 storage

| 服务 | 读什么 | 要点 |
| --- | --- | --- |
| `ctx.sessionProjections` | 从日志折叠出的按会话状态 | 每个单元是纯同步的 fold,框架对每条已提交事件驱动它;宿主用 `stateOf()` 读,客户端拿 `snapshot()` 的成品值,不自己折叠。例:token-meter 的 `tokenUsage` / `contextPressure`,loop 的 `turnBoundary` |
| `ctx.sessionQuery` | 跨会话的精确读取、过滤、血缘追踪、全文搜索 | 事件按 `current` / `shadowed` / `log-only` 分类;全文搜索由 SQLite FTS5 后端提供,索引是独立的派生库 |
| `dsh-session-reference` | 在对话里用 `@label` 引用另一个会话 | 生成有界、只读的快照,附带警告不执行其中的指令;不需要 FTS |
| `ctx.storage` | 会话日志以外的持久数据 | 后端 `json`(base 里根目录 `$DSH_HOME/storages`)和 `sqlite`,业务代码通过 `ctx.storageDomain` 使用 |

注意 base bundle 里全文搜索**默认是关的**:`session-query-sqlite` 配成 `path: ':memory:'`、`openAt: never`,精确读取和标题照常可用,搜索调用报 `SESSION_QUERY_SEARCH_DISABLED`。要开启,在 profile 的 `cordis.patch.yml` 里覆盖这一行(按行 id 整体替换 config,见 11 篇):

```yaml
- id: session-query-sqlite
  name: '@deepseek-ai/dsh-session-query-sqlite'
  config:
    path: /absolute/path/to/session-search.db   # 专用路径,别指向会话日志
    openAt: first-search                        # 或 startup
```

projection 也有持久化缓存:base 里的 `session-projection-cache` 通过 storage 每 200 条事件或 5 秒写一次检查点,给会话列表用。

## 八、持久化变更流程

日志格式是对用户数据的承诺,仓库为此有一套流程(`docs/persistence-changes/README.md`):

- 生成的 `docs/persistence-catalog.md` 和 `docs/persistence-schema.json` 给每个持久化根(会话头、JSONL 头部行、事件信封、每种事件)算 SHA-256 摘要,引用的类型会传递进摘要
- **检测到任何结构变化都要提交一份确认记录**:同一日期名下四个文件——英文 `.md`、中文 `.zh.md`、生成的 `.i18n.yaml`、变化后的完整 `.schema.json`
- 每条变化要声明决定:`same-version`(老读者仍能安全处理,比如新增可选字段、新增普通事件类型)或 `version-bump`(必须提升 `SessionHeader.version`)
- 定稿的记录和 schema 快照不可修改;本地和 CI 的校验只用仓库内文件,比对摘要、前驱链和头部版本约束

一条真实记录的声明部分(`2026-09-18-schedule-optional-title.md`):

```yaml
schemaVersion: 1
id: 2026-09-18-schedule-optional-title
baseline: false
changes:
  - root: "event:schedule/change"
    previous: "2026-09-11-initial"
    after: "a0a2e5c42e1c929445ecd1cd70f49be6b66441894ec72c08e8ae332821d4a3cb"
    decision: same-version
```

后面还要用正文说明兼容性(旧日志没有 title 字段时怎么读)和验证证据(跑了哪些测试)。v3→v4 那次升级的记录 `2026-09-16-session-format-v4.md` 则把 `SessionHeader` 和多种事件标为 `version-bump`。

对插件作者的启示:**给 `SessionEventMap` 加事件类型,就是在改磁盘格式**。仓库外插件的事件不在这套目录里,兼容性要自己负责;还在试验的状态更适合用 `plugin:` 记录。

## 九、回头看:事件溯源换来了什么

| 能力 | 怎么从日志得到 |
| --- | --- |
| 调试 | 失败的尝试以 `assistant/attempt` 保留原始流,重试有 `llm/retry`,请求能逐字节重建 |
| Trajectory 视图 | Web 端的 `ui-trajectory` 和 Chat 视图读同一份事件,只是组装方式不同 |
| 分叉与子代理 | 取日志前缀做种子 |
| 崩溃恢复 | 不截断,只追加补全事件 |
| 统计与上传 | token 用量是 projection;会话上传发送规范事件的后缀 |
| 可逆的压缩 | surface 只遮蔽,原文仍在 |

## 踩坑

1. **插件自己维护一份消息数组拼给模型**——违反"模型可见即记录"。用 `agent.inject()`、自定义会话事件,或注册 message projection
2. **往事件 `data` 里放不可序列化的对象**——`Session.append` 当场抛错,事件不会进入日志
3. **新事件随手标 `ignorable: true`**——只有丢了也不影响重建的纯信息记录才能标;漏标的代价是旧读者拒绝打开,错标的代价是旧读者静默丢掉关键事件
4. **插件自己写 `session/end-seed`**——只有构造函数和 `buildForkSeed` 能写,手写会把之前所有括号都归为"继承的历史"
5. **以为 `append` resolve 就落盘了**——只有 `flush` 保证。需要强保证的场景依赖 checkpoint policy
6. **两个进程同时写同一个会话**——单写者设计,第二个写句柄会被拒绝;观察者用只读句柄
7. **新版本打开过旧会话,再换回旧版本**——写方式打开会发布 v4 代际,旧版本看到更高的代际会拒绝,即使旧文件还在。回退版本前要考虑这一点
8. **以为会话内容默认就能全文搜索**——base 里 `openAt: never`,要用 patch 打开
9. **把崩溃后多出来的 `interrupted` 轮次当成数据损坏**——这是设计行为:恢复时追加的补全事件,中断的工具得到"结果未知"

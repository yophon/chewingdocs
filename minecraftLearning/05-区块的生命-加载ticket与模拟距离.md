# 区块的生命:加载、ticket 等级与模拟距离

你建了一座全自动刷怪塔,站在旁边刷刷刷出怪、掉落、收集,一切完美。然后你跑去几百格外探险,回来发现塔里空空如也——它在你离开的整段时间里**根本没运转**。

很多人对这件事的理解停留在"区块卸载了嘛"。但真相要精细得多:那座塔所在的区块**很可能还加载着**,它只是被降到了一个"不再跑某些逻辑"的等级;而刷怪还有一条和区块等级无关的额外规则。"加载"和"运转"是两回事,Minecraft 用一套**连续的等级数值**来区分它们。

> 一句话先记住:**区块不是"加载/卸载"的二元开关,而是有一个 level 数值(越小越活跃)。加载源像光源一样把周围区块"照亮",离源越远等级越高、越不活跃。农场停摆,要么是区块等级掉出了"会 tick"的范围,要么是没满足"附近要有玩家"这类额外条件。**

---

## 一、区块不是开关,是一片"距离场"

朴素的心智是这样的:

```
区块状态 = { 已加载, 未加载 }   // 错误的二元模型
```

这个模型解释不了一堆现象:为什么有的区块加载了但不刷怪?为什么离玩家近的机器跑、远的不跑,但更远的方块明明还能被命令读到?

真实模型是:每个被加载的区块带一个**整数等级 `level`**,这些等级构成一片**距离场(distance field)**,本质就是一次从"加载源"出发的 BFS 传播:

- 加载源所在区块等级最低(最活跃);
- 向外**每扩散一圈,等级 +1**(包括斜向,所以是一圈圈的正方形);
- 等级超过某个阈值,区块就"还在内存里,但不再跑逻辑";再高就卸载。

这套机制在引擎里叫 **ticket 系统**:任何想让某区块保持活跃的东西,都往世界里放一张 **ticket(加载凭证)**,ticket 自带一个等级,然后这个等级从 ticket 中心向外 +1 传播,每个区块取所有 ticket 传过来的最小值。

用一张 `/forceload` 产生的 ticket 举例,它的等级是 31:

```
单个 /forceload ticket(等级 31)向外传播:

   34 34 34 34 34 34 34
   34 33 33 33 33 33 34
   34 33 32 32 32 33 34
   34 33 32 31 32 33 34      31 = 中心区块:entity ticking
   34 33 32 32 32 33 34      32 = 第一圈:block ticking
   34 33 33 33 33 33 34      33 = 第二圈:border(可访问,但不 tick)
   34 34 34 34 34 34 34      34+ = 更外圈:inaccessible,一直到 44 为止
```

**玩家本身就是一张会移动的 ticket**,而且是一张"更亮"的 ticket:它的等级比 31 低出整整一个模拟距离(simulation distance),所以以玩家为中心、半径等于模拟距离的一整片区块都在 31 以下;再往外一圈是 32、再一圈是 33。

## 二、几条等级线:从"全功能"到"仅加载"

等级不是连续生效的,而是有几条**关键阈值线**,跨过去就掉一档能力(1.18+ Java 版):

| 等级 level | 档位 | 这一档会发生什么 |
| --- | --- | --- |
| ≤ 31 | **entity-ticking(完整)** | 全功能:**实体 AI 和移动**、方块实体、红石、流体、随机刻、刷怪(刷怪另有"128 格内有玩家"的条件,见下) |
| 32 | **block-ticking** | 方块还 tick(红石、流体这些计划刻,漏斗、熔炉这些方块实体),但**实体不再 tick**,也没有随机刻和刷怪 |
| 33 | **border(仅可访问)** | 区块完整加载、能被读写(命令、红石跨区块读取都行),但什么都不 tick |
| 34–44 | **inaccessible** | 还在内存里,通常是生成到一半的"半成品",游戏逻辑不能用 |
| > 44 | 不加载 | 卸载,等级超出 ticket 影响范围 |

最关键的一条线是 **31 → 32**:

- **≤31**:实体会动、会寻路、会被刷出来。这就是俗称的"区块在 ticking"。
- **=32**:实体集体冻结。掉落物不再动、怪不再走、村民不再干活;但红石和漏斗还在跑。

第二条线是 **32 → 33**:跨过去连方块 tick 都停了,区块沦为"只是数据"。

### 还有一条和等级无关的规则:128 格

等级只回答"这个区块有没有资格 tick"。**自然刷怪**还要求:这个区块离某个(非旁观模式的)玩家水平距离在 128 格(8 个区块)以内。雷击、岩浆引燃周围方块也是同样的要求。

随机刻的规则在 1.21.5 变过一次,读老教程时要注意:

- **1.21.4 及以前**:随机刻也要求 128 格内有玩家。所以离玩家很远、但被强制加载着的田,作物不长。
- **1.21.5 起**:随机刻不再看玩家距离,只要区块在 entity-ticking 范围里就有。强制加载的田终于能自己长了。

> 反直觉点:`/forceload` 的 ticket 等级就是 31——被强制加载的区块本身是 **entity-ticking** 的,实体会动、漏斗会吸、红石会跑。可很多人 forceload 了刷怪塔,却发现还是不刷怪。原因不在区块等级,而在上面那条"128 格内要有玩家"的刷怪规则。另外,forceload 只把指定那一个区块压到 31,它周围一圈只有 32——机器跨了几个区块,就得每个都 forceload。

## 三、三个"距离"别再搞混

玩家这边有三个看起来都叫"距离"的概念,它们管的是完全不同的事:

| 概念 | 谁设置 | 管什么 | 关键点 |
| --- | --- | --- | --- |
| **render distance(渲染距离)** | 客户端(服务端用 view distance 限制上限) | 多远的区块会被发给客户端、**画**出来 | 这些区块在服务端也要加载着,但只需要到"可访问"那一档 |
| **simulation distance(模拟距离)** | 服务端(单机时就是你的设置) | 多远的区块进入 **ticking(≤31)** | 决定随机刻、实体、刷怪的范围 |
| **chunk 加载等级 / ticket level** | 引擎内部 | 每个区块**具体**的活跃档位 | 上面两者最终都落到这个数值上 |

实际关系:

```
render distance   → 决定一圈区块被加载并发给客户端(看得见)
simulation distance → 决定其中多大一圈区块等级 ≤ 31(真的在跑)
                      ↓ 两者都通过往区块"压等级"来生效
chunk level (距离场) → 每个区块最终的档位,决定它具体能做什么
```

一个常被忽略的事实:**simulation distance 可以小于 render distance**。你能"看见"远处的山(render),但那片山**不在 ticking 范围**(simulation),所以山里的怪不动、机器不转。看得见,不代表跑得起来。

## 四、推论:为什么远处的农场会停摆

现在那座刷怪塔的谜题自解了。当你跑远:

1. 你这张"移动 ticket"离开了塔所在区块,塔区块的等级开始回升;
2. **离开 128 格**:刷怪停了——哪怕区块还在 ticking 范围里。模拟距离通常大于 8 个区块,所以这一步往往最先发生;
3. **等级升过 31**:实体停 tick——掉落物、怪、村民全部冻结(1.21.4 及以前,作物也在这里停长);
4. **升过 32**:红石、流体、漏斗也停了;
5. **升过 33、再到 44 以外**:区块变得不可访问,最终写盘卸载。

所以"远处机器停摆"的本质,是**它的区块等级掉出了 ticking 档,或者它离玩家超过了 128 格**。这不是 bug,是 Minecraft 控制算力的核心手段:只给玩家身边那一小圈区块花 CPU。

要让远处机器**持续运转**,就得给它的区块放一张能压到足够低等级的 ticket,并且想清楚它依不依赖"附近有玩家":

| 手段 | 原理 |
| --- | --- |
| **挂机(AFK)在机器旁** | 玩家这张移动 ticket 把周围一圈压到 entity-ticking,也满足 128 格规则——唯一能让刷怪塔真正运转的办法 |
| **`/forceload`** | ticket 等级 31,指定区块本身就是 entity-ticking;红石、漏斗、熔炉、实体都能跑,但不会自然刷怪 |
| **下界传送门** | 实体穿过传送门时,会在目的地那边放一张持续 300 tick(15 秒)的 ticket(等级 30,让目标传送门周围 3×3 区块进入 entity-ticking),每有实体穿过就重新计时——所以"持续往门里扔东西"成了经典的区块加载器。1.21.5 起这张 ticket 会随存档保存 |
| **飞行中的末影珍珠** | 较新版本里,飞行中的末影珍珠会让所在区块保持加载,也被玩家拿来做加载器 |
| **第三方区块加载器 / mod** | 显式往目标区块写 entity-ticking 级别的 ticket |

> 踩坑:老教程里常见的"把机器建在**出生点区块**"已经过时了。出生点区块曾经被常驻 ticket 钉在 ticking 状态,服务器开着就一直转(哪怕没人在线,也一直吃 CPU)。1.20.5 先用 `spawnChunkRadius` 游戏规则把默认范围从 19×19 缩到 3×3;**1.21.9 干脆把出生点区块整个删掉了**。现在一个维度只有在有玩家、有强制加载的区块、有活跃的传送门或飞行中的末影珍珠时,才会保持运转。

## 五、加载本身也是分阶段、异步的

最后补一层:把区块"拉到某等级"并不是一瞬间的事。区块从无到有要走一条**异步的生成流水线**,每个阶段(`empty → structure_starts → … → features → full`)都可能要等邻居区块先到某阶段才能继续(因为村庄、洞穴这种结构会跨区块)。

这条流水线跑在**后台线程池**上,结果再提交回主线程。所以:

- 你高速移动(骑马、鞘翅、传送)时会看到**地形"长出来"有延迟**——生成流水线没追上你的脚步;
- 一个区块要先被生成到 `full`,才谈得上被 ticket 压到 ticking 档去跑逻辑;那些停在 34–44 档的区块,往往就是还没生成完的半成品;
- ticket 等级管的是"已存在的区块有多活跃",生成流水线管的是"区块怎么从零到 `full`"——两套系统配合,但解决的是不同问题。

---

## 六、串联

把这一篇接回前后:

- **接第 02 篇(生成阶段)**:那条 `empty → … → full` 的 Status 流水线,就是区块"出生"的过程;本篇的 ticket 等级则决定它出生后"活得多积极"。生成是一次性的,等级是动态的。
- **接第 04 篇(Tick 系统)**:上一篇讲的 random tick、scheduled tick、实体 tick、邻居通知,**全都只在等级足够低的区块里发生**。第 04 篇讲"一个 tick 内做什么",本篇讲"哪些区块有资格参与这个 tick"。两篇合起来才是完整的"世界怎么跑起来":Tick 系统是发动机,ticket 等级是油门——它决定发动机的动力分给哪几圈区块。
- **接第 15 篇(刷怪)**:"128 格内要有玩家"这条规则,和刷怪本身的距离、配额规则是一体的,那一篇会展开。

一句话收束本篇:**Minecraft 不会平等地更新整个世界,它只把算力投给加载源照亮的那一小圈,而刷怪这类最贵的逻辑,还要求玩家本人就在附近。理解了 ticket 距离场和这条 128 格规则,你就能解释几乎所有"为什么这台机器在这里转、在那里停"的现象。**

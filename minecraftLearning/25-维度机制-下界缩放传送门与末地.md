# 维度机制:下界缩放、传送门与末地

第 11 篇说过"维度是一个个独立的世界,各自有独立的 chunk 存储"。那一篇是把维度当成容器一笔带过的。这一篇把容器打开,讲清楚三件容易被当成"魔法"的事:**为什么下界走得快、传送门凭什么知道把你送到哪、末地那一堆传送门各自是干嘛的**。

> 一句话先记住:**维度不是"另一张地图",而是一组由 `DimensionType` 描述的环境参数 + 一份独立的世界生成配置 + 一份独立的存档。维度之间唯一的连接是传送,而下界传送门干的活本质上只是"按比例换算坐标 + 在附近找/建一个出口"。**

---

## 一、维度由两层定义:类型(环境)+ 生成(地形)

很多人以为"主世界 / 下界 / 末地"是写死在引擎里的三个东西。1.16 之后**完全不是**——一个维度是数据驱动的,由两块拼出来(呼应第 11 篇动态注册表、第 16 篇世界生成):

| 层 | 注册表 | 管什么 |
| --- | --- | --- |
| **维度类型 DimensionType** | `dimension_type` | 环境参数:高度范围、坐标缩放、有没有天空、天花板、环境光等 |
| **维度本身 LevelStem / dimension** | `dimension` | 把一个 DimensionType 和一套世界生成器(noise settings / biome source)绑在一起 |

也就是说:**环境规则**和**地形怎么长**是分开配置的。你可以写一个 JSON 给"主世界地形 + 下界环境参数"的缝合怪维度,引擎照跑。

### DimensionType 里最关键的几个字段

下面以 1.21.10 及以前的格式为例(主世界的值):

```
{
  "min_y": -64, "height": 384,         // 世界高度范围(主世界 1.18 后)
  "logical_height": 384,               // 传送门落点、紫颂果传送能到的高度上限(下界是 128)
  "coordinate_scale": 1.0,             // 坐标缩放,关键!
  "has_ceiling": false,                // 下界为 true:有基岩天花板
  "has_skylight": true,                // 下界/末地为 false:没有天空光
  "ambient_light": 0.0,                // 环境光底噪,下界 0.1
  "bed_works": true,                   // 下界/末地 false → 床会爆炸
  "respawn_anchor_works": false,       // 下界为 true:能用重生锚
  "ultrawarm": false,                  // 下界 true:水会蒸发、岩浆流得更快更远
  "natural": true                      // 下界/末地 false:指南针、时钟乱转;
                                       //   为 true 时下界门会自己冒出僵尸猪灵
}
```

| 维度 | min_y / height | logical_height | coordinate_scale | skylight | ceiling | ultrawarm |
| --- | --- | --- | --- | --- | --- | --- |
| 主世界 | -64 / 384 | 384 | **1.0** | 有 | 无 | 否 |
| 下界 | 0 / 256 | 128 | **8.0** | 无 | 有(基岩顶) | 是(水蒸发) |
| 末地 | 0 / 256 | 256 | 1.0 | 无 | 无 | 否 |

那个 `coordinate_scale = 8.0` 就是下面一切的根源。

> **版本说明**:1.21.11 起,上面那些"玩法规则"类字段——`ultrawarm`、`bed_works`、`respawn_anchor_works`、`natural`,以及 `piglin_safe`、`has_raids` 等——从维度类型里搬到了新的**环境属性(environment attributes)**里,并且拆得更细:比如 `ultrawarm` 拆成"水会蒸发""岩浆流得快"等几个独立属性,`bed_works` 变成"床规则"。`fixed_time` 改名为 `has_fixed_time`,同时引入了时间线(timelines)。高度、坐标缩放、天空光、天花板、环境光这类"世界形状"字段仍留在维度类型里。思路是把"这个维度的环境规则"拆成一个个可以单独覆盖的属性,而不是全部捆在一张维度类型上。

## 二、下界 8:1:不是"下界更小",是坐标换算

最经典的反直觉点:**主世界走 1 格,等于在下界走 8 格。**

注意它的实现位置——缩放是写在 `DimensionType.coordinate_scale` 上的,**主世界 1.0、下界 8.0**。换算发生在**跨维度传送的那一刻**:

```
进下界:  nether.x = overworld.x / 8     (用两者 scale 的比值 8.0/1.0)
出下界:  overworld.x = nether.x * 8
y 坐标不缩放,直接搬过去(再按目标维度的 logical_height 夹住)
```

所以"下界更小"是个错觉。下界的方块和主世界一样大,只是**它覆盖的主世界范围被压缩了 8 倍**:你在下界铺一条 100 格的冰道,对应主世界 800 格。这就是**下界高速路**的全部原理——拿 1:8 的换算比,在下界跑短途换主世界长途。

```
主世界  A(0,0) ───────── 800 格 ───────── B(800,0)
                  ↕ 传送(/8)              ↕ 传送(/8)
下界    a(0,0) ── 100 格 ── b(100,0)
```

**踩坑:** 正因为是"传送时换算 + 附近找门",1:8 不是精确双射。多个主世界传送门可能落进下界的同一片搜索范围,于是出现"两个主世界门共用一个下界门""回来时出错地方"的经典配对错乱(见下一节)。手工把每对门的坐标按 /8 对齐,才能稳定一对一。

## 三、传送门:一段"换算坐标 + 找门或建门"的算法

站进激活的紫色传送门,生存模式下要等 4 秒(80 tick)才会传送。到点时,服务端做的是一件具体的事(由 `PortalForcer` 负责),逻辑大致是:

```
1. 取实体当前坐标 (x,y,z),按两个维度的 scale 比值换算:
     主世界 → 下界:x、z 除以 8
     下界 → 主世界:x、z 乘以 8
2. 在换算后的目标坐标周围找已存在的下界传送门:
     目标是下界时,水平搜索半径 16 格;目标是主世界时,128 格(1.16 起)
     传送门方块都登记在 POI 里(第 07 篇的 poi/、第 23 篇),所以不用逐格扫描
3. 找到 → 把实体放到离换算坐标最近的那个门,传送结束
4. 没找到 → 在目标坐标附近找一块合适的空间,
   现场用黑曜石 + 传送门方块「凭空建一个新门」,再放人
```

传送完成后,目的地那边还会挂一张持续 15 秒的加载 ticket(第 05 篇),每有实体穿过就重新计时——这就是"传送门区块加载器"的原理。

几个由此推出的真相:

- **门会"配错",是算法的必然而非 bug。** 第 4 步"没找到就新建"意味着:你在主世界建了 A、B 两个门,如果它们 /8 后在下界相距不到 16 格,B 进去时会找到 A 已经建好的下界门 → 出来在错的地方。反方向更容易出错:从下界回主世界时搜索半径是 128 格,附近任何一个主世界门都可能"截胡"。
- **想要稳定的一对一**:自己在下界手动建门,并让它的坐标 ≈ 主世界门坐标 / 8(y 自定),让算法第 2 步"恰好找到你建的那个",就不会乱跳。
- **门是按一组「门框 + 内部传送门方块」识别的**,新建时引擎会找一块能塞下门框的空间,所以有时你会发现下界半空中莫名多出一个带黑曜石平台的门——那是没找到合适地面、就近造出来的。

下界传送门用**黑曜石框 + 打火石点燃**;末地的几种传送结构是另一套(下面讲),机制完全不同。

## 四、末地:三种"门"各管一段路

末地最容易把人绕晕,因为它一口气有三种传送结构,名字都带 portal,但职责完全不同:

| 结构 | 长什么样 | 作用 |
| --- | --- | --- |
| **末地传送门 End Portal**(主世界要塞里) | 12 个末影之眼填满的门框 | 主世界 → 末地主岛,**单向入口** |
| **返回传送门 Exit Portal**(末地主岛中心) | 杀龙后激活的基岩结构,首次杀龙后顶上会放一颗龙蛋 | 末地主岛 → 主世界(你的重生点),**回家** |
| **末地折跃门 End Gateway**(主岛外缘) | 悬空的小型基岩结构,一个发光点 | 主岛 → 外岛(远处),**去刷鞘翅/紫颂果** |

机制要点:

- **主岛和末影龙**:主岛上那圈黑曜石柱是末地生成时就有的地物;第一次有玩家进入末地时,一个叫 `EndDragonFight` 的全局状态对象负责生成末影龙、追踪战斗进度。末影龙是一个**多部件(multipart)实体**——身体由好几个独立的碰撞部件组成,AI 按"阶段(phase)"切换(盘旋、俯冲、栖息在返回传送门上……),呼应第 06 篇。
- **杀龙激活 Exit Portal**:龙死亡触发返回传送门激活,站上去回主世界。**每杀一次龙**,主岛边缘还会多生成一个 End Gateway,最多 20 个。
- **End Gateway 是"定点跳跃"**:折跃门是一个方块实体(第 09 篇),里面记着出口坐标。第一次被使用时,它才在约 1000 格外的外岛区找落点、生成出口并记下来;之后每次踩进去都直接弹射到那里。它和下界门那种"按比例换算 + 搜索"完全不同,是**预设目标的硬传送**。

> 反直觉:末地的"外岛"理论上无限延伸,但主岛和外岛之间隔着约 1000 格的虚空,没有连续地形。最省事的路是折跃门;也可以搭桥、用末影珍珠或鞘翅硬飞过去。所以末地更像"主岛 + 一圈靠 gateway 连接的孤岛群",而不是一张连续大地图。

## 五、维度之间,什么共享、什么不共享

这是理解维度模型的最后一块,也是最容易想当然的地方:

| 东西 | 跨维度? | 说明 |
| --- | --- | --- |
| 玩家背包 / 经验 | ✅ 跟着玩家走 | 玩家实体本身被搬到目标维度 |
| 实体(怪物/掉落物/矿车) | ❌ 各存各的 | 要么自己走进传送门,要么被命令传送;各维度的实体分开存储 |
| chunk / 方块 | ❌ 完全独立 | 各维度独立存储:`DIM-1/`(下界)、`DIM1/`(末地),各自一套 region 文件(呼应第 07 篇) |
| 世界时间 / 天气 | 版本相关 | 1.21.11 及以前,所有维度共用主世界那一份时间和天气,下界、末地只是"看不到"昼夜;26.1 起引入**世界时钟**,末地有了自己的时钟,下界默认不挂时钟 |
| 出生点 / 重生 | 跨维度规则特殊 | 床只在允许睡觉的维度有效;下界用重生锚 |

所以"维度"在存储层就是**几套并列的世界目录**,在运行层是**几套并列的 `ServerLevel`**,各自独立 tick、独立加载区块(第 04/05 篇的那一整套机制,每个维度都跑一份)。1.21.9 起,一个维度只有在有玩家、有强制加载的区块、有活跃的传送门或飞行中的末影珍珠时才会保持运转,没人的维度就整个歇着。它们之间没有共享的方块和区块,**最主要的桥就是把实体从一个 `ServerLevel` 搬到另一个**——传送门、跨维度的 `/tp`,都是这件事的不同触发方式。

---

## 串一下

把这一篇接回前面:维度类型是**数据驱动的环境配置**(第 11 篇动态注册表),1.21.11 起又拆出了更细的环境属性;维度地形复用**第 16 篇的世界生成管线**;各维度**独立 chunk 存储**(第 07 篇)且**各跑一套 tick/加载**(第 04、05 篇);传送门查找靠 **POI**(第 23 篇);末影龙是**复杂实体**(第 06 篇),折跃门是**方块实体**(第 09 篇)。维度本身没有新机制,它只是把前面这些系统**并列实例化几份**,再用"换算坐标 + 找门/建门"这一小段传送逻辑把它们缝起来。

下界跑得快、传送门偶尔配错、末地一堆门——这三件看着神秘的事,拆开都只是 `coordinate_scale`、`PortalForcer` 和几个方块实体的直接后果。

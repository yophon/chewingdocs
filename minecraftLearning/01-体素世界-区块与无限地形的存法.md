# 体素世界、区块与无限地形的存法

你在 Minecraft 里向一个方向一直走,世界永远不会到尽头。你挖穿一座山、填平一个湖,关游戏再回来,改动还在。但你硬盘上的存档可能就几百 MB。一个"无限大、还能记住你每一次改动"的世界,凭什么塞得进这么点空间?

这一篇不讲玩法,先把 Minecraft 世界最底层的三件事讲清楚:**世界是什么数据结构、它怎么被切块管理、以及"无限"到底是怎么做到的**。这三件事理解了,后面所有篇——地形生成、渲染、tick、存储——都是顺着它们往下展开。

> 一句话先记住:**Minecraft 的世界是一个 3D 体素网格,按区块(chunk)切块加载;"无限世界"的真相不是"存了无限多东西",而是"地形能用种子+噪声按需算出来,没去过的地方根本不存在"。去过的区块会整块存盘,再靠共享和压缩把体积压到很小。**

---

## 一、世界的本质:一个 3D 体素网格

先把"方块"这个词从游戏语境里抽出来,看它的数据本质。

Minecraft 的世界是一个三维的**体素(voxel)网格**——你可以理解成三维版的像素。空间被切成一个个 1×1×1 的格子,每个格子坐标 `(x, y, z)` 上,存的是"这一格是什么方块"。

```
体素网格 = 三维数组,每个格子存一个方块

       y (高度)
       │
       │   ┌──┬──┬──┐
       │  ╱  ╱  ╱  ╱│
       │ ┌──┬──┬──┐ │
       │ │石│石│空│ ┤   每个小立方体 = 一个 voxel
       │ ├──┼──┼──┤╱    存的不是模型,是"方块种类 + 状态"
       │ │土│土│水│
       └─┴──┴──┴──┴──── x
        ╱
       z
```

每一格存的不是一个 3D 模型,而是一个**轻量的标识**:方块种类(ID)+ 一些状态(朝向、是否含水、生长阶段……)。这一点至关重要——正因为单格的数据极小,海量方块才有可能被压缩存储。后续篇会讲到,这个"种类 + 状态"在引擎里叫 BlockState,千万个石头其实共享同一个状态对象,格子里只存一个指向它的下标。

### 为什么不能把方块当模型来渲染

新手最容易有的误解是:"每个方块是一个立方体模型,渲染就是把它们一个个画出来。"

算一笔账就知道这条路走不通:

- 一个区块底面 16×16,世界高度 384,就是 `16 × 16 × 384 ≈ 9.8 万`个方块。
- 玩家视野范围动辄几十个区块,**视野内轻松上千万、上亿个方块**。
- 每个立方体 6 个面、12 个三角形——逐方块提交,几十亿个三角形,任何显卡当场跪下。

```
朴素想法:N 个方块 → N 个立方体模型 → 几十亿三角形 → 炸显卡
现实做法:见 03 篇——只画"暴露在空气里的面",一个区块合并成一个网格
```

所以**体素世界的渲染绝不是"逐方块画"**。怎么把上亿方块压成显卡扛得住的几何体,是 `03 区块渲染` 专门要解决的问题。这里只需要记住一个结论:**方块的存储表示(数据)和渲染表示(几何)是两回事**,中间隔着一层专门的优化。

## 二、区块(Chunk):世界的管理单位

世界这么大,引擎不可能把它整个塞进内存。于是它被切成**区块(chunk)**——这是 Minecraft 里加载、生成、tick、存盘的基本单位。

### 区块的尺寸

```
1 个 Chunk = 16 (x) × 16 (z) × 整个世界高度 (y)

           ┌────────────────┐  ← 世界顶 (y=320, 1.18+)
           │                │
           │   一个 Chunk    │     底面 16×16
           │   竖直的一根     │     高度 384(从 y=-64 到 y=320)
           │   "柱子"        │
           │                │
           └────────────────┘  ← 世界底 (y=-64, 1.18+)
```

- **底面固定 16×16**,这是历史以来没变过的。
- **高度**:1.18 之前是 256(y=0~255),1.18 起主世界扩展到 **384**(y=-64 ~ 319),所以能挖更深、山能更高。下界和末地仍是 256 高(y=0~255)——高度由维度类型决定,见第 25 篇。

### 再切一刀:Section(16³ 子区块)

一根 384 高的柱子还是太大,不好按需处理。所以区块在竖直方向再切成一段段 **16×16×16 的 Section**:

```
Chunk (16 × 16 × 384)
  = 24 个 Section 竖直叠起来

  Section 23   y=304~319
  Section 22   y=288~303
     ...
  Section  0   y=-64~-49
  每个 Section = 16³ = 4096 个方块
```

Section 才是真正的"工作粒度":存储用它(每个 Section 一张方块调色板)、光照按它算、网格按它重建。一个全是空气或全是石头的 Section 可以被极度压缩甚至省略——这点在 `08 存储` 篇会展开。

### 只加载你身边的区块

引擎只把**玩家附近的区块**加载进内存。你走动时,前方的区块被加载/生成,身后远处的区块被卸载、存盘。

```
       ▒▒▒▒▒▒▒▒▒▒▒          ▒ = 已卸载(不在内存)
       ▒░░░░░░░░░▒          ░ = 已加载(在内存,但外圈不更新)
       ▒░░░░░░░░░▒          █ = 玩家所在,完整运行
       ▒░░░░█░░░░▒
       ▒░░░░░░░░░▒          你往右走 →
       ▒░░░░░░░░░▒          右边新区块加载,左边旧区块卸载存盘
       ▒▒▒▒▒▒▒▒▒▒▒
```

注意"加载"也不是非黑即白:区块有不同的活跃等级,有的完整 tick,有的只是加载着但几乎不更新。这套"区块加载等级"决定了远处的农场会不会停摆,是 `05 区块的生命` 的主题。这里先建立一个印象:**任意时刻活在内存里的,只是整个无限世界里你周围一小圈。**

## 三、"无限世界"的真相:没去过的地方根本不存在

现在回到开头那个问题:一个无限大的世界,怎么可能存得下?

答案是——**它从来不是一个"预先造好的无限世界",而是一个"走到哪、生成到哪"的世界**。

### 地形是算出来的:确定性生成

Minecraft 的地形由**程序化生成**:用一组**噪声函数**,输入坐标,输出"这里该是什么"。关键性质是**确定性**:

> 同一个**种子(seed)** + 同一个**坐标** + 同一版本的生成算法,输出永远相同。

确定性带来两个直接后果:

- **世界不需要提前造好。** 你没去过的地方,在磁盘上**根本不存在**,走近时才被生成出来。世界理论上无限,实际只为你到过的那一圈付出代价。
- **世界可以被"分享"。** 把种子发给朋友,他在同一版本下能生成出和你一模一样的原始地形。

```
传统思路:世界 = 一份预先造好的巨大地形数据   → 无限世界 = 无限存储 ❌

Minecraft:世界 = 种子(几个字节) + 确定性生成算法
          某坐标的地形 = f(种子, 坐标)   ← 第一次走到时才求值 ✅
```

### 生成之后:整块写盘,而不是"只存差异"

这里有一个流传很广的误解:"没改过的区块不用存,下次用种子重算一遍就行,只有改过的地方才落盘。"——**Java 版不是这样做的。**

```
某个区块第一次被需要
   │
   ├─ 磁盘上已经有它 → 直接从 region 文件读出来,不再生成
   │
   └─ 磁盘上没有     → 按种子跑一遍生成流水线
                        → 生成出的区块(哪怕你一格都没动)进入内存
                        → 卸载 / 自动保存时,整块写进 region 文件
```

一个区块一旦生成,就会被**完整保存**——包括你从没碰过的每一块石头。原因很实际:

- **重算不便宜**:生成一个区块要走一长串阶段(第 02 篇),远比从磁盘读出来再解压慢。
- **重算不等价**:生成时会顺带刷出动物、放下战利品箱、定下结构布局;而且游戏一升级、生成算法一变,"重算"出来的就不再是原来那块地了(第 02 篇讲的"新旧地形断层带"正是这么来的)。

所以存档大小**正比于你探索过(也就是生成过)的范围**,跟你改没改过关系不大。这也解释了两个常见现象:开着鞘翅一路飞,存档会飞快膨胀;MCA Selector 这类工具最常见的用途,就是按"玩家在区块里停留过多久"把那些路过一下、从没待过的区块删掉瘦身。

那几百 MB 怎么装得下几十万个区块?靠的是另外两招:**能共享的不复制**——千万个石头共享同一个 BlockState,格子里只存一个小下标(第 09 篇);以及**必须存的压到最小**——局部调色板、位压缩、区域文件打包(第 07/08 篇)。一个以石头和空气为主的区块,压缩后往往只有几 KB。

### 这是贯穿全系列的一组招式

请记住这个思路,因为它不止用在地形上,而是**整个 Minecraft 引擎反复使用的核心招式**:

> **没去过的不生成,能共享的不复制,必须存的压到最小。**

| 场景 | 这一招的体现 | 哪一篇细讲 |
| --- | --- | --- |
| 无限地形 | 确定性生成,走到哪生成到哪,没去过的地方零成本 | `01`(本篇)/ `02` |
| 方块状态 | 千万个石头共享一个状态对象,格子只存下标 | `09` |
| 区块存储 | 局部调色板 + 位压缩;均质 section 压到近乎为零;1024 个区块打包进一个文件 | `07` / `08` |
| 内存与磁盘 | 两边都是"调色板 + 紧凑位数组",加载时的转换很便宜 | `03` / `08` |

整个系列你都会一次次看到它们。Minecraft 的"省"和"快",大半来自这三句话。

## 四、踩坑与反直觉

把这一篇容易误解的点单独拎出来:

- **"方块是一个个模型"——错。** 方块在数据层是"种类+状态"的轻量标识,在渲染层会被合并成大网格。把它想成模型,你既理解不了存储压缩,也理解不了渲染优化。

- **"世界是一个大数组全在内存里"——错。** 内存里只有你周围一圈区块,而且这一圈还分不同活跃等级。绝大部分世界要么在磁盘上(去过的),要么压根不存在(没去过的)。

- **"无限世界 = 无限存储"——错。** 无限的是"可生成空间",不是"已存储数据"。没探索的地方零成本,因为它只是种子函数的一个还没被求值的输入。

- **"没改过的区块不存盘,反正能重算"——错。** 生成过的区块会整块存下来,重算既慢又不等价。确定性生成省掉的是"还没去过的地方",不是"去过但没改过的地方"。

- **"种子只是个随机数好玩而已"——低估了。** 种子是整个世界确定性的根。同种子同版本,原始地形可完全复现——这正是种子分享、地形预览工具能存在的原因。

- **反直觉的一致性要求:** 区块是一块块、在不同时间生成的——今天生成了 A,下周你才走到它隔壁、生成 B。所以生成算法**必须严格确定、且跨区块边界自洽**,否则 A 和 B 的交界就会"撕裂"。这也是为什么地形生成不能简单地"每个区块各算各的",得有跨区块协调——细节见 `02 地形生成`。

## 五、串联

这一篇搭好了地基,三条线从这里岔出去:

- **世界怎么"长出来"** → `02 地形生成` 讲种子和噪声函数到底怎么把坐标变成山川洞穴、怎么保证跨区块自洽。
- **世界怎么"画出来"** → `03 区块渲染` 接着第一节那个"不能逐方块画"的坑,讲怎么只画可见面、把一个区块合并成一次绘制。
- **区块怎么"存下来"** → `07 / 08 存储` 把第三节的"整块存盘、压到最小"落到 Region 文件和 NBT/调色板的字节布局上。

而本篇反复强调的那组招式——**没去过的不生成,能共享的不复制,必须存的压到最小**——会是你读完整个系列后,对 Minecraft 工程设计最该记住的东西。

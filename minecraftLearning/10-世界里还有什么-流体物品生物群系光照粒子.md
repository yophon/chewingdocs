# 世界里还有什么:流体、物品、生物群系、光照、粒子

讲完方块、方块实体、实体,大多数人会觉得"世界的构成讲完了"。其实没有。如果你把一个坐标剖开看,会发现上面叠着的东西远不止"一个方块"。这一篇要补上那些**和方块平行存在、却容易被忽略**的对象与数据层。

它们不属于前三类,但每一类都实打实地占着坐标、影响着世界的行为。漏掉它们,你对"世界由什么构成"的理解就是残缺的。

> 一句话先记住:**同一个坐标 (x, y, z) 上,不是只能读出"一个方块",而是能读出方块、流体、两种光照好几层信息;此外还有生物群系给区域贴标签、物品寄生在容器里、粒子只活在客户端。** 方块只是这叠信息里最显眼的一层。

---

## 一、流体 FluidState:从方块状态里"读"出来的第二视角

这是最容易被误解的一类。很多人以为每一格同时存着一个方块和一份独立的流体数据,其实不是:

> **区块里只存 BlockState。FluidState 是从 BlockState 推出来的**——代码里就是 `blockState.getFluidState()`,每个 BlockState 在启动时就算好了自己对应哪种流体状态。

- 对绝大多数方块,FluidState 是"空"(`Fluids.EMPTY`)。
- 水方块、岩浆方块:FluidState 对应它们的流体和水量。
- 带 `waterlogged=true` 的方块(含水楼梯、含水栅栏……):FluidState 是**水源**。

也就是说,方块和流体在存储上是**一份数据、两种读法**;但在行为上是**两套逻辑**——方块管碰撞、外形、掉落,流体管流动、推动实体、淹没。

### 含水机制:一个布尔属性,两套行为

你能给楼梯、栅栏、台阶"灌水",底层是这样的:

```
坐标 (10, 64, 20)
├── 存下来的:BlockState = oak_stairs[facing=east, half=bottom, waterlogged=true]
└── 读出来的:getFluidState() → 水源(water,source)
```

**方块仍然是楼梯**(碰撞、外形、掉落都按楼梯走),流体系统从 `waterlogged=true` 读出"这里有一格水源",于是这格也会往外流水、能淹没实体。由此直接推出一个现象:**含水方块里只能装水源,不能装流动水,也不能装岩浆**——因为 `waterlogged` 只是一个布尔值,存不下"流到第几格"或"是哪种流体"。

### 独立的 tick 队列

回忆存储那一篇里 chunk NBT 同时存了 `block_ticks` 和 `fluid_ticks` —— 它们是**两个独立队列**,不是一个。流体的扩散、衰减全在自己的队列里跑。

讲流动之前,先说清一个最容易绕晕的数字约定。水的"等级"有两套写法,方向正好相反:

| 写法 | 水源 | 流动水 | 用在哪 |
| --- | --- | --- | --- |
| 方块属性 `level`(`water[level=…]`) | 0 | 1–7,**离源越远数字越大**;8 及以上表示正在下落的水 | 方块状态、命令、wiki |
| FluidState 的"水量" amount | 8 | 7→1,**离源越远数字越小** | 流体代码内部 |

本系列统一用第一种(第 04 篇也是)。流动规则:

| 概念 | 含义 |
| --- | --- |
| 衰减 | 水平每流一格 `level` +1,到 7 就不再往外铺;竖直下落不衰减 |
| 找洞 | 流动前会探测附近能向下掉的方向,优先朝坑铺 |
| 无限水 | 一格流动水如果两侧各挨着一个水源、且下方是实心方块或水源,会变成新的水源 |

所以你看到的"水慢慢铺开",本质是流体在它自己的 tick 队列里**一圈一圈扩散衰减**,跟方块的 random tick 完全是两套机制。

### 踩坑 / 反直觉

- **流体曾经就是方块**:1.13("扁平化")之前,水只是普通方块,所以那时做不了含水栅栏。1.13 引入了 FluidState 这套"从方块状态读出流体"的抽象,再给可含水方块加上 `waterlogged` 属性,含水机制才成为可能。这是一次典型的"不改存储、只加一层抽象"的重构:存档里依然只有方块状态。
- **挖掉含水楼梯**:破坏方块时,游戏会把这一格设成"它原来那份流体对应的方块"——含水楼梯的流体是水源,于是原地变成一格水。这就是为什么破坏含水方块后会留下水。

## 二、物品 ItemStack:寄生在容器里的纯数据

物品是和方块**地位相当**的一大类,只是它**不直接待在世界格子里**,而是住在"容器"里。

- 容器 = 背包、箱子(方块实体)、漏斗、玩家手上……
- 一个 **ItemStack** = 物品种类 + 数量 + 一组组件(耐久、附魔、自定义名等)。1.20.5 后这些附加信息从旧的 NBT `tag` 迁移成了"数据组件"。

```
ItemStack
├── item   : minecraft:diamond_sword   (种类,注册表里的类型)
├── count  : 1
└── components
    ├── damage      : 12
    ├── enchantments: { sharpness: 5 }
    └── custom_name : "断钢"
```

### 寄生型类别

物品自身是纯数据,**必须依附在某个宿主里才能存在**:

```
在箱子里 ─► 挂在箱子的方块实体的 Items 列表下
在背包里 ─► 挂在玩家实体数据下
扔到地上 ─► 被一个 ItemEntity(实体)"装着"进入世界,有了坐标和速度
```

最后一种最能说明问题:**同一份剑的数据,在箱子里时挂在方块实体下,扔出去时原样搬进一个实体里**。物品本身没变,变的是"谁在容纳它"。这也是物品和方块、实体三者通过同一套序列化(NBT/组件)互相衔接的缩影。

## 三、生物群系 Biome:坐标上的"气候标签"

生物群系也绑定到坐标,但和方块很不一样。

- **粒度粗**:不是每格一个,而是 **4×4×4 一格**(1.15 起)。一个 16³ 的 section 只有 `4×4×4 = 64` 个生物群系格,同样用 palette 压缩(和方块状态用的是同一套调色板思路,只是每个方向的分辨率低 4 倍)。26.4 的快照正在把它改成逐方块存储,尚未进入正式版。
- **它不"占地方"**,而是给一片区域贴一个标签,决定:

| 影响 | 例子 |
| --- | --- |
| 气候 | 温度、湿度、是否下雪/下雨 |
| 刷怪 | 这片区域刷什么怪、刷不刷 |
| 染色 | 草、树叶、水的**颜色**(同样的草方块在沼泽和平原是不同绿) |
| 地物 | 生成什么植被、结构、矿物分布倾向 |

### 反直觉

你**挖不到、也撞不上**"生物群系"。它是一层无处不在的数据,而非可交互的对象 —— 这是它和"看起来也铺满世界"的方块最根本的区别:方块是实体化的格子内容,生物群系是贴在格子上的元数据。

## 四、光照 Light:逐格的数值场

光照是又一个**逐格存在、绑定坐标、要进 chunk** 的数据层,但它不是"东西",而是一个 0–15 的**数值场**。

关键:光有**两个独立通道**。

```
坐标 (x, y, z)
├── BlockLight : 0–15   ← 火把/岩浆/萤石等"光源"发出的光
└── SkyLight   : 0–15   ← 天空照下来的光(遇到遮挡后逐格衰减)
```

- 存储:每格 **4 bit**,按 section 存成 `BlockLight` / `SkyLight` 两个 Byte_Array(存储那一篇见过)。两个通道分开存,是因为来源和传播规则不同:方块光从光源向四周逐格衰减;天空光从天空往下照,在露天的竖直方向上**不衰减**(一路 15 照到底),碰到遮挡、拐进洞里才开始逐格减弱。
- **存下来的天空光不随昼夜变化。** 正午和半夜,露天格子里存的都是 15。你看到的天黑,是渲染时用 lightmap 把天空光整体调暗(第 20 篇);刷怪这类逻辑则另算一个随时间变化的"天空变暗"量去修正它(第 15 篇)。这样太阳落山时不必改写全世界每一格的光照值。
- **传播靠洪水填充(flood-fill)**:放下一支火把,光以"每跨一格 -1"的方式向四周扩散;挖掉一格不透明方块,光要重新灌进新腾出的空间。

### 踩坑:光照是著名性能热点

这套"光照引擎"在方块频繁变动时要做大量的重新传播,历史上是 Minecraft 的卡顿大户 —— Starlight、Phosphor 这类著名 mod 专门重写它来优化。原因正是 flood-fill 的级联:改一格可能引发一大片光值重算,和红石的更新风暴是同类问题。1.20 原版重写了光照引擎,性能大幅改善,Starlight 也因此停止了对新版本的跟进(第 19 篇)。

## 五、粒子 Particle:纯客户端的"视觉幽灵"

火焰、烟、药水雾、爆炸碎屑这些:

- **只存在于客户端**:服务端不存、不 tick,存盘里完全没有它们。
- **没有逻辑、不可交互**:纯渲染效果。
- 它和实体长得像(有坐标、会动),但**完全是另一类东西**。

这解释了几个现象:粒子从不影响游戏结果;多人游戏里别人看到的粒子可能和你不完全一样(因为各自客户端独立生成);把画质调低关掉粒子,玩法毫发无损。

> 严格说粒子不算"世界数据",它是渲染层的产物。但既然在讨论"世界里还有什么",必须点明它的存在,以及它和实体的界线 —— **能存盘、能影响逻辑的才是世界对象,粒子两样都不是。**

---

## 六、声音 SoundEvent:粒子的"听觉版"

粒子是纯客户端的视觉幽灵,声音几乎是它的镜像——**纯客户端的听觉表现层**。

- 和粒子一样:基本只活在客户端,**触发即播放、不存盘、不参与任何世界状态**。挖方块、走路、怪叫,服务端广播一个"在这个坐标播这个音效"的事件,各客户端自己去放,放完就没了。
- `SoundEvent` 是注册表里的一个类型(和方块、物品一样上户口,呼应注册表那一篇)。它本身只是个 ID(如 `minecraft:block.stone.break`);客户端拿到这个 ID,按资源包里的 `sounds.json` 查到实际的音频文件去播放。换皮资源包能改音效,就是改这张映射表。
- 有坐标、会**随距离衰减、声像偏移**(左右声道),但这些都只是给玩家听的——对世界逻辑零影响。

### 和"游戏事件 GameEvent / 振动"要分清

这两个最容易混,因为同一个动作往往**两者都发**:

| | SoundEvent | GameEvent / 振动 |
| --- | --- | --- |
| 给谁 | 给玩家**听** | 给**幽匿感测体 / 监守者**监听 |
| 属于 | 纯表现层 | 玩法层的瞬时信号 |
| 影响世界 | 否 | **是**(触发红石、招怪) |
| 存盘 | 否 | 否(瞬时) |

举例:你放一个方块,服务端既播一个 `SoundEvent`(让你听见"咚"),又发一个 `GameEvent`(让附近幽匿感测体能"感觉到"你动了)。前者纯装饰,后者是会被玩法机制消费的真信号。**潜行能消除振动(GameEvent)却消不掉某些声音**,正是因为它们是两套独立的东西。

所以:**声音 + 粒子共同构成"纯表现层"**——都有坐标、都会传播衰减,但都不存盘、都对世界逻辑毫无影响。它们是世界"长什么样、听起来怎样"的产物,而不是世界"是什么"的一部分。

## 七、把一格剖开:多层叠加

把前面几层合起来看,一个坐标的真实构成是这样的:

```
坐标 (x, y, z) ───────────────────────────────
  ├── BlockState   方块状态(网格,可共享,palette)          ← 存
  │     └→ FluidState  流体状态(从 BlockState 读出,独立 tick 队列) ← 不单独存
  ├── BlockLight   光源光照(0–15,4 bit)                    ← 存
  ├── SkyLight     天空光照(0–15,4 bit)                    ← 存
  └──(可能)BlockEntity   少数方块的附加数据/渲染            ← 存

区域级(4×4×4 一格):
  └── Biome        气候/染色/刷怪标签

不在格子里:
  ├── ItemStack    寄生在容器/实体中的物品数据
  └── Particle     纯客户端视觉,不占数据
```

**最反直觉、也最关键的一点**:一格上能读出方块、流体、两种光照好几层信息,它们各自按自己的规则更新;其中方块和两种光照是分开存的,流体则是从方块状态读出来的。"一格 = 一个方块"是新手最容易先入为主、却最该被打破的错觉。

## 串联

- 承接方块三层那一篇:方块、方块实体是"格子内容"和它的附加;这一篇补的流体是**从方块状态读出的另一种视角**,光照是**叠在同一格上的另一层数据**,生物群系是**贴在格子上的标签**,物品是**寄生在容器里的数据**。合起来,"世界里的对象类别"才算齐。
- 呼应存储那一篇:chunk NBT 里的 `biomes`(4×4×4 palette)、`BlockLight`/`SkyLight`(Byte_Array)、`fluid_ticks`(独立队列)正是这一篇这些数据层的落盘形态 —— 你在磁盘上看到的字段,对应的就是这里讲的运行时分层。
- 指向注册表那一篇:这里每一类的**类型**(每种流体、每种物品、每种生物群系)同样登记在注册表里;生物群系更是"数据驱动的动态注册表"的典型,留到下一篇展开。

这一篇之后,世界里主要的对象和数据层就都见过了:方块、流体、方块实体、实体、物品、生物群系、光照,外加不算世界数据的粒子和声音。再往上,就是把这一切**类型**装起来的元系统了。

# 前半程总图:分层架构与一个方块的生命周期

前面十一篇,我们从体素世界一路拆到注册表:地形怎么算出来、区块怎么画、20 TPS 怎么驱动世界、数据怎么存盘、方块和实体和流体到底是什么、最后一切类型怎么登记在注册表里。知识点很多,但如果只是记住一堆零散名词,过几天就忘了。

这一篇不引入任何新机制,只做一件事:**把前三层(第 01–11 篇)缝成一张图,再让一个方块在这张图上"活一遍"**。当你能闭着眼睛画出这张分层图、能讲清一格石头从生成到存盘再到加载走了哪些层,你就理解了 Minecraft 世界的骨架,而不只是背下了它的零件。

先说清这张图的范围:它画的是**世界本身**——服务端那一侧的数据模型、运行循环和存储。世界怎么到达玩家(网络、渲染管线、资源包),以及建在它上面的玩法与扩展(红石、刷怪、指令、AI、mod、维度),在第 13–25 篇展开;第 26 篇再把它们和这张图合成全系列总图。所以这一篇是"中场的地图",不是终点。

> 一句话先记住:**Minecraft 的世界是"同一格上能读出好几层信息 + 一根注册表主轴穿透所有层";理解它的关键不是数清有多少种东西,而是看清每种东西活在哪一层、以及一格数据怎么在这些层之间流动。**

---

## 一、先立一条正交轴:类型 vs 实例

在画总图之前,必须先讲清一条**横切所有层**的轴,否则总图会看不懂。

前面我们反复遇到一个现象:几乎每种"东西"都分成**两层**。

| 类型层(单例,定义行为,在注册表里) | 世界里的那一份(逐格 / 逐个) |
| --- | --- |
| `Block`(石头这"类") | 每格的 BlockState(本身是共享对象,格子里只存指向它的调色板下标) |
| `Item`(钻石剑这"类") | `ItemStack`(你背包里这一把) |
| `EntityType`(僵尸这"类") | `Entity`(刷出来的那只僵尸) |
| `BlockEntityType`(箱子这"类") | `BlockEntity`(这个坐标的箱子) |
| `Fluid`(水这"类") | `FluidState`(从这格的 BlockState 读出来,不单独存) |

左列是游戏启动时就固定下来的"模板",像面向对象里的"类",全游戏每种只有一个实例,登记在注册表里。右列是世界里那一份具体的东西。

其中 BlockState 和 FluidState 比较特殊:它们处在两层之间——种类有限、全局共享,更像"枚举值";世界里逐格存的只是指向 BlockState 的小下标,FluidState 则连下标都不存,直接从 BlockState 推出来。而 ItemStack、Entity、BlockEntity 才是真正逐个存在、各带一份数据、要单独序列化的对象。

**为什么这条轴重要?** 因为它解释了 Minecraft 最核心的省法:

- 千万个石头方块,共享**同一个** `Block` 单例和同一个 BlockState 对象,世界里每格只存一个"调色板下标"。
- 一种方块的所有行为(硬度、碰撞、掉落、tick 逻辑)只写一份,挂在类型层。

这条轴是**正交的**——它不是"另一类东西",而是看待每一类东西的两个视角。后面总图里几乎每个名词,你都要意识到它同时活在这两层上。

## 二、一个反直觉的事实:一格上能读出好几层

新手脑子里的世界是"每个格子里放一个方块",一格 = 一个东西。**这不完整。** 同一个坐标上,能读出好几层彼此半独立的信息:

```
坐标 (x, y, z) 上能读出:
├── BlockState    方块状态(楼梯、朝向、含水标记)   → 存在 section 的调色板里
│     └→ FluidState  流体状态(有没有水、水量)    → 从 BlockState 读出,不单独存
├── Light         光照(BlockLight + SkyLight)     → 两个通道各 0–15,单独存
├── (BlockEntity) 少数方块才有的 NBT 附加/渲染锚  → 单独存在 block_entities 里
└── Biome         4×4×4 粒度的气候标签            → section 里单独一张小调色板
```

这正是**含水机制(waterlogging)** 能存在的原因:一个被水淹的楼梯,存下来的只有一个 BlockState——`oak_stairs[…, waterlogged=true]`;流体系统从这个 `true` 读出"这里有一格水源",于是它既按楼梯碰撞,又按水流动。

记住这一点,你才不会被"水到底算不算方块"这种问题绕住:在存储上,水就是方块状态(水方块,或别的方块的 `waterlogged=true`);在行为上,流体系统把它读出来,按自己的规则流动、按自己的队列 tick。

## 三、对象有限,系统开放

读到这里,很容易一直追问"还有没有别的类别"。其实"类别"这个词指的是两种性质不同的东西,分开就清楚了:

- **世界里的对象和数据层**是一个**有限集合**,前十篇基本讲全了:方块、流体、方块实体、实体、物品、生物群系、光照,外加纯客户端的粒子和声音。
- **让世界运转的系统**是**开放的**:第 11 篇讲的修饰层、运行时信号、交互会话、注册表与标签、维度 / 存档 / 数据包,还能继续往下拆——碰撞形状、AI、结构生成、命令……这正是后半程要做的事。

分清这两类,读后面的篇章时就知道每个新概念该往图里哪一层放。

## 五、如何读这张图

这张图不是用来背的,是用来"定位"的。三条读法:

**纵向:从"存"到"动"再到"交互"。** 下层(6/7)回答"静态的数据怎么躺在硬盘上",中层(5)回答"它怎么被驱动起来",上层(1-4)回答"动起来之后世界里有哪些东西、哪些状态、哪些交互"。任何一个游戏现象,你都能在某一层找到它的落点。

**横向:注册表是穿透所有层的主轴。** 每一层的"类型"都来自第 0 层;内存里的全局调色板、网络包里的数字 ID、存盘时的方块名、跨版本的 DataFixerUpper 迁移,全都绕着注册表转。理解了它,前面零散的点就被一根线串起来了。

**一格能读出多层。** 这是最反直觉、也最关键的一点(第二节讲过):同一坐标上能读出 BlockState、FluidState、Light,可能还挂一个 BlockEntity。别再把世界想成"每格一个东西"。

还有那条**正交轴**别忘了:图里几乎每个名词,都同时活在"注册表里的单例模板"和"世界里的那一份"两层上。

## 六、一个 16³ Section 的生命周期

光有静态分层还不够。真正把所有层缝起来的,是数据**流动**的过程。下面让一个 16×16×16 的 section(以及里面的一格方块)从出生到重新加载,在这张图上走一遍。

```
                  一个 16³ Section 的一生
═══════════════════════════════════════════════════════════════

① 生成(第 0/1/6 层:噪声 → PalettedContainer)
   磁盘上还没有这个区块 → 世界生成器按 种子+坐标 逐阶段计算
   → 决定每格是空气/石头/矿石…
   → 写入内存中的 PalettedContainer:
        palette = [air, stone]          ← 局部调色板
        data    = bit-packed long 数组   ← 每格只存调色板下标
   注:此刻硬盘上还没有它,但它已被标记为"未保存"——迟早会写盘(见③)
        │
        ▼
② 运行(第 5 层 Tick 系统 驱动 第 1 层 数据)
   区块等级 ≤ 32(block ticking):
     · scheduled tick 队列 → 水流逐圈扩散、红石中继延迟
     · setBlock + 邻居通知 → 红石级联、沙子下落、活塞响应
   区块等级 ≤ 31(entity ticking):
     · random tick 抽样   → 抽到作物/草 → 生长,改写 PalettedContainer
                            (1.21.4 及以前还要求 128 格内有玩家)
     · 自然刷怪           → 另需 128 格内有玩家(第 05、15 篇)
   每次方块变化:
     · 调色板可能新增种类(放下一块从未出现的方块)
     · 种类超出当前位宽的容量 → bitsPerEntry 增大,long 数组重新打包
     · 种类变少时不会立刻缩回去,闲置的调色板项等下次存盘时才被清掉
        │
        ▼
③ 卸载 或 自动保存(第 1 层 → 第 6 层:序列化下盘)
   触发:周期性自动保存 / 区块卸载 / 关服
   条件:区块是新生成的,或加载后发生过变化
         (从磁盘读出后原封未动的区块不必重写)
     · 按实际内容重新整理局部调色板,连同位数组写成 block_states:
          { palette: [方块名+属性 …], data: long 数组 }
     · 连同 block_entities、未结算的 block_ticks/fluid_ticks、
       Heightmaps、biomes、光照、Status、DataVersion → 打包成该 chunk 的 NBT 树
     · NBT 树 → zlib 压缩
     · 在 .mca 里找一段连续空闲扇区写入(按 4KB 对齐)
     · 更新文件头的 location table(偏移+扇区数)与 timestamp table
        │
        ▼
④ 再加载(第 6 层 → 第 1 层:反向走一遍)
   玩家走回来:
     · 查 location table → 得到扇区偏移与长度
     · seek 到扇区 → 读出 → 看压缩类型字节 → 解压
     · 解析 NBT 树(数据版本旧的话,先经 DataFixerUpper 升级,第 17 篇)
     · 调色板里的方块名查注册表还原成 BlockState,配上 long 数组重建 PalettedContainer
     · 不会重新跑生成——磁盘上有,就以磁盘为准
   回到 ②,继续被 tick 驱动
```

注意两个细节:

- **①→③ 这条路**:一个 section 哪怕从生成到卸载一格都没变,也会被写盘。"没改过就不存"是误解,生成过就会存。
- **③④ 的转换很便宜**:内存里的 PalettedContainer 和磁盘上的 `block_states` 是同一个思路——都是"局部调色板 + 紧凑位数组"。所以保存和加载只需做少量转换(整理调色板、名字和对象互查),不需要把 4096 个方块逐个展开。这不是巧合,是刻意的设计。

## 七、收尾:三招贯穿始终

如果前半程只让你记住一句话,那就是这组贯穿前十二篇的招式:

> **没去过的不生成,能共享的不复制,必须存的压到最小。**

回头看,Minecraft 世界几乎所有的"省"和"快",都是这三招的不同变体:

- **没去过的不生成**:无限地形靠种子 + 噪声确定性地按需生成(第 01/02 篇);战利品箱在打开前只存"战利品表 + 种子",物品现场生成(第 09 篇)。
- **能共享的不复制**:千万个石头共享一个 BlockState,世界里每格只存调色板下标(第 09 篇);FluidState 直接从方块状态读出,不另存一份(第 10 篇);注册表让每种类型只有一个单例(第 11 篇)。
- **必须存的压到最小**:局部调色板 + 位压缩,单值 section 连数组都省掉(第 08 篇);1024 个区块打包进一个扇区对齐的 region 文件(第 07 篇);内存与磁盘结构相近,加载转换便宜(第 03/08 篇)。

后半程你会看到同样的招式在别处反复出现:物品的"默认组件 + 只存差异"(第 17 篇)、模型靠旋转和父模型复用(第 22 篇)、网络只发增量(第 13 篇)。

把这组招式和这张分层图一起记住,你看 Minecraft 就不再是"一堆方块的游戏",而是一个**把按需生成、数据共享和紧凑存储做到极致的体素引擎**。你在游戏里观察到的很多现象——麦子参差成熟、远处机器停摆、含水的楼梯、打不开的箱子——都能在这张图上找到它的层、找到它的因。

下一层开始,我们把镜头从服务端的世界移向玩家:世界怎么经过网络、渲染管线和资源包,变成你屏幕上的画面。

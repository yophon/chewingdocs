# 扩展机制选型

写到这里,这个系列已经讲了十几种扩展 Claude 的方式:CLAUDE.md、rules、output style、skills、hooks、子 agent、dynamic workflows、MCP、plugins、mods、权限和沙箱,再往外还有 Messages API、Agent SDK、Managed Agents,以及自己写 MCP server。每一种单独看都不难,难的是面对一个具体需求时选对。选错的代价往往不是"不能用",而是**看起来能用、其实不可靠**:把安全要求写进 CLAUDE.md,把一份几千行的手册塞进每次请求,为一个 `gh` 命令就能完成的事写一个 MCP server。

这一篇把它们放在一起比较,给出一套从需求出发的选型方法。

> 一句话先记住:**先问三个问题**——这件事是必须每次都发生,还是让 Claude 判断?需要的是知识,还是能力?作用在谁身上:我自己、这个仓库、整个团队,还是产品的用户?三个答案基本就决定了用哪种机制。

---

## 一、两类场景

| 场景 | 你在做什么 | 用到的机制 |
| --- | --- | --- |
| **定制 Claude Code** | 让自己和团队用 Claude Code 时更顺手、更可控 | CLAUDE.md、rules、output style、skills、子 agent、workflows、hooks、MCP、plugins、mods、权限 |
| **基于 Claude 构建** | 做一个给别人用的东西:自动化流程、内部工具、产品功能 | Messages API、Agent SDK、Managed Agents,以及作为共享能力层的 MCP server |

两类可以共存:同一个团队里,开发者用 Claude Code 写代码,CI 里跑 Agent SDK 做审查,客服后台调 Managed Agents——而它们背后接的是同一组 MCP server。

## 二、Claude Code 里的机制一览

| 机制 | 解决什么 | 什么时候加载 | 上下文成本 | 是强制还是建议 | 篇 |
| --- | --- | --- | --- | --- | --- |
| **CLAUDE.md** | 每次都要知道的项目约定 | 会话开始,全文 | 每次请求都带 | 建议 | 06 |
| **rules** | 按目录、按文件类型的约定 | 会话开始,或打开匹配的文件时 | 按需 | 建议 | 06 |
| **output style** | 回答的角色、语气、格式 | 会话开始 | 每次请求都带 | 建议 | 09 |
| **skills** | 可复用的知识和流程 | 描述常驻,正文用到时加载 | 低 | 建议 | 10 |
| **子 agent** | 隔离上下文、并行、专门角色 | 被调用时 | 不占主会话 | 建议 | 13 |
| **dynamic workflows** | 几十上百个子 agent 的大规模任务 | 被调用时 | 不占主会话 | 由脚本编排 | 17 |
| **hooks** | 每次事件都必须执行的动作 | 事件触发时 | 零(除非有输出) | **强制** | 11 |
| **权限规则 / 沙箱** | 什么能做、什么不能做 | 每次工具调用 | 零 | **强制** | 03-04 |
| **MCP** | 连接外部系统 | 工具名常驻,schema 按需 | 低 | — | 12 |
| **plugins** | 把上面这些打包分发 | — | 取决于内容 | — | 14 |
| **mods** | 改造 Claude Code 程序本身:界面、事件处理 | 进程启动时 | 取决于实现 | 强制(代码) | 15 |

## 三、三个关键问题

### 3.1 必须每次发生,还是让 Claude 判断?

这是最重要的一条分界线。CLAUDE.md、skills、output style 里写的都是**指令**:Claude 会尽量遵守,但它是在理解和判断,不是在执行程序。hooks、权限规则、沙箱是**强制**:不经过模型的判断,每次都生效。

| 需求 | 错误的做法 | 正确的做法 |
| --- | --- | --- |
| 不许改 `.env` | CLAUDE.md 里写"不要修改 .env" | `permissions.deny` 加 `Edit(.env)`,或 `PreToolUse` hook |
| 每次改完代码都格式化 | CLAUDE.md 里写"记得跑 prettier" | `PostToolUse` hook 跑格式化 |
| 不许 `git push --force` | skill 里写"不要强推" | deny 规则 `Bash(git push --force*)` |
| 不许访问外网 | 提示词里要求 | 沙箱的网络限制(04 篇) |
| 用 pnpm 不用 npm | — | CLAUDE.md(错了也不是事故,而且 Claude 需要知道原因) |
| 提交信息按团队格式写 | — | CLAUDE.md 或 skill(需要理解和判断) |

**判断标准:如果它没被遵守会造成事故,就不能只靠指令。**反过来,需要理解和判断的东西也不适合写成 hook——一个 hook 没法判断"这次改动需不需要更新文档"。

### 3.2 需要的是知识,还是能力?

- **知识**(怎么做、规范是什么、为什么):CLAUDE.md、rules、skills
- **能力**(能访问什么、能执行什么):MCP、内置工具、Bash 能调用的 CLI

两者经常一起出现:MCP 让 Claude 能查数据库,一个 skill 告诉它表结构和查询习惯。只有能力没有知识,Claude 会用但用不好;只有知识没有能力,它知道该做什么却做不了。

### 3.3 作用在谁身上?

| 范围 | 放在哪 | 例子 |
| --- | --- | --- |
| 只有我 | `~/.claude/`(用户级 CLAUDE.md、skills、settings) | 个人偏好、常用命令 |
| 这个仓库的所有人 | 仓库里的 `CLAUDE.md`、`.claude/`、`.mcp.json` | 项目约定、构建命令、项目专用的 server |
| 团队的多个仓库 | plugin + 团队的 marketplace | 团队的审查规范、部署流程 |
| 整个组织 | 托管设置(managed settings、`managed-mcp.json`) | 安全策略、允许的 MCP server、统一的权限规则 |
| 产品的用户 | 你的应用代码(Agent SDK、Managed Agents) | 面向客户的功能 |

一个常见的误区是把团队规范放在每个人自己的 `~/.claude/` 里,结果每个人的版本都不一样。**团队共享的东西进仓库或进 plugin。**

## 四、几组容易混淆的选择

### 4.1 CLAUDE.md、rules 还是 skill

| | CLAUDE.md | rules | skill |
| --- | --- | --- | --- |
| 加载 | 每次会话 | 每次会话,或打开匹配文件时 | 用到时 |
| 适合 | 构建命令、核心约定、"永远不要" | 某种语言、某个目录的规范 | 参考资料、可调用的流程 |

经验法则:**CLAUDE.md 控制在 200 行以内**。它在变长,就把参考资料挪到 skill,把只和部分文件有关的规范挪到带 `paths` 的 rules。

### 4.2 skill 还是子 agent

skill 是**内容**,加载进当前上下文;子 agent 是**一个独立的执行者**,在自己的上下文里工作,只把结论交回来。需要隔离大量中间结果、需要并行、需要限制工具权限时用子 agent;只是需要一份知识或一个流程时用 skill。两者可以组合:子 agent 可以预加载指定的 skills,skill 也可以用 `context: fork` 在子 agent 里运行。

### 4.3 子 agent 还是 dynamic workflow

子 agent 由 Claude 一轮一轮决定下一步;workflow 由 Claude 写的脚本决定。几个子 agent 能搞定的用子 agent;任务大到需要几十上百个 agent、或者需要另一批 agent 交叉验证结果时,用 workflow(17 篇)。

### 4.4 hook 还是 skill

| | hook | skill |
| --- | --- | --- |
| 触发 | 生命周期事件,不经过 Claude 判断 | 用户输入 `/名字`,或 Claude 认为相关 |
| 结果 | 确定的 | 取决于 Claude 的理解 |
| 上下文成本 | 零(除非有输出) | 描述常驻 |
| 适合 | 格式化、拦截危险命令、日志、通知 | 需要推理的流程、参考资料 |

### 4.5 MCP、skill + CLI,还是 Agent SDK 里的自定义工具

| 情况 | 选 |
| --- | --- |
| 有成熟的 CLI(`gh`、`aws`、`kubectl`),Claude 本来就会用 | **Bash + 一个讲清楚团队用法的 skill**,往往就够了 |
| 没有 CLI,或者需要处理 OAuth、返回结构化结果、做服务端的权限控制 | MCP server |
| 能力要同时给 Claude Code、Claude Desktop、云端 agent 等多个客户端用 | 独立的 MCP server |
| 只在你自己的 Agent SDK 应用里用 | SDK 的进程内工具(33 篇) |

MCP 不是越多越好。每多一个 server,就多一组工具定义(即使有工具搜索,工具名和 server 说明仍然常驻)、多一个需要维护和审查的依赖。

### 4.6 hook 还是 mod

hook 在 Claude Code **外部**运行一段脚本或请求,通过输入输出和它交互;mod 是跑在 Claude Code **进程里**的代码,能画界面、改写事件(15 篇)。能用 hook 解决的就不要写 mod:mod 能力更强,但以你的完整权限运行、不在沙箱里,出了问题影响的是整个程序。

### 4.7 plugin 还是复制文件

同样的 skills、hooks、agents 要在第二个仓库里用时,就该打包成 plugin 了。复制文件的问题是改了一处,其他地方不会同步。

## 五、按触发条件逐步添加

不要一开始就把所有机制都配上。每种机制都有一个明确的"该加它了"的信号:

| 信号 | 加什么 |
| --- | --- |
| Claude 把某个约定或命令搞错了两次 | 写进 CLAUDE.md |
| 总在要求它回答短一点、多解释一点、换个格式 | 设置 output style |
| 总在输入同一段开场白来开始某类任务 | 做成用户可调用的 skill |
| 第三次往对话里粘贴同一份操作手册 | 做成 skill |
| 总在从 Claude 看不到的浏览器页面里复制数据 | 把那个系统接成 MCP server |
| Claude 为了找一个符号的定义读了很多文件 | 装对应语言的代码智能插件 |
| 一个支线任务的输出淹没了对话 | 交给子 agent |
| 希望某件事每次都自动发生 | 写一个 hook |
| 某件事绝对不能发生 | 权限规则或 hook |
| 第二个仓库需要同样的配置 | 打包成 plugin |
| 全组织需要统一的策略 | 托管设置 |

同样的信号也告诉你什么时候该修改已有的东西:一个反复出现的错误、一条反复出现的审查意见,应该改 CLAUDE.md,而不是每次在对话里纠正。

## 六、基于 Claude 构建时怎么选

| | Messages API | Agent SDK | Managed Agents |
| --- | --- | --- | --- |
| 谁跑 agent 循环 | 你(或 Tool Runner) | Claude Code 的循环,在你的进程里 | Anthropic |
| 工具在哪执行 | 你的代码里 | 你的机器上 | Anthropic 的容器里(或自托管沙箱) |
| 内置工具 | 无(服务端工具除外) | Claude Code 的全套 | 预置工具集 |
| 状态 | 你自己管 | 本地会话文件 / `SessionStore` | 托管的会话、memory store |
| 运维负担 | 低(无状态调用) | 中到高(子进程、隔离、扩缩容) | 低 |
| 平台 | 所有云平台 | 所有云平台 | Claude API、Claude Platform on AWS |
| 适合 | 单次调用、自己编排的流程 | 需要操作本地仓库或内网的自动化 | 托管的、定时的、带工作区的 agent |
| 篇 | 23-30 | 32-35 | 31 |

选择的顺序是**从最简单的开始**:一次 API 调用能解决的,不要上 agent;自己编排几步流程就能解决的,不要让模型自由探索。"最简单"指的是你要维护的代码最少——对一个需要定时运行、要有工作区、要跨会话记忆的 agent 来说,Managed Agents 反而是最简单的。41 篇会展开讲 agent 的设计模式。

### MCP server 作为共享能力层

如果一组能力会被多个地方用到,把它写成 MCP server 是最划算的投资:

```
                     ┌─ Claude Code(开发者日常)
                     ├─ Claude Desktop / claude.ai(非技术同事)
 acme-support MCP ───┼─ Agent SDK(CI、批处理)
                     ├─ Managed Agents(托管的客服 agent)
                     └─ Messages API 的 MCP connector(自己的应用)
```

能力只实现一次,权限、审计、业务规则都在一个地方(37-38 篇)。

## 七、一个团队的完整配置

以一个后端团队为例,把需求和机制对上:

| 需求 | 机制 | 放在哪 |
| --- | --- | --- |
| 构建、测试命令,目录结构,"所有 SQL 都走 repository 层" | CLAUDE.md | 仓库根目录 |
| `migrations/` 目录下的迁移脚本规范 | 带 `paths` 的 rules | `.claude/rules/` |
| 发布流程、事故复盘模板 | skills(`/release`、`/postmortem`) | 团队 plugin |
| 不许改生产配置、不许强推 | deny 规则 | 托管设置 |
| 改完 Go 代码自动 `gofmt` | `PostToolUse` hook | 仓库的 `.claude/settings.json` |
| 查工单、查监控、查部署记录 | MCP server | 组织的托管 MCP 配置 |
| 代码审查时分别看安全、性能、测试 | 三个只读子 agent | 团队 plugin |
| PR 自动审查 | Agent SDK + GitHub Actions(35 篇),或官方的 Code Review(22 篇) | CI |
| 每周依赖升级检查 | routines(19 篇)或 Managed Agents 定时部署 | 云端 |

注意这张表里**没有一项是"在 CLAUDE.md 里写一条安全要求"**。

## 八、踩坑

1. **把安全要求写成指令**——CLAUDE.md 和 skill 里的"不要"是请求,不是保证。用权限规则、hook、沙箱
2. **CLAUDE.md 越写越长**——每次请求都带着它。参考资料挪进 skill,局部规范挪进 rules
3. **团队规范放在每个人自己的 `~/.claude/` 里**——版本各不相同。进仓库或进 plugin
4. **为一个 CLI 就能做的事写 MCP server**——Bash + skill 往往就够,少一个要维护的服务
5. **需要判断的事写成 hook**——hook 不会思考,"需不需要更新文档"这种事交给 skill 或 CLAUDE.md
6. **什么都交给子 agent**——子 agent 看不到主会话的上下文,需要它的判断依赖这些上下文时反而更差
7. **能用 hook 的事写成 mod**——mod 以完整权限运行在进程里,风险和维护成本都高得多
8. **为一个能单次调用解决的需求上 agent**——更贵、更慢、更不稳定
9. **同一套能力在每个产品里各写一遍**——写成 MCP server,一处实现,到处使用
10. **一开始就把所有机制都配上**——按信号逐步添加,每一项都能说出它解决了什么问题

# Prompt Caching

一个客服机器人每次请求都带着 2 万 token 的产品手册;一个代码助手每一轮都重发整个对话历史;一个 agent 每次调用都带着几十个工具定义。这些重复的部分如果每次都按全价计费、从头处理,又贵又慢。prompt caching 让 API **把请求开头重复的部分缓存起来**,后续请求命中时只按约十分之一的价格计费,首 token 延迟也明显下降。

> 一句话先记住:**缓存是前缀匹配,前缀里任何一个字节变了,它后面的缓存全部失效**。所有关于缓存的技巧,都是从这一条推出来的:稳定的内容放前面,易变的内容放后面,前缀里绝不能有时间戳、随机 ID 这种每次都变的东西。

---

## 一、它是怎么工作的

请求按这个顺序渲染:**`tools` → `system` → `messages`**。缓存的 key 由到某个断点为止的**精确字节**决定:

```
[tools][system][历史消息 1][历史消息 2]...[最新一轮]
 ←───────────── 可缓存的前缀 ─────────────→ ← 新内容 →
```

第二次请求时,如果前缀和缓存里的一字不差,这部分直接从缓存读;只有后面新增的部分按全价处理。

### 1.1 价格

| | 相对基础输入价 |
| --- | --- |
| 缓存写入(5 分钟 TTL) | 1.25× |
| 缓存写入(1 小时 TTL) | 2× |
| **缓存读取** | **约 0.1×**(Opus 5.5 为 0.05×,即 $0.20/百万 token;Fable 5.1 为 0.025×) |

5 分钟 TTL 下,**同一个前缀用两次就回本**。在 Claude API 上,大多数模型的缓存读取还**不计入输入 token 的限流额度**,所以缓存不仅省钱,还能提高有效吞吐。

## 二、怎么开启

### 2.1 自动缓存(推荐的起点)

```python
response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    cache_control={"type": "ephemeral"},     # 顶层字段:自动在最后一个可缓存块上打断点
    system="你是这份产品手册的专家……(很长的手册内容)",
    messages=[{"role": "user", "content": "总结一下退货政策"}],
)
```

顶层 `cache_control` 会自动把断点放在最后一个可缓存的块上,并随着对话增长自动往后移。**多轮对话用它最省心**。

### 2.2 手动断点

```python
response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    system=[{
        "type": "text",
        "text": "你是这份产品手册的专家……(很长的手册内容)",
        "cache_control": {"type": "ephemeral"},          # 默认 5 分钟
        # "cache_control": {"type": "ephemeral", "ttl": "1h"},   # 1 小时
    }],
    messages=[{"role": "user", "content": "总结一下退货政策"}],
)
```

- 每个请求**最多 4 个断点**
- 断点可以放在 system 文本块、工具定义、消息里的各种内容块(文本、图片、tool_use、tool_result、文档)上
- **断点打在最后一个 system 块上,会把 tools 和 system 一起缓存**(tools 渲染在它前面)

### 2.3 什么时候必须用手动断点

| 情况 | 为什么自动缓存不合适 |
| --- | --- |
| prompt 末尾是每次都不同的内容(检索结果、本次的问题) | 自动断点会落在这段独有内容之后,每次都白付写入费 |
| 几段内容变化频率不同(工具从不变、上下文每天变、对话每轮变) | 自动只放一个断点,多个稳定性边界需要手动标 |
| 一部分要 1 小时 TTL,一部分 5 分钟 | 需要按块设置;**长 TTL 的必须在短 TTL 的前面** |

**agent 循环的稳妥组合**:在静态 system 前缀的最后一块上手动打一个断点(保证最贵的共享部分一定能命中),再加上顶层自动缓存跟随对话增长。

## 三、放置模式

### 3.1 大段共享的系统提示

断点打在最后一个 system 块上。

### 3.2 多轮对话

断点放在最新一轮的最后一个内容块上。之前的断点仍然是有效的读取点,命中会随对话逐步累积。

### 3.3 共享前缀 + 每次不同的后缀

```python
messages=[{"role": "user", "content": [
    {"type": "text", "text": "<共享的上下文:few-shot 示例、检索文档、长指令>",
     "cache_control": {"type": "ephemeral"}},
    {"type": "text", "text": "<每次不同的问题>"},      # 不打标记
]}]
```

断点打在**共享部分的末尾**,不是整个 prompt 的末尾。

### 3.4 每次开头都不一样

不要缓存。前 1K token 每次都不同就没有可复用的前缀,加了 `cache_control` 只会白付写入溢价。

## 四、那些悄悄让缓存失效的写法

| 写法 | 为什么会破坏缓存 |
| --- | --- |
| system 里有 `datetime.now()`、"当前时间:……" | 前缀每次都变 |
| 内容开头有 `uuid4()`、请求 ID | 同上 |
| `json.dumps(d)` 没有 `sort_keys=True`、遍历 `set` | 序列化顺序不确定,字节不同 |
| system 里拼接了用户 ID、会话 ID | 每个用户一个前缀,无法跨用户共享 |
| `if flag: system += ...` 这类条件拼接 | 每种标志组合都是一个不同的前缀 |
| `tools=build_tools(user)`,工具集因用户而异 | 工具在最前面,什么都缓存不了 |

修法:**把动态部分挪到最后一个断点之后、让它变成确定性的,或者干脆删掉**。三条架构原则:

1. **system prompt 冻结**:日期、模式、用户名这类动态信息放到 `messages` 里,不要插进 system
2. **对话中途不要换工具、不要换模型**:工具渲染在最前面,增删或调整顺序会让整个缓存失效;缓存按模型隔离,换模型等于从零开始。需要"模式切换"就别换工具集
3. **分叉调用要复用父请求的精确前缀**:摘要、压缩、子任务这类旁路调用,如果重新组装 system / tools / model 时有任何差异,就命中不了父请求的缓存

---

## 五、不是所有改动都让一切失效

缓存分三层:**工具 → system → messages**。一个改动只会让它所在层及之后的层失效:

| 改动 | 工具缓存 | system 缓存 | messages 缓存 |
| --- | :---: | :---: | :---: |
| 增删、重排工具定义 | 失效 | 失效 | 失效 |
| 换模型 | 失效 | 失效 | 失效 |
| 开关 fast mode(speed)、web search、citations | 保留 | 失效 | 失效 |
| 改 system 内容 | 保留 | 失效 | 失效 |
| 改 `tool_choice`、加图片 | 保留 | 保留 | 失效 |
| 改 thinking 或 effort | 因模型而异 | 因模型而异 | 失效 |

几个"不破坏缓存"的替代写法(在支持的新模型上):

- **对话中途追加运维指令** → 往 `messages` 末尾加一条 `{"role": "system", "content": "..."}`,而不是改顶层 `system`。这也是**防提示注入的正确做法**:运维指令走 system 角色,不要伪装成用户消息里的文字
- **每轮都要的临时提醒** → 用带 `clear_at` 的、只在本轮生效的 system 消息,并且**留在历史里不要删**。往历史里插提醒、下一轮再删掉,本身就是一次历史修改,缓存从那里开始失效
- **中途增删工具** → 用专门的 `tool_addition` / `tool_removal` 块
- **中途改 effort** → 用一条只带 `output_config` 的 system 消息(部分新模型支持)

换模型没有替代写法:**主循环固定一个模型,便宜的子任务派给子 agent 用另一个模型**。

## 六、TTL 怎么选

缓存命中会免费刷新计时器。TTL 从写入或读取它的请求**开始时**算起——生成本身的耗时也算在内。

| 共享同一前缀的两次请求的间隔 | 选 |
| --- | --- |
| 5 分钟以内(持续的流量、每轮生成远少于 5 分钟的 agent 循环) | 5 分钟:每次请求都在刷新,更便宜 |
| 5 到 60 分钟(用户 20 分钟后才回复;中间夹着一次长生成) | 1 小时:这是 2 倍写入价唯一划算的区间 |
| 超过 1 小时 | 都没用:定时预热,或接受冷启动 |

---

## 七、最小缓存长度

前缀太短不会被缓存——**不报错,只是 `cache_creation_input_tokens` 为 0**:

| 模型 | 最小长度 |
| --- | ---: |
| Opus 5.5、Opus 5、Fable 5 / 5.1、Sonnet 5.5、Haiku 5.5 | 512 token |
| Opus 4.8、Sonnet 5、Sonnet 4.6、Sonnet 4.5 | 1024 token |
| Opus 4.7 | 2048 token |
| Opus 4.6、Opus 4.5、Haiku 4.5 | 4096 token |

**这个值不是随代数单调变化的**:一个 3K token 的 prompt 在 Opus 5 上能缓存,在 Haiku 4.5 上不能。

## 八、验证命中

```python
u = response.usage
print(u.cache_creation_input_tokens)   # 本次写入缓存的(付了写入溢价)
print(u.cache_read_input_tokens)       # 本次从缓存读取的(约 0.1×)
print(u.input_tokens)                  # 按全价处理的(最后一个断点之后的部分)
```

**`input_tokens` 只是未缓存的那部分**,总 prompt 大小 = 三者之和。

健康的多轮循环应该是这样的:

- `cache_read_input_tokens`:之前累积的整个前缀,逐轮增长
- `cache_creation_input_tokens`:大约是上一轮的输出加上新追加的输入,相对很小
- `input_tokens`:只有最后断点之后的尾巴

如果每次请求的 `cache_creation_input_tokens` 都接近整个对话的大小,说明断点之前的前缀在被改写。排查方法:**记录几次连续请求的完整 JSON,两两 diff**——相邻请求只应该在末尾不同,前面任何不同的地方就是罪魁祸首。

> **每次改代码后都要验证,不只是上线时**。缓存失效最隐蔽的地方是:请求照常成功,只是账单变高了,没有任何错误提示。

## 九、几个进阶细节

- **20 块回看窗口**:每个断点最多往回找 20 个位置去匹配之前的缓存条目(连续的 tool_use 算一个位置,连续的 tool_result 算一个)。一轮里追加了超过 20 个位置时,在中间每约 15 个位置补一个断点
- **并发请求**:缓存要等第一个响应**开始流式输出**后才可读。N 个前缀相同的并发请求会全部按全价付费。扇出的正确做法:先发 1 个,等到第一个 token,再发其余 N-1 个
- **预热**:对首请求延迟敏感(聊天、语音),而流量间隔又超过 TTL 时,在启动或定时发一个 `max_tokens: 0` 的请求,只写缓存不生成。流量持续、前缀很小或因人而异时不要预热
- **隔离范围**:Claude API 上缓存按 workspace 隔离,永远不会跨组织共享

## 十、和 Claude Code 的关系

05 篇讲过 Claude Code 的缓存行为,其实就是这些规则的应用:它按"系统提示 → 项目上下文 → 对话"排列请求;中途换模型、改 effort、增删 MCP server 会让缓存失效;改 CLAUDE.md 不会立刻生效(也就不破坏缓存)。如果你在用 Agent SDK 自己搭 agent,这些规则同样适用。

## 十一、踩坑

1. **在 system 里写"当前时间"**——前缀每次都变,缓存永远不命中
2. **`json.dumps` 不排序**——字典顺序不确定,字节不同
3. **按用户动态生成工具列表**——工具在最前面,什么都缓存不了
4. **对话中途换模型或增删工具**——整个缓存失效
5. **断点打在每次不同的问题后面**——每次都白付写入费,从不读取
6. **prompt 太短还加缓存标记**——低于最小长度,静默不缓存
7. **并发发出一批相同前缀的请求**——全都按全价付费,先发一个再发其余
8. **每轮往历史里插提醒、下一轮再删**——这本身就是历史修改,缓存从那里断掉
9. **以为 `input_tokens` 就是总输入**——它只是未缓存的部分
10. **上线时测过一次就不管了**——一次无关的改动就可能让命中率归零,定期看 `cache_read_input_tokens`

# Agent 设计模式与产品选型

aiLearning/26-28 讲过 agent 的通用理论:ReAct、Plan-Execute、Reflection、多 agent 协作框架。这一篇站在"用 Claude 做一个真正上线的东西"的角度,把这个系列前面的内容收拢成一套设计方法:**先判断要不要 agent,再决定结构,然后设计工具面、上下文策略、人工介入点和评测**,最后选一个合适的产品形态去实现它。

> 一句话先记住:**能不用 agent 就不用,能用工作流就不用自主 agent**。agent 的价值在于处理那些步骤无法事先写清楚的任务;代价是更贵、更慢、结果更难预测。把确定的部分交给代码,只把真正需要判断的部分交给模型。

---

## 一、真的需要 agent 吗

动手之前,用四个问题检验:

| 问题 | 例子(需要) | 例子(不需要) |
| --- | --- | --- |
| **复杂度**:任务是多步的、很难事先完全写清楚吗? | "把这份设计文档实现成一个 PR" | "从这个 PDF 里提取标题" |
| **价值**:结果值得更高的成本和延迟吗? | 一次节省工程师半天的迁移 | 一个每天跑百万次的分类 |
| **可行性**:Claude 擅长这类任务吗? | 读代码、写代码、查资料、整理信息 | 需要它不可能拿到的实时信息 |
| **出错代价**:错误能被发现和挽回吗? | 有测试、有审查、能回滚 | 直接给客户转账 |

**任何一个回答是"否",就退回更简单的层级**:一次 API 调用,或者由代码编排的工作流。

## 二、从简单到复杂的五种结构

Anthropic 把基于大模型的系统分成两类:**工作流**(由代码预先规定步骤)和 **agent**(由模型自己决定步骤)。常见的结构按复杂度排列:

| 结构 | 怎么工作 | 适合 | Claude 生态里的实现 |
| --- | --- | --- | --- |
| **链式调用** | 一步的输出是下一步的输入,中间可以加代码检查 | 能拆成固定几步的任务:先提纲再成文、先抽取再校验 | 几次 Messages API 调用 |
| **路由** | 先分类,再交给专门的处理流程 | 输入类型差异大:客服问题分流到退款、技术、账单 | 一个便宜模型做分类 + 各自的提示词 |
| **并行** | 同一任务拆成独立的片段同时做,或同一问题多次求解再投票 | 多维度检查;需要更高置信度的判断 | 并发的 API 调用;Batches API |
| **编排者-执行者** | 一个模型规划并分派,多个执行者完成,再汇总 | 工作量大、能拆成很多独立块,事先不知道怎么拆 | 子 agent(13、33 篇);Managed Agents 多 agent;dynamic workflows(17 篇) |
| **评估-优化循环** | 一个生成、一个按标准评估,不合格就改 | 有清晰的验收标准:翻译、报告、代码要过测试 | Managed Agents 的 outcomes(31 篇);Claude Code 的 `/goal`(08 篇) |
| **自主 agent** | 模型在循环里自己决定调用什么工具,直到完成 | 开放式任务:调试、调研、实现一个功能 | Claude Code、Agent SDK、Managed Agents |

这些结构可以嵌套:一个路由后面接一个评估循环,一个编排者下面的执行者本身是自主 agent。

### 关于多 agent 的现实

多 agent 听起来很强大,但官方的成本实测给出的结论相当克制(30 篇):

- **编排者-执行者只在有大量可以独立处理的工作时才划算**,最好多到一个上下文窗口装不下。如果工作是一条相互依赖的链,或者一个窗口就放得下,单个模型用低 effort 做,往往比编排更便宜、效果也不差
- **advisor 模式**(便宜的执行者 + 关键时刻咨询强模型)只在两个模型能力差距大、执行者确实会去咨询时有效
- 子 agent 从新的上下文开始,看不到主会话的信息,和主会话也不共享缓存。**需要它的判断依赖主会话上下文时,拆出去反而更差**

一个"问答类" agent(客服、文档问答、辅导)一次处理一个问题,不需要再配一群检查者、投票者——让一个 agent 把答案做对。

## 三、设计工具面

工具决定了 agent 能做什么,也决定了**你的程序能控制什么**。

### 3.1 通用工具还是专用工具

一个 `bash` 工具几乎什么都能做,但对你的程序来说,每次调用都只是一串不透明的命令。把一个动作提升为专用工具,程序就拿到了一个带类型参数、可以拦截的钩子:

| 什么时候提升为专用工具 | 为什么 |
| --- | --- |
| **需要把关** | `send_email(to, subject, body)` 很容易加确认;`bash -c "curl -X POST ..."` 很难。难以撤销的动作(对外调用、发消息、删数据)都应该是专用工具 |
| **需要一致性检查** | 专用的 `edit` 工具可以在文件被改过之后拒绝写入,bash 做不到 |
| **需要特殊的展示** | Claude Code 把提问做成工具,才能渲染成选项对话框并暂停循环 |
| **需要并行调度** | 只读工具可以标记为可并发;都走 bash 时,程序分不清 `grep` 和 `git push`,只能串行 |

**经验法则:先用 bash 获得广度,需要把关、展示、审计或并行时,再提升为专用工具。**Claude Code 本身就是这样设计的:有 `Bash`,也有 `Read`、`Edit`、`AskUserQuestion`。

### 3.2 写好工具

24 篇和 36 篇讲过工具的写法,这里只列最影响 agent 表现的几条:

- 描述写清楚做什么、返回什么、什么时候用;参数有说明和约束
- 按任务设计,不要照搬后端 API;一次调用回答一个完整的问题
- 只返回需要的内容,大结果截断并说明怎么继续
- 错误信息告诉模型下一步该怎么做
- 让模型不该填的值(当前用户、价格、审批人)由程序提供(37 篇的 `Resolve`)

### 3.3 工具多了怎么办

- 几十个以上的工具:工具搜索,不常用的延迟加载(28 篇)
- 一长串依次调用、中间结果没用:程序化工具调用,让 Claude 写脚本串起来,只有最终结果进入上下文(28 篇)
- 一份很长的操作手册只有部分任务需要:做成 skill,按需加载

## 四、上下文策略

agent 跑得越久,上下文问题越突出。几条贯穿全系列的原则:

| 原则 | 做法 | 篇 |
| --- | --- | --- |
| **前缀保持稳定** | system prompt 冻结;中途的指令用 system 角色的消息追加;工具一开始就声明全,中途用 `tool_addition` | 25 |
| **一个循环固定一个模型** | 便宜的子任务派给用别的模型的子 agent,不要在循环中途换模型 | 25、26 |
| **历史只追加,不修改** | 新模型的思考块绑定了完整前缀,客户端改历史会让它们失效 | 26、29 |
| **修剪和压缩交给服务端** | context editing、compaction;客户端只做"总结成一条消息"的简单压缩 | 29 |
| **大量中间结果隔离出去** | 子 agent 只交回结论 | 13、33 |
| **跨会话的状态写进文件** | memory 工具、memory store、CLAUDE.md、进度文件 | 06、29、31 |

### 长时间运行的 agent

一个要跑几小时、跨好几个上下文窗口的任务,最怕的是"做到一半忘了自己在干什么"。实践中有效的做法:

- **一开始就把任务、意图和约束写完整**。中途补充指令会打断它,而且新模型在任务描述清楚时自主性最强
- **让 agent 维护一个进度文件**:做完了什么、正在做什么、遇到的问题、下一步。压缩或换窗口之后,它读这个文件就能接上
- **定义可检查的完成标准**:测试通过、rubric 满足。没有标准的长任务很容易提前收工或者无止境地"优化"
- **用 git 做检查点**:每完成一个阶段提交一次,出了问题能回到上一个好的状态
- **设预算**:task budget 让模型自己控制节奏,`max_turns`、`max_budget_usd`、会话预算是硬上限

## 五、人在哪里介入

完全无人值守和每步都确认是两个极端,大多数系统在中间:

| 介入方式 | 适合 | 实现 |
| --- | --- | --- |
| **开始前审批计划** | 改动范围大、方向错了代价高 | Claude Code 的 plan mode(08 篇);SDK 的 `plan` 权限模式 |
| **危险操作逐次确认** | 对外发送、删除、付款 | 权限规则的 ask;`can_use_tool`;MCP 的 `requiresUserInteraction` |
| **执行中途补充信息** | 只有用户知道的选择 | `AskUserQuestion`;MCP 的 elicitation(39 篇) |
| **结果审查** | 产出物要进入正式流程 | PR 审查;outcomes 的 rubric 之外再加人工抽查 |
| **事后审计** | 低风险的自动化 | hooks 记录;OpenTelemetry;审计日志 |

设计时问自己:**这个 agent 最坏能做出什么事?** 然后在那件事之前放一个人,或者用权限让它根本做不到。对不可信输入(网页、邮件、PR 内容)进入上下文的 agent,这一点尤其重要(35、38 篇)。

另一个常见的问题是 agent **问得太多**:每个小决定都停下来确认,用户很快就会烦。新模型在提示词里明确"小决定自己做、范围变化和破坏性操作才问"时表现最好。

## 六、提示词的几条新规矩

为新模型写 agent 提示词,和为两年前的模型写很不一样:

- **少用大写的强调**:`CRITICAL`、`MUST`、`如果有疑问就……`这类为老模型写的强硬措辞,会让新模型过度执行,比如过度频繁地调用某个工具
- **说清楚自主程度和范围**:无人值守的任务,告诉它不需要等确认、遇到什么情况才停下、哪些东西不要碰
- **说明为什么**:规则附上理由,模型能在规则没覆盖到的情况下做出合理判断
- **委派时不要强迫主 agent 等待**:启动子 agent 的工具立即返回,结果晚些送达,主 agent 可以先做别的事
- **用 effort 控制思考深度**,不要在提示词里写"仔细想想"(26 篇)

迁移到新模型时,用 `/claude-api prompt-audit` 检查一遍旧提示词里过时的写法,往往能直接降低成本。

## 七、评测

没有评测,所有的改进都是凭感觉。aiLearning/32 讲过评测的通用方法,这里是针对 Claude 应用的最小做法:

1. **一个流程一个评测**。一个应用有分类、摘要、agent 循环三个流程,就是三个评测,不要做一个大而全的基准
2. **输入从真实数据来**:生产日志 > 用户反馈的问题案例 > 人工编写 > 模型合成。第一版 15 到 100 个,少于 15 个时一个不稳定的用例就能让分数大幅波动
3. **评分用最便宜的、真正能测出你关心的东西的方法**:程序化检查(测试通过、JSON 合法、标签正确)> 两两盲比 > 模型按 rubric 打分 > 人工抽查。agent 任务尽量检查**结果**(测试过了没有、文件对不对),而不是检查过程
4. **评分标准要先在几个样例上和人的判断对齐**,对不齐就改标准
5. **调用真实的入口**:评测脚本调用应用本身的函数或接口,不要在评测里重新拼一遍 API 调用——那测的是另一个东西
6. **同时记录成本、延迟、工具调用次数**,先报绝对值再报相对变化
7. **怀疑每一个零**:成本 0 美元、延迟 0 秒,通常是字段没对上,不是真的

有了评测,30 篇的成本优化和换模型、调 effort 才有依据。Claude Code 里的 `/claude-api build-eval` 可以引导你搭一个评测,`hillclimb` 在评测上迭代改进。

## 八、产品形态怎么选

确定了要做什么,最后选实现方式。两个独立的问题:**谁提供循环(harness)?谁负责部署?**

| 方式 | 你写什么 | 循环 | 部署 | 工具 | 适合 |
| --- | --- | --- | --- | --- | --- |
| **API 手写循环** | 整个 `while` 循环 | 你 | 你 | 只有你定义的 | 要完全掌控流程 |
| **API + Tool Runner** | 工具函数 | SDK 提供 | 你 | 只有你定义的 | 大多数自定义工具的 agent(24 篇) |
| **Agent SDK** | 提示词 + 选项 | Claude Code 的完整循环 | 你 | 内置文件、shell、搜索 + MCP + 子 agent | 在自己的机器上操作仓库和文件系统(32-35 篇) |
| **Managed Agents** | agent 配置 + 你的工具结果 | Anthropic | **Anthropic** | 托管沙箱 + skills + MCP + 你的工具 | 托管的、长时间运行的、定时的 agent(31 篇) |
| **直接用 Claude Code** | CLAUDE.md、skills、hooks | Claude Code | 开发者的机器或云端会话 | 全部 | 内部开发场景:`-p`、routines、GitHub Actions(18-22 篇) |

注意两个容易混的东西:**Tool Runner 是 Claude API SDK 里的一个辅助工具**,只循环调用你定义的工具,没有内置工具;**Agent SDK 是另一个产品**,是打包成库的 Claude Code。两者都只提供循环,部署都要你自己做;只有 Managed Agents 把部署也托管了。

一些具体的建议:

- **面向开发者的内部自动化**,先看 Claude Code 本身能不能做:`claude -p`、GitHub Actions、routines、Code Review。能用就不要自己写
- **嵌在产品里的 AI 功能**,大多数是 Messages API 的单次调用或简单工作流
- **需要操作代码仓库、跑命令的自动化**,Agent SDK
- **需要工作区但不想运维、要定时、要跨会话记忆**,Managed Agents
- **同一组能力多处使用**,先写成 MCP server(40 篇)
- **要上第三方云平台**,先查功能支持表:Managed Agents、Files API、很多服务端工具只在 Claude API 上(28 篇)

## 九、一个例子:从需求到设计

需求:"每天早上把昨天的线上告警整理成一份报告,能自己处理的(比如已知的磁盘告警)直接处理,需要人的标出来。"

| 设计问题 | 决定 |
| --- | --- |
| 需要 agent 吗? | 整理报告可以是工作流;"判断能否自己处理并处理"需要 agent。拆开 |
| 结构 | 代码拉取告警 → 路由(已知类型 / 未知类型)→ 已知类型交给受限的处理 agent → 汇总报告 |
| 工具面 | 只读的查询工具(监控、日志、部署记录);处理动作做成专用工具(`clean_disk(host)`、`restart_service(name)`),不给通用 shell |
| 人工介入 | 重启服务需要确认;未知类型只报告不处理 |
| 上下文 | 每个告警一个子 agent,只交回结论 |
| 评测 | 过去 30 天的告警作为输入;检查"该处理的处理了、不该碰的没碰、报告里有没有漏" |
| 产品形态 | 定时运行、要工作区、要记住"上周处理过什么"→ Managed Agents 定时部署 + memory store;工具做成内部 MCP server |

## 十、踩坑

1. **一上来就做自主 agent**——先问四个问题,大多数需求一次调用或一个工作流就够
2. **为了"架构好看"上多 agent**——只有大量独立工作时才划算,依赖链和小任务用单个 agent
3. **只给一个 bash 工具**——程序没法对危险动作把关、没法并行。需要控制的动作做成专用工具
4. **长任务没有完成标准**——要么提前收工,要么无止境地改
5. **长任务不留进度文件**——压缩或换窗口后接不上
6. **每个小决定都问用户**——提示词里说清楚哪些自己做、哪些才问
7. **提示词里满是 `CRITICAL`、`MUST`**——为老模型写的措辞让新模型过度执行
8. **没有评测就调提示词、换模型**——改进全凭感觉,退步也发现不了
9. **评测脚本里重新拼了一遍 API 调用**——测的不是线上真正运行的东西
10. **把 Tool Runner 和 Agent SDK 当成一个东西**——一个只循环你的工具,一个是完整的 Claude Code

# 团队与企业落地

一个人用 Claude Code,装上、登录、开始用就行。一个团队、一家公司用,问题就变成了另一些:用哪种账号和计费方式?安全团队要求的策略怎么下发到每台机器?钱花在哪了、值不值?代码和数据会不会被拿去训练?AI 写的代码谁来审、出了问题谁负责?

这是系列的最后一篇,讲从个人试用走到组织级使用的完整路径。

> 一句话先记住:**落地的顺序是试点 → 团队规范 → 组织管控 → 度量 → 扩展**。工具配置只是一半,另一半是把 Claude Code 写进团队的工程流程:仓库里的 CLAUDE.md 像代码一样评审,AI 参与的改动照常经过测试和人工审查,提交的人对代码负责。

---

## 一、分阶段推进

| 阶段 | 规模 | 目标 | 产出 |
| --- | --- | --- | --- |
| **试点** | 5-10 个愿意尝试的工程师,2-4 周 | 找到真正有用的场景,测出成本基线 | 场景清单、每人每天的花费、遇到的问题 |
| **团队规范** | 一个或几个团队 | 把有效的用法沉淀下来 | 仓库里的 CLAUDE.md、团队 plugin、使用约定 |
| **组织管控** | 全公司 | 让安全和合规要求在每台机器上生效 | 托管设置、MCP 白名单、接入方式 |
| **度量** | 持续 | 知道钱花在哪、效果如何 | 用量看板、成本报表、告警 |
| **扩展** | 持续 | 从"人用 Claude Code"扩展到自动化 | CI 审查、定时任务、内部 MCP server、基于 Agent SDK 的工具 |

试点阶段最重要的不是"证明它有用",而是**找到在你们的代码库、你们的工作方式下哪些场景有用**。常见的高价值起点:熟悉陌生的代码、写测试、修 bug、重构和迁移、写脚本和小工具、代码审查。试点用户的反馈直接决定了后面的 CLAUDE.md 和 plugin 里该写什么。

## 二、选择接入方式

| 方式 | 适合 |
| --- | --- |
| **Claude for Teams / Enterprise** | 默认推荐。Claude Code 和 claude.ai 一起按席位订阅,没有基础设施要运维 |
| **Claude Console(API)** | 以 API 为主,按用量付费 |
| **Amazon Bedrock / Google Cloud / Microsoft Foundry** | 想沿用已有云平台的合规体系和账单 |

几点要知道:

- **有些功能必须用 claude.ai 账号**:云端会话、云端定时任务、Code Review、Remote Control、Chrome 扩展,只用 Console API key 或云平台凭据都用不了(19-22 篇)
- 走云平台时,很多新功能(Managed Agents、Files API、部分服务端工具)不可用或晚一些上线(28 篇)
- 需要统一入口、按身份审计每个请求、按数据敏感度路由时,在开发者和模型提供方之间放一个**网关**。Anthropic 提供了自托管的 **Claude apps gateway**(内置在 `claude` 二进制里,`claude gateway --config gateway.yaml`):开发者用公司的 SSO 登录,上游凭据只留在你的基础设施里,按 IdP 分组控制可用的模型和下发的托管设置,并输出带用户身份的遥测。员工离职在 IdP 里停用,访问权限随会话过期失效
- SSO、SCIM 用户同步、席位分配在 Claude 账号层面配置,不在 Claude Code 里

## 三、托管设置:让策略到达每台机器

组织的策略通过**托管设置**下发,它的优先级高于开发者自己的用户级和项目级设置。

| 下发方式 | 位置 | 优先级 |
| --- | --- | --- |
| **服务端托管** | claude.ai 管理后台(或 Claude apps gateway) | 最高 |
| plist / 注册表策略 | macOS `com.anthropic.claudecode`;Windows `HKLM\SOFTWARE\Policies\ClaudeCode` | 高 |
| 文件 | macOS `/Library/Application Support/ClaudeCode/managed-settings.json`;Linux/WSL `/etc/claude-code/managed-settings.json`;Windows `C:\Program Files\ClaudeCode\managed-settings.json` | 中 |
| Windows 用户注册表 | `HKCU\SOFTWARE\Policies\ClaudeCode` | 最低 |

- **服务端托管**最省事:Claude Code 启动时拉取、会话中每小时刷新,不用部署任何东西;需要 Teams 或 Enterprise
- plist 和 HKLM 注册表需要管理员权限才能写,不容易被篡改;**HKCU 普通用户就能改,不要当作强制手段**
- 混合使用多种接入方式时,服务端托管 + 文件或 MDM 兜底,保证每种用户都能收到策略
- 数组类的设置(比如 `permissions.deny`)会**合并**各级来源:开发者可以追加,但删不掉托管下发的条目
- 下发后让开发者在 Claude Code 里运行 `/status`,看 `Setting sources` 一行是否显示了托管设置及其来源

## 四、管什么

### 4.1 控制项一览

| 控制 | 作用 | 关键设置 |
| --- | --- | --- |
| 权限规则 | 允许、询问、禁止特定工具和命令 | `permissions.allow` / `ask` / `deny` |
| 权限锁定 | 只认托管设置里的权限规则;禁用 bypass 模式 | `allowManagedPermissionRulesOnly`、`permissions.disableBypassPermissionsMode` |
| 沙箱 | 系统级的文件和网络隔离,网络按域名白名单 | `sandbox.enabled`、`sandbox.network.allowedDomains` |
| 组织级 CLAUDE.md | 全公司的行为指导(是指令,不是强制) | 托管策略路径下的文件 |
| MCP 管控 | 能接哪些 server(38 篇) | `allowedMcpServers`、`deniedMcpServers`、`allowManagedMcpServersOnly`、`managed-mcp.json` |
| 插件市场管控 | 能从哪些市场安装插件 | 托管的市场白名单 |
| 自定义锁定 | skills、agents、hooks、MCP 只能来自插件或托管设置 | `strictPluginOnlyCustomization` |
| hook 限制 | 只运行托管的 hooks;限制 HTTP hook 的地址 | `allowManagedHooksOnly`、`allowedHttpHookUrls` |
| 登录与提供方 | 限制登录方式和组织;限制可用的 API 提供方 | `forceLoginMethod`、`allowedProviders` |
| 模型与 effort | 可选的模型;effort 上限 | `availableModels`、`maxEffortLevel` |
| 版本 | 最低版本;允许的版本范围 | `minimumVersion`、`requiredMinimumVersion` |
| 遥测 | 关闭发往 Anthropic 的非必要流量 | `env` 中的 `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` |

### 4.2 一个起步配置

```json
{
  "permissions": {
    "deny": [
      "Read(**/.env)", "Read(**/.env.*)", "Read(~/.aws/credentials)", "Read(~/.ssh/**)",
      "Bash(git push --force*)", "Bash(git push -f*)",
      "Bash(curl * | sh)", "Bash(sudo *)"
    ],
    "disableBypassPermissionsMode": "disable"
  },
  "sandbox": {
    "enabled": true,
    "network": {
      "allowedDomains": ["github.com", "*.github.com", "*.npmjs.org", "pypi.org", "*.internal.acme.com"]
    }
  },
  "allowManagedMcpServersOnly": true,
  "allowedMcpServers": [
    { "serverUrl": "https://mcp.acme.internal/*" }
  ],
  "availableModels": ["opus", "sonnet", "haiku"],
  "minimumVersion": "2.1.250"
}
```

起步配置宁松勿紧:先拦住真正危险的(凭据、强推、提权、未审批的 MCP),再根据使用情况收紧。限制太多,开发者会觉得"什么都要点确认",然后去找绕过的办法。

### 4.3 权限和沙箱是两层

**权限规则拦的是 Claude 的工具调用,沙箱拦的是进程实际能做的事**。禁止了 `WebFetch` 工具,但允许 `Bash`,`curl` 和 `wget` 照样能访问任何地址;沙箱的网络白名单在操作系统层面补上这个缺口(04 篇)。要可靠地限制外网访问,两者都要配。

## 五、度量:成本与效果

### 5.1 心里先有个数

官方给出的企业部署平均水平:**每个开发者每个活跃日约 13 美元,每月 150-250 美元,90% 的用户每个活跃日低于 30 美元**。差异主要来自模型选择、代码库大小、是否同时开多个会话或跑自动化。用试点数据建立你们自己的基线,而不是照搬这个数字。

### 5.2 在哪里看

| 你的接入方式 | 看花费 | 限制花费 | 按人统计 |
| --- | --- | --- | --- |
| Teams / Enterprise | 组织分析里的花费报表 | 管理后台的花费上限(组织、分组、个人) | 花费报表 CSV;Enterprise Analytics API |
| Console | Console 的用量页 | 工作区花费上限 | Console 看板;Claude Code Analytics API |
| 云平台 | 云平台账单 | 云平台预算控制,或网关的按人限额 | OpenTelemetry 或网关 |

- 开发者自己用 `/usage` 看当前会话的花费、缓存命中情况,以及按 skill、子 agent、插件、MCP server 拆分的用量和优化建议
- 采用情况(日活、会话数、贡献的代码行数)看 analytics 看板
- 公司按合同价结算时,托管设置里配 `modelPricing`,让 `/usage` 和遥测里的金额按合同价计算
- Console 方式下,团队的限流可以参考官方建议:规模越大,每人分到的 TPM 越少(5-20 人每人 10-15 万 TPM,100-500 人每人 1.5-2 万),因为同时在用的人比例会下降

### 5.3 OpenTelemetry:接进自己的监控

OpenTelemetry 是**唯一一种对所有接入方式都适用、而且近实时的方式**,能把按人的 token 和成本指标送进你们自己的监控系统:

```bash
export CLAUDE_CODE_ENABLE_TELEMETRY=1
export OTEL_METRICS_EXPORTER=otlp
export OTEL_LOGS_EXPORTER=otlp
export OTEL_EXPORTER_OTLP_ENDPOINT=https://otel.acme.internal:4318
export OTEL_RESOURCE_ATTRIBUTES="department=engineering,team.id=platform,cost_center=eng-123"
export OTEL_METRICS_INCLUDE_REPOSITORY=true      # 按仓库归因
```

这些通常通过托管设置的 `env` 统一下发。常用的指标和事件:

| 名称 | 内容 |
| --- | --- |
| `claude_code.cost.usage` | 估算花费 |
| `claude_code.token.usage` | token 用量(按类型、模型) |
| `claude_code.session.count` | 会话数 |
| `claude_code.lines_of_code.count` | 增删的代码行数 |
| `claude_code.commit.count`、`claude_code.pull_request.count` | 提交数、PR 数 |
| `claude_code.active_time.total` | 活跃时间 |
| `claude_code.code_edit_tool.decision` | 编辑被接受还是拒绝 |
| 事件:API 请求、工具结果、权限决定、MCP 连接、hook 执行…… | 审计和排查 |

用 `OTEL_RESOURCE_ATTRIBUTES` 加上部门、团队、成本中心,就能按团队出报表和设告警。事件可以送进 SIEM,回答"谁在什么时候让 Claude 执行了什么命令"这类安全问题。

### 5.4 看效果,不只看花费

花费是最容易统计的,但真正要回答的是"值不值"。几个比"代码行数"更有意义的观察点:

- 试点团队在某类任务(写测试、迁移、修 bug)上的周期变化
- PR 被打回的比例、上线后的缺陷率有没有变差
- 开发者的主观反馈:哪些场景省了时间,哪些反而更费劲
- 自动化(CI 审查、定时任务)替代了多少重复劳动

## 六、数据与合规

| 问题 | 答案 |
| --- | --- |
| 会拿我们的代码训练模型吗? | **Teams、Enterprise、API、云平台等商业条款下不会**,除非你主动选择提供数据(比如参加开发合作计划)。个人的 Free / Pro / Max 账号取决于用户自己的设置 |
| 数据保留多久? | 商业账号标准保留 30 天;符合条件的 Enterprise 组织可以申请**零数据保留**(ZDR),需要单独开通 |
| 本地留了什么? | 会话记录以明文存在 `~/.claude/projects/`,默认保留 30 天以便恢复会话,用 `cleanupPeriodDays` 调整 |
| 能满足 HIPAA 吗? | 开启了 HIPAA 的 Enterprise 组织有专门的配置,部分功能会被关闭 |
| 能把流量留在指定区域吗? | 走云平台的区域端点,或通过网关路由 |
| `/feedback` 会上传什么? | 用户确认后才上传对话记录;ZDR 组织、关闭了反馈的组织不会上传 |

落地时还要处理的几件事:

- **仓库里的密钥**:用 deny 规则禁止读取 `.env`、凭据文件;更根本的是不要把密钥放进仓库
- **个人数据**:如果 Claude 会接触到生产数据(通过 MCP 查客户信息),要按数据保护的要求评估,并在 MCP server 一侧做最小化和脱敏(37 篇)
- **第三方 MCP server 和插件**:它们会看到 Claude 发给它们的数据,纳入供应商评估,用白名单管控(38 篇)
- **审计需求**:需要逐请求审计时,用网关;需要操作审计时,用 OpenTelemetry 事件

## 七、融入工程流程

工具配好了,真正决定效果的是团队怎么用它。

### 7.1 仓库是配置的家

- **CLAUDE.md 进仓库,像代码一样评审**。它是团队约定的一部分,改动要走 PR。Claude 犯了一个错,修正 CLAUDE.md,而不是每个人各自在对话里纠正
- 团队通用的 skills、子 agent、hooks 打包成**团队 plugin**,放进公司的插件市场(14 篇);项目专用的放在仓库的 `.claude/` 里
- 项目需要的 MCP server 写进 `.mcp.json`,新人克隆仓库就能用

### 7.2 责任不变

- **提交代码的人对代码负责**,不管它是谁写的。"这是 Claude 写的"不是合并一段没看懂的代码的理由
- AI 参与的改动**照常经过测试和审查**。测试是最好的安全网:Claude 在有测试的代码库里表现明显更好,也更容易发现它的错误
- 鼓励**小 PR**:大量 AI 生成的改动塞进一个 PR,审查者根本看不过来
- PR 描述里说清楚改了什么、为什么、怎么验证的——可以让 Claude 写,但提交者要确认它是对的

### 7.3 自动化

当团队对交互式使用有了信心,再把它延伸到流程里:

- PR 自动审查:官方 Code Review 或 GitHub Actions(22 篇),或者自己用 Agent SDK 做(35 篇)
- 定时任务:依赖升级、文档同步、告警整理(18-19 篇,31 篇的定时部署)
- 内部能力:把常用的内部系统做成 MCP server,开发者、自动化、托管 agent 共用(36-39 篇)

### 7.4 培训与分享

- 官方的 Claude Code 101、Claude Code in Action 课程可以作为入门材料
- 每个团队有一两个熟练的人,负责维护团队的 CLAUDE.md 和 plugin,解答问题
- 定期分享好用的 skills、提示方式和踩过的坑——它们是团队的资产,不该只留在某个人的 `~/.claude/` 里

## 八、常见的顾虑和应对

| 顾虑 | 应对 |
| --- | --- |
| 安全团队:"它会不会执行危险命令、泄露数据?" | 托管的 deny 规则 + 沙箱网络白名单 + MCP 白名单 + 禁用 bypass 模式;OpenTelemetry 事件进 SIEM |
| 财务:"成本会不会失控?" | 试点建立基线;花费上限;按团队的遥测报表和告警 |
| 技术负责人:"代码质量会不会下降?" | 审查和测试照常;小 PR;CLAUDE.md 写清楚团队的质量标准;看缺陷率的变化 |
| 开发者:"AI 写的代码没人懂" | 要求提交者能解释每一处改动;让 Claude 解释和写文档;复杂改动先用 plan mode 讨论方案 |
| 开发者:"每一步都要确认,太烦了" | 用 auto mode 或合理的 allow 规则减少确认,把真正危险的交给 deny 和沙箱(04 篇) |
| 法务:"数据会被拿去训练吗?" | 商业条款下不会;需要更严格的,申请 ZDR |

## 十、踩坑

1. **一上来就全公司铺开**——没有基线、没有规范,问题集中爆发。先试点
2. **只发账号不给方法**——每个人从零摸索,大部分人停留在"偶尔问个问题"
3. **团队规范放在个人目录**——每个人的版本都不同。进仓库、进 plugin
4. **用 HKCU 注册表或用户设置下发安全策略**——普通用户就能改
5. **只禁了 WebFetch 就以为断了外网**——Bash 里的 curl 照样能出去,配沙箱网络白名单
6. **限制配得太紧**——处处要确认,开发者会想办法绕过。先拦真正危险的
7. **只看代码行数衡量效果**——行数多不等于价值高,看周期、缺陷率和反馈
8. **AI 生成的大 PR 直接合并**——审查形同虚设。小 PR,提交者负责
9. **第三方 MCP server 和插件不做评估**——它们能看到 Claude 发给它们的数据
10. **按列表价算成本,和账单对不上**——合同价用 `modelPricing` 配置

## 结语

这个系列从"Claude Code 是什么"讲起,一共七层:

1. **用 Claude Code**(01-09):工具、权限、会话、记忆、模型、计划模式、界面
2. **扩展 Claude Code**(10-15):skills、hooks、MCP、子 agent、plugins、mods
3. **并行、自动化与多端**(16-22):worktree 和 agent teams、dynamic workflows、无人值守、云端会话、多端协作、浏览器与 computer use、代码审查与 CI
4. **Claude API**(23-31):模型和 SDK、工具调用、缓存、思考与 effort、文档、服务端工具、长对话、成本、Managed Agents
5. **Claude Agent SDK**(32-35):把 Claude Code 当库用,以及一个完整的 PR 审查 agent
6. **MCP Server 开发**(36-39):按 2026 年的协议写 server、企业场景、安全与远程化、进阶原语
7. **设计与团队落地**(40-42):扩展机制选型、agent 设计、团队和企业落地

贯穿始终的几条线索:**先理解它怎么工作,再决定怎么用它**;**确定的事交给程序,需要判断的事交给模型**;**能力越强,越要先想清楚它不该做什么**;以及**从最简单的方案开始,有了明确的信号再加复杂度**。

Claude Code 和 Claude API 的更新非常快,这个系列写于 2026 年 10 月,具体的参数、版本号、功能可用性以官方文档和更新日志为准。但这些原则,应该能比具体的命令活得更久。

# 云端会话与 Routines

本地会话有一个天然限制:**你的电脑得开着,终端得开着**。合上笔记本,任务就停了。云端会话把 Claude Code 搬到云上的虚拟机里运行:你在浏览器、手机、Desktop 或终端里发起任务,然后就可以走开,它在云上继续跑,做完开好 PR 等你回来看。

这一篇讲云端会话本身、它跑在什么样的环境里、怎么在终端和云之间转移任务、云端定时任务(以前叫 routines),以及让 Claude 统筹一大块工作的 Projects。

> 一句话先记住:**云端会话适合"派出去、不用盯"的任务**。它从你的仓库全新克隆,看不到你本机的文件、工具、个人配置;它不需要你的电脑开着。需要本地环境的任务留在本地,或者用 20 篇的 Remote Control。

---

## 一、云端会话是什么

一个在云端基础设施上运行的 Claude Code 会话。默认跑在 Anthropic 托管的虚拟机上,也可以跑在你们组织自建的运行环境里(见第六节)。

可以从这些地方发起:

- **浏览器**:claude.ai/code(Claude Code on the web)
- **手机**:Claude App 的 Code 标签页
- **Desktop App**:新建会话时选 **Cloud** 而不是 **Local**
- **终端**:`claude --cloud "..."`
- **云端定时任务**:每次触发都是一个云端会话

可用于 Pro、Max、Team 计划,以及有相应席位的 Enterprise 用户。启用了零数据保留(ZDR)或 HIPAA 配置的组织不能用云端会话。

### 1.1 连接 GitHub

云端会话要克隆代码、推送分支,需要 GitHub 访问权限:

| 方式 | 能访问的仓库 | 适合 |
| --- | --- | --- |
| **Claude GitHub App** | 公开仓库,以及装了这个 App 的私有仓库 | 网页上开通;需要 auto-fix、Projects 的团队 |
| **`/web-setup`** | 你本地 `gh` 令牌能访问的所有仓库 | 已经在用 `gh` 的个人开发者 |

在 Anthropic 托管的环境里,**你的 GitHub 凭证加密存在 Anthropic 服务器上,从不进入会话的虚拟机**,虚拟机里的 git 操作经由一个 GitHub 代理附加凭证。

## 二、云端环境

每个云端会话都运行在一个"环境"里:一份保存好的配置,决定网络访问、环境变量、启动脚本。第一次使用时会建一个 **Default** 环境。

### 2.1 预装了什么

Ubuntu 24.04,预装常见语言运行时和工具:Python 3(pip、poetry、uv、ruff、pytest……)、Node.js 20/21/22(npm、pnpm、yarn、bun……)、Ruby、PHP、Java 21(Maven、Gradle)、Go、Rust、C/C++,还有 Docker、PostgreSQL 16、Redis 7 和 `gh`、`jq`、`ripgrep` 等常用工具。资源大约是 **4 核 CPU、16GB 内存、30GB 磁盘**,特别吃内存的构建可能被终止。

### 2.2 网络访问

| 级别 | 出站连接 |
| --- | --- |
| **None** | 不能通过会话网络访问外部 |
| **Trusted**(默认) | 只能访问白名单域名:包管理仓库、GitHub、云厂商 SDK 等 |
| **Full** | 任意域名 |
| **Custom** | 你自己的白名单,可以包含默认列表 |

无论哪个级别,都能访问:GitHub(走单独的代理)、你启用的 MCP connectors(流量走 Anthropic 服务器)、Anthropic API。

### 2.3 密钥怎么给

**不要把密钥写进环境变量**——用这个环境的人都能读到环境变量和启动脚本。在 Anthropic 托管的环境里,用 **network secrets**:你在环境上添加一次密钥,代理会在请求指定主机时自动附加,密钥本身不进入会话。

### 2.4 启动脚本

```bash
#!/bin/bash
apt update && apt install -y shellcheck
```

会话启动、Claude Code 运行之前执行,以 root 身份运行。三条约束:

- **必须以 0 退出**,否则会话启动失败。非关键命令后面加 `|| true`
- **控制在约 5 分钟以内**:在这个时间内完成,环境会被快照缓存,之后的会话直接从快照启动;超时就不缓存,每次重跑
- 安装依赖需要网络能访问对应的包仓库

启动脚本和 `SessionStart` hook 的区别:启动脚本属于环境、每个环境配一次;hook 属于仓库、提交在 `.claude/settings.json` 里,本地和云端都会跑。

### 2.5 哪些配置会带到云端

云端会话从仓库**全新克隆**,所以:

| 会带过去 | 不会带过去 |
| --- | --- |
| 仓库里的 CLAUDE.md、`.claude/rules/` | 你的 `~/.claude/CLAUDE.md` |
| 仓库 `.claude/settings.json` 里的 hooks 和权限规则 | 你的个人 skills、子代理、命令 |
| 仓库的 `.mcp.json` | 用默认 local / user 作用域 `claude mcp add` 的 server |
| 仓库的 `.claude/skills/`、`agents/`、`commands/` | 插件(即使仓库 settings 里启用了也不装) |
| 组织的 server-managed settings | AWS SSO 这类浏览器交互式认证 |

**想让配置在云端可用,就提交进仓库**。个人偏好不想提交,可以在自己的环境的启动脚本里写一个 `~/.claude/CLAUDE.md`。

## 三、终端和云端之间转移任务

### 3.1 从终端发到云端

```bash
claude --cloud "修复 src/auth/login.ts 里的认证 bug"
```

云端虚拟机克隆的是**当前目录的 GitHub remote 上的当前分支**,不是你的本地检出——有本地提交就先 push。仓库没有 remote,或 GitHub App 没装在这个仓库上时,Claude Code 会把本地仓库打包上传(上限 100MB;macOS / Linux 上会排除 `.env`、`*.pem` 这类敏感文件的未提交改动,原生 Windows 不会,注意先 stash)。

一个好用的组合:**本地 plan,云端执行**——先 `claude --permission-mode plan` 和它对齐方案,再把执行甩到云端。

### 3.2 给运行中的云端会话发消息

```bash
claude -p "下一步把测试覆盖率补到 80%" --cloud session_01DiUkqY...
```

发一条消息就退出,不等回复。可以用来在 CI 脚本里给长时间运行的云端会话追加指令。

### 3.3 把云端会话拉回终端

```bash
claude --teleport                 # 选择器
claude --teleport <session-id>
```

会话里也可以 `/teleport`(`/tp`),或在 `/tasks` 里按 `t`。teleport 会检查你在同一个仓库、工作区干净、分支已推送、登录的是同一个账号,然后拉取分支、加载完整对话。

注意方向:**从 CLI 只能把云端会话拉下来,不能把正在进行的本地会话推上去**。`--cloud` 是新建一个云端会话。也别和 `--resume` 混淆:`--resume` 只找本机的会话记录。

## 四、管理云端会话

- **权限模式**:创建任务时和运行中都可以在下拉框里选
- **审查改动**:在 claude.ai/code 里看 diff,满意了直接开 PR
- **分享**:把会话分享给队友
- **闲置**:几分钟没有活动,虚拟机会暂停并保存文件;Claude 问了你问题后闲置,你回来还能接着回答,直到环境过期

### 4.1 Auto-fix:盯着 PR 自动修

```
/autofix-pr          # 在 PR 的分支上运行
```

或在云端会话的 CI 状态栏里打开 **Auto-fix**,或直接对它说"盯着这个 PR,修掉所有 CI 失败和评审意见"。之后:

- **明确的修复**:改、推、在会话里说明
- **有歧义的评审意见**或涉及架构的改动:先问你
- **重复或无需改动的事件**:记一笔,跳过

需要仓库装了 Claude GitHub App。它**感知不到 base 分支前进造成的合并冲突**(GitHub 不发这个事件),要你手动让它 rebase。它回复评审意见时用的是**你的 GitHub 账号**,但会标注来自 Claude Code。

## 五、云端定时任务(Routines)

### 5.1 是什么

一份保存好的 Claude Code 配置——**一个 prompt、一个或多个仓库、一组 connectors**——在云端自动运行。以前叫 routines,现在叫 cloud scheduled tasks,部分地方仍沿用旧名。研究预览阶段。

三种触发器,可以组合:

| 触发器 | 什么时候运行 |
| --- | --- |
| **Schedule** | 按周期(每小时、每天、每周、自定义 cron),或在某个时间点运行一次 |
| **API** | 有人带 bearer token POST 到这个任务的专属地址 |
| **GitHub** | 仓库发生指定事件,如 `pull_request.opened`、release |

### 5.2 创建

在 claude.ai/code/routines、Desktop App,或在 CLI 里:

```
/schedule 每天早上 9 点审查新开的 PR
/schedule 明天上午 9 点,总结昨天合并的 PR
/schedule 两周后,开一个删除这个 feature flag 的清理 PR
```

`/schedule` 会以对话的形式问清楚时间、仓库和 prompt。API 触发器在网页上配置;GitHub 触发器可以在网页或 CLI 里加,需要仓库装 Claude GitHub App。

### 5.3 典型用途

- **待办维护**:每个工作日晚上读新开的 issue,打标签、分配负责人
- **告警分诊**:监控系统在错误超阈值时调用 API 触发器,把告警内容传进来,让 Claude 调查
- **定制化代码审查**:新 PR 时按团队自己的清单审查,留行内评论
- **部署验证**:CD 流水线每次发布后调用,跑冒烟检查、扫错误日志,给出放行或回滚建议
- **文档漂移检查**:每周扫描合并的 PR,找出引用了已变更 API 的文档,开 PR 更新

### 5.4 要注意的

- **它自主运行,不选权限模式**,不会停下来问你。它能碰到什么,完全由你选的仓库、环境的网络和变量、包含的 connectors 决定——**每一项都只给任务需要的**
- 定时任务**属于你个人的 claude.ai 账号**,不和队友共享,消耗你的额度。它通过 connectors 做的事都是以你的身份
- 整点运行可能延迟几分钟,想准时就选 9:07 这样的时间
- 最短间隔 1 小时;GitHub 事件有每小时上限,超出的会被丢弃
- Team / Enterprise 的 Owner 可以在组织设置里关掉这个功能

## 六、自建运行环境(self-hosted environments)

代码不能离开公司网络,又想用云端会话的体验?自建运行环境让**云端会话在你们自己的基础设施上执行**:

| 组成 | 作用 |
| --- | --- |
| **Environment** | 一个命名的目的地,在 claude.ai 管理后台创建,下面挂一组 runner |
| **Runner** | 跑在你们网络里的程序,执行会话,类似自建的 CI runner |
| **Session** | 开发者发起的一个任务 |

开发者发起云端会话时,环境选择器里会同时列出 Anthropic 托管的环境和你们自建的。选了自建的,Anthropic 的控制面把会话放进队列,你们的 runner 认领并执行,代码和工具都在你们的网络里。可以常驻一批 runner,也可以用自动扩缩容的编排器按需启动。Team 和 Enterprise 公测中,默认关闭。

## 七、Projects:让 Claude 统筹一大块工作

没有 Project 时,同时跑几个会话意味着**你自己当协调者**:决定每个会话干什么、在每个会话开头重复同样的背景、来回检查哪个完成了哪个在等你。Project 把这件事交给 Claude:

- **一个对话收所有工作**:随时把 bug 报告、报错栈、任务清单贴进来,Claude 为每件事开一个线程(通常是云端会话),或者交给已经在处理相关领域的线程
- **背景只说一次**:每个新线程都从 Project 的指令开始,"PR 都提到 develop 分支"这种规则说一次就够
- **回来看结果**:**Overview** 面板显示哪些线程完成了、哪些 PR 等审、哪个线程在等你回答
- 需要本机才能做的线程,可以让它通过 Remote Control 在你的电脑上跑

适合:**一个目标跨很多仓库**(把所有服务升级到新的 lint 配置)、**一个你持续投喂的领域**、**比一次会话大得多的构建或迁移**,甚至不是代码的工作(反复查询一批上传的合同或工单)。

不适合:一次会话能搞定的单个任务(直接开云端会话)、每个任务都需要你本机环境(用本地会话或 agent view)、没有对话、只是定期重复的任务(用定时任务)。Pro 和 Max 公测中,逐步开放。

## 八、本地、云端、自建怎么选

| 情况 | 选 |
| --- | --- |
| 要盯着改、需要本地工具和文件 | 本地会话 |
| 派出去不用管、不想让电脑一直开着 | 云端会话 |
| 本地没有这个仓库 | 云端会话 |
| 代码不能离开公司网络 | 自建运行环境 |
| 人不在电脑前,但任务需要本机环境 | Remote Control(20 篇) |
| 固定时间、API 调用、GitHub 事件触发 | 云端定时任务 |
| 持续产生任务的一大块工作 | Projects |
| PR 的 CI 失败和评审意见自动处理 | Auto-fix |

## 九、踩坑

1. **有本地提交就 `--cloud`**——云端克隆的是 remote 上的分支,先 push
2. **以为云端有我的个人 skills 和 MCP**——只有提交进仓库的配置会带过去
3. **把 API key 写进环境变量**——用这个环境的人都看得到,用 network secrets
4. **启动脚本超过 5 分钟**——不会被缓存,每个会话都重跑一遍
5. **启动脚本里一个可选安装失败,整个会话起不来**——非关键命令加 `|| true`
6. **想把本地正在进行的会话推到云端**——做不到,只能拉下来;推上去是新建一个
7. **定时任务的仓库、网络、connectors 给太宽**——它完全自主运行,权限面就是你给它的这些
8. **以为队友能看到我建的定时任务**——它属于你个人账号
9. **指望 auto-fix 处理合并冲突**——GitHub 不发这个事件,要你手动让它 rebase
10. **在原生 Windows 上打包上传含敏感文件改动的仓库**——Windows 不会自动排除,先 stash

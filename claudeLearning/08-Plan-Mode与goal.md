# Plan Mode 与 /goal

这一篇讲两个方向相反的控制手段。**plan mode 是刹车**:让 Claude 先调研、出方案,在你点头之前不动源码。**`/goal` 是油门**:给它一个完成条件,它会一轮接一轮地干,直到条件满足才把控制权交还给你。

> 一句话先记住:**plan mode 解决"方向对不对",`/goal` 解决"做没做完"**。大任务的典型节奏是:先在 plan mode 里把方案对齐,再挂一个 `/goal`,让它一直跑到验收标准全部满足。

---

## 一、为什么要先计划

让 Claude 直接开写,最常见的失败不是代码写错,而是**解决了一个错误的问题**:它误解了需求、选了和团队约定不符的方案、改了不该动的模块。官方推荐的工作流分四步:

```
1. 探索   进 plan mode,让它读相关代码、搞清现状
2. 计划   让它出一份具体的实施方案,你来改
3. 实施   批准方案,让它按方案写代码、跑测试
4. 提交   让它写提交信息、开 PR
```

**什么时候该计划**:不确定该怎么做、改动跨多个文件、你自己不熟悉要改的代码。

**什么时候跳过**:改一个 typo、加一行日志、重命名一个变量。**如果你能用一句话描述出 diff,就不需要计划**。

---

## 二、进入 plan mode

| 方式 | 说明 |
| --- | --- |
| `Shift+Tab` | 循环到状态栏显示 `⏸ plan mode on` |
| `claude --permission-mode plan` | 启动就进 plan mode |
| 消息前加 `/plan` | 只对这一条消息生效 |
| Claude 自己提出 | 它判断任务需要先规划时,会调用 `EnterPlanMode` |
| 项目默认 | 在 `.claude/settings.json` 里设 `"defaultMode": "plan"` |

再按一次 `Shift+Tab` 可以不批准方案直接离开 plan mode。

---

## 三、plan mode 下它能做什么

- **能**:读文件、跑只读命令探索代码、向你提问、写方案
- **不能**:改源码
- **探索用的命令**:auto mode 可用时(`useAutoModeDuringPlan` 默认开),由分类器批准,不用你一条条点;否则只读集合以外的命令都会问你

方案写在一个文件里,默认放在 `~/.claude/plans/`。在 settings 里设 `plansDirectory`(相对项目根)可以改到项目目录下,比如 `"./plans"`,方便提交或分享给队友。

**方案文件在上下文压缩后会被重新注入**,所以长任务做到一半压缩了,Claude 依然记得原定计划。

---

## 四、审批方案

方案写好后,Claude 用 `ExitPlanMode` 把它交给你,你有几个选择:

| 选项 | 结果 |
| --- | --- |
| **Yes, and use auto mode** | 批准,切到 auto mode 开始执行(auto 不可用时显示为 Yes, auto-accept edits) |
| **Yes, manually approve edits** | 批准,但每处修改都要你确认 |
| **No, keep planning** | 留在 plan mode,告诉它要改什么 |

几个实用操作:

- **`Ctrl+G`**:在你的编辑器里直接打开并修改方案,改完再让它执行。比在对话里描述"第三步改成……"更精确
- **批准并清空上下文**:打开 `showClearContextOnPlanAccept` 后,列表里会多一个选项,批准方案的同时清掉调研阶段的上下文。调研读了大量文件时很有用——执行阶段只需要方案,不需要那些原始材料
- 批准方案后会话会自动获得一个基于方案的标题

## 五、一份好方案长什么样

```markdown
## 目标
给登录流程加 Google OAuth,保留现有的邮箱密码登录。

## 现状
- 会话管理在 src/auth/session.ts,用 Redis 存 session
- 密钥通过 src/config/secrets.ts 从环境变量读取

## 改动
1. 新增 src/auth/oauth/google.ts:授权跳转和回调处理
2. session.ts 增加 provider 字段,兼容旧 session
3. 新增路由 /auth/google 和 /auth/google/callback
4. .env.example 增加 GOOGLE_CLIENT_ID / GOOGLE_CLIENT_SECRET

## 验证
- pnpm test 全部通过,新增回调处理的单元测试
- 本地起服务,手动走一遍 Google 登录和旧的密码登录

## 风险与回滚
- session 结构变化:旧 session 没有 provider 字段,按 "password" 处理
- 回滚:回退本次提交即可,不涉及数据迁移

## 不在本次范围
- 不做账号合并(同邮箱的 Google 账号和密码账号)
- 不改前端登录页样式
```

要点:

- **写清"不在范围"**,防止它顺手改一堆你没要的东西
- **写出验证方式**,执行阶段它才知道什么叫"做完了"
- **点名具体文件和接口**,方案越具体,执行越不跑偏

## 六、大功能:先让 Claude 采访你

需求本身还模糊时,与其自己写一大段说明,不如让 Claude 来问:

```
我想做 [一句话描述]。用 AskUserQuestion 工具详细采访我。
问技术实现、交互、边界情况、顾虑和取舍。别问显而易见的问题,
挖那些我可能还没想到的难点。问完之后把完整的需求写进 SPEC.md。
```

它会用选择题形式一轮轮问你。规格写完后,**开一个新会话去实现**——新会话的上下文干干净净,只围绕实现,而你手里有一份书面规格可以对照。

好的规格是自包含的:点名涉及的文件和接口、写明不做什么、最后有一个端到端的验证步骤证明功能可用。

## 七、opusplan:计划用 Opus,执行用 Sonnet

模型设成 `opusplan`,在 plan mode 下自动用 Opus 做推理和架构决策,执行阶段切到 Sonnet 写代码。

代价是**每次进出 plan mode 都是一次模型切换**,缓存会失效。来回切换频繁的工作方式不适合它。需要"主模型自己判断什么时候请教更强模型",用 07 篇的 advisor。

## 八、/goal:设定完成条件

### 8.1 它是什么

```
/goal test/auth 下所有测试通过,并且 lint 没有报错
```

设定后立即开始一轮工作,条件本身就是指令。每一轮结束,一个小模型会检查条件是否满足:

- **还没满足**:Claude 接着干,把评估给出的理由当作下一步的方向
- **满足了**:清除目标,记录一条"已达成"
- **不可能满足**:清除目标,记录失败原因

状态栏会显示 `◎ /goal active` 和已运行时长。按 `Ctrl+O` 能看到每次评估的理由。

### 8.2 和其他"让它继续跑"的方式的区别

| 方式 | 下一轮何时开始 | 何时停 |
| --- | --- | --- |
| `/goal` | 上一轮结束后 | 评估模型确认条件满足或不可能 |
| `/loop`(18 篇) | 到了时间间隔 | 你停止,或 Claude 判断做完了 |
| Stop hook(11 篇) | 上一轮结束后 | 你自己的脚本或 prompt 决定 |

`/goal` 本质上是一个**只在当前会话生效的 prompt 型 Stop hook**。需要确定性检查(真正跑一个脚本判断)或者对所有会话生效,就自己写 Stop hook。

> **auto mode 本身不会开启新一轮**。它只是在一轮之内自动批准工具调用,Claude 认为做完了就停。`/goal` 加的是一个独立的评估者,"做没做完"由它而不是由干活的模型判断。

### 8.3 怎么写条件

**评估模型不会自己跑命令、读文件**,它只看对话里 Claude 已经展示出来的东西。所以条件要写成"Claude 的输出能证明"的形式:

| 不好 | 好 |
| --- | --- |
| "代码质量变好" | "`pnpm lint` 输出 0 个错误" |
| "迁移完成" | "`grep -r oldApi src/` 没有结果,并且 `pnpm test` 退出码为 0" |
| "测试都过了" | "`npm test` 退出码为 0,且没有修改任何已有的测试文件" |

一个能撑过很多轮的条件通常有三部分:

1. **一个可度量的终态**:测试结果、构建退出码、文件数量、空队列
2. **明确的检查方式**:用什么命令证明
3. **必须遵守的约束**:过程中不能改什么

想给它设上限,在条件里加一句"或者 20 轮后停止"。条件最长 4,000 字符。

### 8.4 常用命令

```
/goal <条件>     设定(已有目标时会替换)
/goal            查看状态:条件、时长、已评估轮数、token 花费、最近一次理由
/goal clear      清除(stop、off、cancel 等也行)
```

`/clear` 开新对话也会清除目标。**恢复会话时,仍然活跃的目标会被恢复**,轮数、计时和花费基线重置。

非交互模式下一次调用就会跑到底:

```bash
claude -p "/goal CHANGELOG.md 里本周合并的每个 PR 都有对应条目" --output-format stream-json --verbose
```

不加 `stream-json`,中间过程不输出,看起来像卡住了。

### 8.5 什么时候会停下

- **需要你修复的错误会清除目标**:认证失败、余额耗尽、自动压缩也处理不了的上下文溢出、模型不可用
- **其他错误保留目标**:服务器过载、断线会自动重试,三次后暂停;限流、用量上限、hook 结束了这一轮会直接暂停,等你处理
- **原地打转**:连续几轮没有任何工具调用、只是在回应评估者,会停下并提醒你,目标仍保留
- **后台任务还在跑**:这一轮跳过评估,等后台任务结束后再评估;后台任务拖了 30 分钟,会触发一次检查,让 Claude 看看任务是在推进还是卡住了

### 8.6 权限

**`/goal` 不改变权限模式**。在 Manual 模式下,每个没被放行的命令还是会停下来问你,目标也就推进不下去。想让目标无人值守地跑完,在 auto mode 下设 `/goal`。

## 九、组合起来:一个大任务的完整节奏

```
1. Shift+Tab 进 plan mode
   "读一下 src/payments,我想把 Stripe SDK 从 v12 升到 v16,出个方案"

2. 审方案,Ctrl+G 补上"不改 webhook 签名校验逻辑"
   选 Yes, and use auto mode(或批准并清空上下文)

3. 设目标
   /goal pnpm typecheck 和 pnpm test 都退出码为 0,
         src/ 里不再有 stripe v12 的 import,并且没有修改 tests/fixtures/,
         或者 30 轮后停止

4. 去干别的。回来看 /goal 状态和会话回顾

5. 达成后审 diff,让它提交并开 PR
```

## 十、踩坑

1. **小改动也进 plan mode**——一句话说得清的改动,计划只是额外开销
2. **方案没写"不在范围"**——它会顺手做一堆你没要求的改动
3. **方案里没有验证步骤**——执行阶段不知道什么算完成
4. **在对话里口头修改方案**——用 `Ctrl+G` 直接编辑方案文件更准确
5. **调研上下文太大直接开干**——批准时清空上下文,或者开新会话按方案执行
6. **`/goal` 条件写得主观**——"代码更优雅"无法评估。写成命令和退出码
7. **以为评估模型会自己跑测试**——它只看对话。条件里写明用什么命令证明,Claude 会去跑并展示结果
8. **在 Manual 模式下挂 `/goal` 然后走开**——第一个需要授权的命令就停住了。用 auto mode
9. **不给目标设上限**——条件可能永远达不到。加"或者 N 轮后停止"
10. **频繁进出 plan mode 又用着 `opusplan`**——每次切换都让缓存失效

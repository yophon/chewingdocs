# Claude Code 总览与心智

aiLearning/38 里讲过 Coding Agent 的通用骨架:**主循环 + 文件/终端工具 + 模型**。Claude Code 就是这个骨架 Anthropic 自己做出来的版本。它最早是一个跑在终端里的 CLI,到 2026 年已经长成一整套产品:终端、VS Code / JetBrains、桌面 App、浏览器里的云端会话、手机、Slack、CI——**但所有这些界面背后跑的是同一个内核**。

> 一句话先记住:**Claude Code 不是"一个终端工具",而是一个 agent harness(Agent 外壳)**。模型负责推理,harness 负责给模型工具、管理它看到的上下文、守住权限边界。你学的是这个 harness 的用法,换到哪个界面都通用。

---

## 一、Agent harness:模型 + 工具 + 上下文管理

### 1.1 主循环的三个阶段

你给 Claude 一个任务,它会在三个阶段之间反复循环:

```
收集上下文(读文件、搜代码、看 git 状态)
    ↓
采取行动(改文件、跑命令、调外部服务)
    ↓
验证结果(跑测试、跑 lint、读输出)
    ↓
没完成 → 回到第一步,带着新信息继续
```

问一个关于代码的问题,可能只需要第一阶段;修一个 bug 会把三个阶段转好几圈;一次重构的大部分时间可能都花在验证上。**每一步做什么,由模型根据上一步学到的东西决定**——这就是"agentic"的含义。

你也在这个循环里:

- **按 `Esc`**:立刻停下,当前工具调用被取消,等你下一句话
- **直接打字回车**:不打断它,消息进入队列,Claude 在当前这批工具调用结束后马上读到并调整方向

### 1.2 工具是"能动手"的来源

没有工具,模型只能回文字;有了工具,它能动手。内置工具大致分五类:

| 类别 | 能做什么 |
| --- | --- |
| 文件操作 | 读文件、改代码、建文件、重命名和整理目录 |
| 搜索 | 按模式找文件、按正则搜内容、探索陌生代码库 |
| 执行 | 跑 shell 命令、起服务、跑测试、用 git |
| Web | 搜索网页、抓文档、查报错信息 |
| 代码智能 | 改完文件后看到类型错误、跳转定义、找引用(需要装语言服务插件) |

此外还有派子代理、向你提问、管理任务清单这类"编排工具"。完整清单和每个工具的权限规则在 03 篇。

### 1.3 Harness 替你管上下文

模型每一轮能看到的东西都由 harness 组装:

- **你的项目**:当前目录及子目录的文件,其他位置要你授权
- **你的终端**:任何你能在命令行跑的东西
- **git 状态**:当前分支、未提交的改动、最近的提交
- **CLAUDE.md**:你写给它的项目说明;仓库里只有 `AGENTS.md` 的话它也能读
- **auto memory**:它自己在工作中记下的经验,`MEMORY.md` 的前 200 行(或前 25KB)在每次会话开始时加载
- **你配置的扩展**:MCP server、skills、子代理等

harness 还会主动往对话里塞一些东西,比如文件在磁盘上被改了的提醒、提交信息里的署名行。**如果 Claude 遵守了一条你没写过的规则,多半是 harness 加的**——这些都能在 settings 里关掉(02 篇)。

## 二、为什么"终端原生"这个出发点仍然重要

Claude Code 现在有图形界面了,但它的设计底色仍然是终端:

1. **终端 = 整台电脑的能力**。`gh`、`docker`、`kubectl`、`psql`、任何脚本,它都能直接用,不需要谁去给它"加插件"
2. **可脚本化**。`claude -p "review this PR"` 可以直接当命令用,能进 CI、能在远程服务器上跑、能被别的程序调用(18 篇)
3. **工具回归本质**。读、写、搜、跑命令——Claude Code 没有发明一套 IDE 概念,它认为"文件 + 命令"已经能表达程序员要做的所有事

**图形界面是给人看的,内核依然是命令行的思路**。理解这一点,你在桌面 App 和云端看到的各种功能就都能对上号。

## 三、在哪里用:界面与执行环境

### 3.1 界面

| 界面 | 适合什么 | 特点 |
| --- | --- | --- |
| **CLI(终端)** | 终端工作流、脚本、远程服务器 | 功能最全;脚本化和 Agent SDK 只有 CLI 有 |
| **Desktop App** | 看 diff、并行开多个会话 | 可视化 diff、应用预览、内置浏览器、定时任务 |
| **VS Code / JetBrains** | 不想离开编辑器 | 行内 diff、选区上下文、计划审阅 |
| **Web(claude.ai/code)** | 不用怎么盯的长任务、本地没有的仓库 | 跑在云端,你断开后继续跑 |
| **手机** | 出门在外时发起和盯任务 | 云端会话 + 遥控本机会话 |
| **Slack / CI** | 团队里 @Claude、PR 自动审查 | 从聊天和流水线里派任务 |

**同一个项目可以混着用**。CLAUDE.md、settings、MCP server 在本地的几个界面之间是共享的。

### 3.2 执行环境

界面决定"你怎么看",执行环境决定"代码在哪跑":

| 环境 | 代码跑在哪 | 用途 |
| --- | --- | --- |
| **本地** | 你的电脑 | 默认。能访问你所有的文件、工具和环境 |
| **云端** | Anthropic 托管的虚拟机,或组织自建的环境 | 把任务甩出去、处理本地没有的仓库 |
| **Remote Control** | 你的电脑,但从浏览器或手机操控 | 人不在电脑前,文件和执行都留在本地 |

> 选界面的心法:**要盯着改的用本地(CLI / IDE / Desktop),派出去不想管的用云端,人走了还想接着管本地会话的用 Remote Control**。19、20 篇细讲。

## 四、扩展层地图

Claude Code 真正强大的地方是扩展面。2026 年的扩展层比早期多了不少,但可以按"什么时候加载、谁来触发"分成几组:

```
常驻上下文     CLAUDE.md / .claude/rules/ / output style
               → 每次会话都在,写"一直要遵守"的东西

按需加载       Skills(含自定义 /命令) / MCP 工具
               → 用到才加载,写"有时候需要"的知识和流程

隔离执行       Subagents / Dynamic workflows
               → 在独立上下文里干活,只把结论带回来

确定性触发     Hooks
               → 事件发生就一定执行,不经过模型判断

打包与分发     Plugins / Marketplace
               → 把上面这些打成一个包,装到别的仓库、发给别人

改造界面       Mods
               → 给 Claude Code 自己加面板、命令、工具调用规则
```

| 扩展 | 干什么 | 谁触发 | 例子 |
| --- | --- | --- | --- |
| **CLAUDE.md** | 每次会话都加载的项目说明 | 自动 | "用 pnpm 不用 npm,提交前跑测试" |
| **Skill** | 可复用的知识和工作流 | 你输 `/名字`,或模型按描述匹配 | `/deploy` 部署清单、API 风格指南 |
| **MCP** | 接外部系统 | 模型调用 | 查数据库、发 Slack、控浏览器 |
| **Subagent** | 在独立上下文里跑子任务 | 模型派发 | 读几十个文件只回一段结论 |
| **Hook** | 生命周期事件上跑脚本 | harness 自动 | 每次改完文件跑 ESLint |
| **Plugin** | 把以上打包分发 | 你安装 | 团队统一的一套 skills + hooks + MCP |

> 两个变化要特别注意:**自定义斜杠命令已经并入 Skills**——`.claude/commands/deploy.md` 和 `.claude/skills/deploy/SKILL.md` 都会生成 `/deploy`,旧文件继续能用;**Plugins 成了正式的分发层**,团队共享配置不再靠复制粘贴。

选层的原则没变:**按"谁触发、多久加载一次"来选**。必须每次都发生的事放 hook,一直要知道的放 CLAUDE.md,偶尔需要的放 skill,会污染上下文的子任务交给 subagent。40 篇会把这些放在一起做选型。

## 五、两道安全网:检查点和权限

### 5.1 检查点:文件改动可撤销

Claude 改文件前会先给文件拍快照。改坏了,**连按两下 `Esc`** 回退到之前的状态,或者直接让它撤销。检查点独立于 git,恢复会话后仍然可用。

但它**只管文件**。改了数据库、调了外部 API、发布了服务——这些动作撤不回来,只能靠权限去拦。

### 5.2 权限模式:决定它什么时候需要问你

按 `Shift+Tab` 在几种模式之间切换:

| 模式 | 行为 |
| --- | --- |
| **Auto** | 后台分类器审查每个动作,危险的直接拦下,其余放行。交互式终端和 VS Code 会话的默认模式 |
| **Manual** | 改文件、跑 shell 命令前都问你 |
| **Accept edits** | 改文件和 `mkdir`、`mv` 这类常见文件命令不问,其他命令仍然问 |
| **Plan** | 只调研、出方案,不改源码 |

再配合 settings 里的允许/拒绝规则(比如永远放行 `npm test`、永远拦截读 `.env`),就构成了完整的权限体系。03、04 两篇细讲。

## 六、心智差别:派任务,而不是提问

很多人第一次用 Claude Code,带着用聊天机器人的习惯:"我问一个问题,你回答我"。这样用浪费了它一大半能力。

正确用法是**告诉它要完成的目标**:

| 不好的用法 | 好的用法 |
| --- | --- |
| "怎么改这个 bug?" | "把这个 bug 修了,跑测试通过" |
| "这段代码什么意思?" | "给这段代码加注释,把调用关系讲清楚" |
| "我的部署有问题" | "排查生产环境为什么 502,看 nginx 日志和最近的提交" |
| "Redis 怎么配?" | "把项目接入 Redis,用 ioredis,配置走环境变量" |

**你的角色从"提问者"变成"项目负责人"**。像委托一个能干的同事那样:给背景、给方向、给验收标准,细节让它自己找。

两个配套习惯:

- **不必一次写出完美指令**。先说要什么,第一次没对就接着纠正:"不对,问题在 session 处理那块"。你是在迭代,不是重来
- **给它验证手段**。"跑这几个测试"、"打开页面截图看看"、"对比改动前后的输出"——有了验证手段,它才能自己发现错误并修正

## 七、什么场景该用,什么场景不该

### 该用

- **重复性工作**:补测试、修全项目的 lint、解合并冲突、升依赖、写发布说明
- **跨文件改造**:重命名一个 API、统一一套写法、升级一个框架版本
- **不熟悉的领域**:第一次接 Stripe、第一次写 Flutter、第一次配 K8s
- **调试**:让它跑命令、看日志、缩小范围、定位问题
- **长任务**:迁移、审计、批量改造,可以派到云端或交给多个 agent 并行(16-19 篇)
- **跨工具串联**:issue → 写代码 → 开 PR → 写描述 → 跑测试

### 不该用

- **极小的改动**:改一个 typo、加一行日志,自己改更快
- **核心架构决策**:让它给方案可以,**最终拍板必须是你**
- **你完全看不懂的代码**:它写的你看不懂,等于你丢掉了对系统的控制权
- **严格保密的代码**:代码会发送到模型服务,**按公司合规策略来**(42 篇讲零数据保留等选项)

> 一条硬规则:**你看不懂的 PR 不要合并**。Claude Code 帮你写得快,但评审责任永远在你。

## 八、和同类产品的关系

Coding Agent 大致有三种形态,各有代表:

| 形态 | 代表 | 强项 |
| --- | --- | --- |
| **编辑器内嵌** | Cursor 这类 AI IDE | 交互式写代码、补全、行内编辑 |
| **终端 / harness 型** | Claude Code、Codex CLI | 自动化、脚本化、扩展性 |
| **云端自治型** | Devin 这类平台 | 派出去不管的长任务 |

Claude Code 现在横跨后两种,还通过 IDE 扩展覆盖了第一种的一部分场景。**真正的差异不在"有没有界面",而在扩展体系和自动化能力**——这也是本系列花最多篇幅的地方。

## 十、给新手的最快入门路径

1. **装上**:macOS / Linux / WSL 执行 `curl -fsSL https://claude.ai/install.sh | bash`;Windows PowerShell 执行 `irm https://claude.ai/install.ps1 | iex`。装完开新终端跑 `claude --version`
2. **进一个真实项目**:`cd your-project && claude`,第一次会提示登录
3. **跑 `/init`**:让它读一遍项目,生成第一版 CLAUDE.md,然后你删改
4. **派一个真任务**:别问"你能干什么",直接说"给这个项目加一个 Dockerfile 并跑通构建"
5. **看它怎么干**:读了哪些文件、调了哪些工具、为什么这么改
6. **学会刹车**:`Esc` 停下、两下 `Esc` 回退、`Shift+Tab` 切权限模式、`/clear` 清上下文、`/context` 看上下文占用
7. **出问题跑 `/doctor`**:安装和配置的体检,能自动修一部分问题
8. **第二周开始定制**:写第一个 skill、加第一个 hook、接一个 MCP

> 真正的学习曲线在**派任务的能力**——会拆任务、会给验收标准、知道它哪里靠谱哪里不靠谱。这部分是经验,不是知识。

## 十一、踩坑提醒(总览版,后面每篇细讲)

1. **不读 diff 直接接受**——最常见也最危险。auto mode 让你更少被打断,但**读 diff 的责任没有转移**
2. **大改动不先出计划**——大改先进 plan mode 对齐方案,再执行(08 篇)
3. **CLAUDE.md 没写或写成百科全书**——没写等于每次从零理解项目;写太长又挤占上下文。控制在 200 行以内
4. **把规则写进 prompt 指望它每次遵守**——"禁止改 `.env`"写在 CLAUDE.md 里只是请求,写成 hook 才是保证
5. **MCP server 一接一大堆**——工具描述虽然按需加载了,但选错工具、权限面变大的风险还在。只接当前需要的
6. **长会话不管上下文**——上下文快满时会自动压缩,早期的细节指令可能丢失。重要规则放 CLAUDE.md,用 `/context` 定期看看
7. **以为检查点能撤销一切**——它只管文件,数据库和外部系统的改动撤不回来
8. **当聊天机器人用**——你给问题它给答案,但你的目标是让它**做事并自己验证**
9. **完全信任输出**——模型会出错,重要改动一定看 git diff、跑测试
10. **不学几个快捷键**——`Esc`、两下 `Esc`、`Shift+Tab`、`/clear`、`/compact`,不会这几个每天要多花不少时间
